# Протокол совместной правки

Документ для тех, кто пишет сервер под `@numior/collaboration` (первый потребитель — SaleHub).
Эталонная реализация лежит в `packages/collaboration/server` и служит тестам и песочнице: она держит
всё в памяти, не проверяет права и продуктом не является. Типы сообщений —
`packages/collaboration/src/protocol/protocol.types.ts`. Решения и их причины —
`.archcore/collaboration.adr.md`.

## Модель

Сервер задаёт единственный порядок правок. У документа есть журнал шагов, который только дополняется, и
**версия — это число шагов в журнале**. Клиент применяет свои шаги сразу и отправляет их от известной ему
версии. Если кто-то успел раньше, сервер сам переносит пачку через пропущенные шаги и записывает то, что
получилось; автору он возвращает записанные шаги, и они заменяют отправленные. Отказ `stale` остаётся
запасным путём: пачка старше окна, которое помнит сервер, или шаг, который сервер переносить не берётся.

Без переноса на сервере пачку принимал бы один участник на версию, а остальные получали бы отказ и слали
заново: при N одновременно пишущих это N²/2 отправок на раунд, и время доставки растёт с числом людей.

## Транспорт

Одно сообщение — один текстовый кадр WebSocket с JSON-объектом, поле `kind` задаёт вид сообщения.
Транспорт обязан сохранять порядок внутри соединения. Клиенту транспорт передаётся интерфейсом
`CollabTransport`, готовая реализация — `webSocketTransport(url)`.

Свой транспорт реализует `open(listener)` и возвращает соединение с `send` и `close`. События `opened`,
`message` и `closed` можно вызывать в любой момент, в том числе до возврата из `open`: клиент обработает их
сразу после возврата. События соединения, которое клиент уже закрыл или бросил, он не слушает.

Аутентификации и прав в протоколе нет: в `hello` нет токена. Их проверяют при установке соединения
(cookie, параметр адреса), и там же сервер решает, можно ли этому пользователю в документ `doc`.
`clientId` присылает клиент, поэтому связывать его с пользователем сервер должен сам.

## Сообщения клиента

| `kind`     | Поля                                   | Смысл                                                                                                                |
| ---------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `hello`    | `doc`, `clientId`, `version`, `schema` | Первое сообщение соединения. `version: null` — документа у клиента нет, нужен снимок. `schema` — `{ name, version }` |
| `steps`    | `seq`, `version`, `steps`              | Пачка шагов от версии `version`. Это конверт изменений: документ задан `hello`, `kind` шага сервер не разбирает      |
| `pull`     | `from`                                 | Прислать журнал начиная с версии `from`                                                                              |
| `presence` | `state`                                | Своё присутствие, произвольный JSON. `null` — убрать                                                                 |
| `ping`     | —                                      | Проверка связи: клиент давно ничего не слышал от сервера                                                             |

`seq` нумерует пачки внутри одного запуска клиента и нужен только для сопоставления ответа. После
перезагрузки страницы он начинается заново, поэтому повторы по нему отсеивать нельзя: от повторов защищает
проверка версии.

## Сообщения сервера

| `kind`     | Поля                                    | Смысл                                                                                                         |
| ---------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `welcome`  | `version`, `presence`, `snapshot?`      | Ответ на `hello`. `presence` — список `{ clientId, state }`. `snapshot` — только при `hello.version === null` |
| `accepted` | `seq`, `version`, `steps?`              | Пачка принята, `version` — версия журнала после неё. `steps` — шаги, записанные вместо отправленных           |
| `rejected` | `seq`, `reason`, `version`              | Пачка отклонена. `reason`: `stale` или `invalid`, `version` — текущая версия журнала                          |
| `steps`    | `version`, `clientId`, `steps`, `sent?` | Шаги из журнала. `version` — номер **перед** первым шагом пачки, `sent` — сколько шагов прислал автор         |
| `presence` | `clientId`, `state`                     | Присутствие другого участника, `null` — ушёл                                                                  |
| `pong`     | —                                       | Ответ на `ping`                                                                                               |
| `error`    | `code`                                  | `schema` — схема не совпала, `protocol` — нарушение протокола                                                 |

## Что обязан делать сервер

1. Сообщения одного документа обрабатываются строго по очереди: проверка версии и запись в журнал — одна
   атомарная операция.
2. На `hello` сверить `schema` с документом. При расхождении — `error { code: 'schema' }`, участник в
   комнату не входит. Иначе — `welcome`.
3. На `steps`:
   - `version` равна текущей: шаги применяются как есть. Не применились — `rejected { reason: 'invalid',
     version: текущая }`, журнал не меняется, частичного применения нет. Иначе записать, автору отправить
     `accepted`, всем остальным — `steps` с версией до записи;
   - `version` меньше текущей: перенести пачку через шаги журнала от `version` до текущей версии тем же
     правилом, каким это делает клиент (ниже), записать результат, автору отправить `accepted` с полем
     `steps` — записанными шагами, остальным — `steps`. Шаг, который после переноса ничего не меняет или не
     применяется, выпадает; если выпали все, автору уходит `accepted` с пустым `steps`, остальным ничего;
   - перенести нельзя (версия старше окна, которое помнит сервер, шаги не применяются к своей версии,
     `version` больше текущей) — `rejected { reason: 'stale', version: текущая }`. Журнал не меняется.
4. На `pull`: `from` больше текущей версии — `error { code: 'protocol' }`. Иначе — все шаги начиная с
   `from` сообщениями `steps`. Подряд идущие пачки одного автора можно объединять в одно сообщение. Целая
   пачка несёт `sent` — число шагов, которые прислал автор (у объединённых пачек сумма): перенос мог изменить
   их число. Пачка, отданная с середины, идёт без `sent`. Если новых шагов нет, ничего не отправлять.
5. На `presence`: запомнить или убрать состояние и разослать остальным. Когда участник отключается, разослать
   `state: null`, если у этого `clientId` не осталось других соединений.
6. На `ping` сразу ответить `pong` тому же соединению.
7. Нечитаемое сообщение и повторный `hello` — `error { code: 'protocol' }`.
8. Соединение, которое перестало отвечать, закрыть самому: иначе присутствие участника с оборванной сетью
   останется у остальных до таймаута TCP. Эталон раз в 30 секунд шлёт ping-кадр WebSocket и закрывает
   соединение, от которого с прошлой проверки не пришло ни pong-кадра, ни сообщения (`heartbeat`).

Сервер не доверяет шагам клиента: шаг перед записью проверяется и применяется к серверной копии. Для
редактора это `stepFromJSON` и `applyStep` из `@numior/editor-core`, которые сверяют форму, типы узлов,
пометки и атрибуты со схемой (`packages/collaboration/server/authority.ts`). Шаг может оказаться валидным по
форме, но неприменимым к текущему документу — это тоже `invalid`.

**Перенос опоздавшей пачки.** Серверу нужны документ версии, от которой пачка написана, и отображения
пропущенных шагов. Эталон хранит рядом с каждым из последних 4096 шагов его обратный шаг: откатывает ими
текущий документ до нужной версии, проверяет на нём пачку и вызывает `rebaseSteps` из
`@numior/editor-core` — ту же функцию, которой перебазирует очередь клиент. Свой сервер может хранить
вместо обратных шагов документы последних версий. Клиент не полагается на то, что сервер перенёс шаги
так же, как он сам: записанные шаги приходят ему в `accepted` и заменяют его версию.

**Журнал нельзя укорачивать.** Клиент, долго работавший без сети, запросит `pull` от своей старой версии, а
ответа «эта часть журнала уже удалена» в протоколе нет. Снимок для новых клиентов можно строить как угодно, но
шаги должны оставаться доступными.

**Размер пачки не ограничен протоколом.** Клиент без сети копит очередь и отправляет её одной пачкой, поэтому
лимит на размер кадра должен быть с запасом.

## Что делает клиент

Эти правила определяют, какие ответы сервера клиент переживает.

- В полёте одна пачка. Следующая уходит после `accepted`.
- `accepted` без `steps` подтверждает отправленные шаги как есть. `accepted` со `steps` означает, что сервер
  записал эти шаги вместо отправленных. К этому моменту клиент уже получил пропущенные шаги (порядок внутри
  соединения) и перебазировал очередь сам. Если его шаги совпали с записанными, это обычное подтверждение.
  Если нет, клиент откатывает очередь, убирает отправленные шаги, применяет записанные как чужие и
  перебазирует остаток очереди. Версия после `accepted` обязана равняться локальной версии плюс число
  записанных шагов, иначе клиент останавливается с причиной `protocol`.
- При `stale` клиент догоняет журнал через `pull`, перебазирует очередь и отправляет снова. Пока он позади
  известной версии, новые шаги не уходят.
- `steps` с `version` больше локальной означает разрыв: клиент делает `pull`. Шаги, которые у него уже есть,
  отбрасываются, поэтому повторная доставка безопасна.
- Если `accepted` потерялся при обрыве, свои шаги вернутся через `pull` с тем же `clientId`. Пачка с `sent`
  заменяет первые `sent` шагов очереди тем же способом, что `accepted` со `steps`; пачка без `sent`
  подтверждает шаги по одному. Поэтому `clientId` в `steps` должен быть тем, с которым шаги были записаны.
- Переподключение — экспоненциальная задержка от 200 мс до 10 с со случайной половиной, сброс после `welcome`.
  После обрыва клиент снова шлёт `hello` со своей версией.
- Соединение считается оборванным и без события закрытия. После `hello` и после пачки шагов клиент ждёт
  любого сообщения сервера 10 секунд. Если сервер молчит 15 секунд, клиент шлёт `ping` и ждёт столько же.
  Не дождавшись, он бросает соединение и переподключается: статус `offline`, очередь шагов цела. Так
  находится сокет, оборванный сном ноутбука или сменой сети. Интервалы задаёт опция `liveness`
  (`interval`, `timeout`), `interval: 0` отключает `ping`.
- `welcome.version` меньше локальной версии означает, что сервер потерял шаги. Клиент останавливается с причиной
  `diverged`.

После следующих событий клиент не переподключается, а статус становится `failed` с причиной:

| Причина    | Когда                                                                                                       |
| ---------- | ----------------------------------------------------------------------------------------------------------- |
| `schema`   | Получен `error { code: 'schema' }`                                                                          |
| `protocol` | Получен `error { code: 'protocol' }`, нечитаемое сообщение или `accepted` со `steps` не от локальной версии |
| `invalid`  | Получен `rejected { reason: 'invalid' }`                                                                    |
| `diverged` | Версия сервера меньше локальной                                                                             |
| `document` | Снимок, чужие или записанные сервером шаги не применились к документу клиента                               |

В статусе `failed` правки больше никуда не уходят, поэтому приложение обязано закрыть документ для записи
и сказать об этом человеку. `useCollabEditor` делает это сам: `failure` несёт причину и число неотправленных
шагов, `readOnly` становится `true`, `rejoin()` бросает локальную копию вместе с неотправленными шагами и
открывает документ с сервера заново. `NuiCollabFailure` показывает причину, судьбу неотправленных правок и
кнопку «Открыть заново» (событие `rejoin`); при причине `schema` кнопки нет — поможет только обновление
страницы. Для книги приложение собирает `failure` из статуса клиента и `pending()` документа, ставит листу
`readonly` и по `rejoin` создаёт новые книгу, документ и клиент.

## Шаги редактора

Сервер, который хранит шаги как есть, поля шага знать не обязан. Шаг на проводе — объект с полем `kind`.
Позиции — неотрицательные целые в документе версии, от которой применяется шаг.

| `kind`          | Поля                                                | Смысл                                                                    |
| --------------- | --------------------------------------------------- | ------------------------------------------------------------------------ |
| `replace`       | `from`, `to`, `slice`                               | Заменить диапазон                                                        |
| `replaceAround` | `from`, `to`, `gapFrom`, `gapTo`, `slice`, `insert` | Заменить края диапазона, сохранив середину                               |
| `move`          | `from`, `to`, `target`                              | Перенести целые соседние узлы `from..to` в позицию `target` без копий    |
| `addMark`       | `from`, `to`, `mark`, `skip?`                       | Добавить пометку на диапазон, `skip` — пропускаемые участки              |
| `removeMark`    | `from`, `to`, `mark`, `skip?`                       | Снять пометку                                                            |
| `attrs`         | `pos`, `attrs`                                      | Заменить перечисленные ключи атрибутов узла, остальные ключи не меняются |
| `markup`        | `changes: { pos, type, attrs }[]`                   | Сменить тип и атрибуты нескольких узлов целиком                          |
| `docAttrs`      | `attrs`                                             | Атрибуты документа                                                       |

У шага `move` диапазон `from..to` — один или несколько целых узлов одного родителя, а `target` лежит вне
диапазона: `target <= from` или `target >= to`. Узлы переезжают как есть, с теми же `id`. Позиции внутри
переезжают вместе с узлом, поэтому чужой набор, удаление и разрез абзаца в перенесённом блоке остаются на месте.
Чужой диапазон, который перенос разорвал на две части, при перебазировании отбрасывается.

`slice` — `{ content, openStart, openEnd }`. Снимок в `welcome` — `{ format: 1, schema, root }` (`toJSON`
ядра редактора). Для клиента снимок непрозрачен так же, как для сервера шаг: разбирает его адаптер
`CollabDocument`.

Комната знает шаг только через адаптер `RoomAuthority { schema, snapshot, apply, rebase? }`, поэтому шаги
листа ездят тем же конвертом, а сервер отличается только реализацией адаптера. `rebase(steps, behind)`
переносит пачку, написанную `behind` шагов назад, применяет её и возвращает записанные шаги, либо
`undefined`, когда перенести не может; без `rebase` комната отвечает `stale` на любую опоздавшую пачку.

## Шаги книги

`@numior/spreadsheet/core` использует тот же конверт со схемой `{ name: 'numior-workbook', version: 1 }`. `createStepCodec` переводит шаги
в JSON и обратно и проверяет каждое поле, `workbookAuthority` реализует `RoomAuthority` и подходит как образец для сервера.

Виды шагов: `setCells`, `setFormat`, `insertLines`, `deleteLines`, `addSheet`, `removeSheet`, `renameSheet`, `setName`, `addTable`, `setTable`,
`renameTable`, `setConditional`, `setLayout`, `setPivot`, `refreshPivot`, `putPivot`. Пачка `batch` на провод не уходит: клиент раскладывает её на
простые шаги. Эталонный снимок — `{ steps: [...] }`, список шагов от пустой книги; если книга приходит другим путём вместе с номером версии,
клиент отправляет этот номер в `hello` и снимок не запрашивает.

`setPivot` и `refreshPivot` читают вычисленные значения. Сервер, который применяет шаги, должен закончить пересчёт перед ними.

Опоздавшую пачку `workbookAuthority` переносит через структурные изменения пропущенных шагов (вставка и удаление линий, переименование
и удаление листа, переименование таблицы) функциями `stepOver` и `changesOver`. Пачку с `setLayout` без поля `base` он не переносит и
отвечает `stale`: слияние раскладки требует прежней раскладки, которая есть только у автора.

`setLayout`, `setConditional` и `putPivot` бывают двух видов. Без `base` шаг заменяет раскладку (правила) листа целиком — так пишет
интерфейс. С `base` шаг описывает изменение: `base` — что автор видел, `layout` (`formats`) — что он на это место ставит; в обоих лежит
только отличающееся (линии, ключи вида, рисунки по `id`, целиком — объединения, размеры по умолчанию, XML листа и части). При применении
каждая часть меняется, только если в книге она всё ещё равна `base`; изменённую кем-то позже часть шаг не трогает. В таком виде
приходят шаги отмены и повтора, и сервер переносит их наравне с остальными.

На клиенте документ создаётся через `createWorkbookDocument({ book, calculator })` и передаётся в `NuiSpreadsheet` пропом
`collaboration`. Отправку запускает потребитель: `@change="client.sync()"`. Присутствие — объект `{ user, place }`, где `place` равно `{ sheet, selection }` или отсутствует: его даёт событие `@presence`, входящее читает `workbookPeers` для пропа `peers`. Пример — `apps/playground/src/collab/CollabBookApp.vue`
(`/collab?book=1&user=Анна`); эталонный сервер отдаёт книгу комнатам, имя которых начинается с `book`.

## Пример обмена

```text
A → hello    { doc: "d1", clientId: "a", version: null, schema: { name: "numior-content", version: 4 } }
A ← welcome  { version: 4, presence: [], snapshot: { format: 1, … } }

B → hello    { doc: "d1", clientId: "b", version: 4, schema: { name: "numior-content", version: 4 } }
B ← welcome  { version: 4, presence: [] }

A → steps    { seq: 1, version: 4, steps: [s1] }
B → steps    { seq: 1, version: 4, steps: [s2] }

A ← accepted { seq: 1, version: 5 }
B ← steps    { version: 4, clientId: "a", steps: [s1] }

B ← accepted { seq: 1, version: 6, steps: [s2'] }    сервер перенёс s2 через s1
A ← steps    { version: 5, clientId: "b", steps: [s2'] }
```

## Присутствие

Содержимое `state` сервер не разбирает. У редактора это `{ user: { id, name, avatar? }, selection, version }`, а
точка выделения — `{ block, offset }`: id текстового блока и смещение. Смещение за концом блока прижимается.

`version` — версия документа, на которой записано выделение: версия клиента плюс число его шагов, которые ещё в
пути. Присутствие и шаги идут разными сообщениями, и получатель может увидеть присутствие раньше шагов, после
которых оно верно. Поэтому получатель с меньшей версией не ставит каретку по такому состоянию: он ждёт шагов и до
тех пор показывает участника на прежнем месте. Отправитель повторяет присутствие, когда заявленная версия
перестала подходить к его выделению: между его шагами в журнал попали чужие, и его шаги получили другие номера.
Состояние без `version` получатель ставит сразу. Канал шлёт не чаще раза в 60 мс и только когда все локальные шаги
уже ушли.

## Конфликт одного значения

Арбитр один — порядок журнала, серверу ничего делать не нужно. Два шага `attrs`, пишущие в один ключ одного
узла, применяются по порядку, и побеждает записанный позже. Проигравшее значение клиент победившего участника
показывает в истории как альтернативу и хранит локально. По сети оно не передаётся, отдельного серверного списка
нет. Вставки в текст значениями не считаются: шаги сливаются, остаются оба текста.

## Работа без сети

Для сервера такой клиент — обычный клиент, который переподключился. `@numior/offline` хранит снимок, журнал и
очередь в IndexedDB, сохраняет `clientId` между запусками и после `hello` со своей версией проходит общий путь
«`pull`, перебазирование, отправка». Записанные сервером шаги из `accepted` и из своих пачек с `sent` он пишет в
журнал вместо отправленных. Если версия схемы изменилась, миграции выполняются на устройстве до
`hello`. Если перевести данные нельзя, документ открывается только для чтения с отчётом, а очередь остаётся на
устройстве и на сервер не уходит.

Копию документа ведёт одна вкладка браузера: владельца выбирают Web Locks, без них — обмен заявками в
`BroadcastChannel`. Остальные вкладки работают как обычные клиенты без сохранения. Запись, которую браузер
отклонил, повторяется с растущей паузой до 30 секунд; правки за это время лежат только в памяти вкладки.
Приложение узнаёт о состоянии копии из `onState`: `kept`, `failing`, `elsewhere`, `unavailable`.

## Что идёт вне протокола

Комментарии (`CommentsAdapter`) и версии документа (`HistoryAdapter`) — адаптеры потребителя с собственной
доставкой. Эталонный сервер их не хранит.

Якорь комментария адаптер хранит и отдаёт как есть, не разбирая. У текстового якоря, кроме id блоков и смещений,
есть необязательное поле `at: { version, from, to }` — позиции в документе названной версии. Клиент с меньшей
версией ждёт шагов, клиент с большей ведёт позиции своими картами шагов. Запись `move` присылает только тот
участник, чья правка сдвинула якорь, и только после подтверждения его шагов.

`@numior/collaboration/yjs` — другой способ синхронизации, а не надстройка над этим протоколом: при нём шаги и
журнал не используются, документ живёт в `Y.Doc`, а транспорт выбирает потребитель.

## Как проверить свой сервер

Эталон запускается после `pnpm build` командой `node packages/collaboration/server/main.ts` на порту 4175
(другой порт задаёт `COLLAB_PORT`) и задаёт ожидаемое поведение. Правила выше покрыты тестами комнаты и клиента в
`packages/collaboration/test`, а сценарии двух браузеров — в `tests/e2e/collab.spec.ts`. Песочница `/collab`
подключается к своему серверу параметром адреса `?server=ws://хост:порт`.

Нагрузку задаёт `packages/collaboration/test/load.node.test.ts`: 20 одновременно пишущих, 100 участников с 10
пишущими и 100 одновременно пишущих — для редактора и для книги. Каждый уровень требует одинаковых документов
у всех, сохранности каждой правки, отсутствия `rejected` и ровно одной отправки на пачку.
