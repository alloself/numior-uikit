## Context

План волны 7 (блок E) требует совместной правки поверх шагов редактора: те же обратимые шаги с
отображением позиций, что у истории, центральный порядок версий на сервере и протокол, который
SaleHub сможет реализовать у себя. Yjs — необязательный адаптер последним коммитом блока, а не
основа: своя история, якоря комментариев и шаги листа завязаны на шаги ядра.

## Decision

- Пакет `@numior/collaboration` (приватный). Точка входа `.` без Vue и DOM зависит только от
  `@numior/editor-core`; `check-artifacts.mjs` проверяет отсутствие `vue`, `yjs` и `ws`. Зоны fallow:
  `collaboration` (только ядро редактора) и `collaboration-server` (`server/`, `test/`).
- Сервер — источник порядка. Журнал только дополняется, `version` равна его длине. Пачка от текущей
  версии принимается как есть. Пачку от прошлой версии сервер переносит сам через пропущенные шаги
  (`RoomAuthority.rebase`) и записывает результат; автор получает записанные шаги в `accepted.steps`.
  `rejected: stale` остаётся для пачки старше окна (4096 шагов), для шагов, не применимых к своей
  версии, и для `setLayout` книги. Причина (замер 2026-11-10): при приёме только от текущей версии
  N одновременно пишущих делают N²/2 отправок на раунд — 4 774 отправки и 3,2 с на 100 нажатий
  ста авторов, а время доставки правки растёт с числом пишущих (~N × RTT).
- Сообщения клиента: `hello { doc, clientId, version | null, schema }`, `steps { seq, version, steps }`,
  `pull { from }`. Сообщения сервера: `welcome { version, snapshot? }`,
  `accepted { seq, version, steps? }`, `rejected { seq, reason: stale | invalid, version }`,
  `steps { version, clientId, steps, sent? }` (`version` — номер перед первым шагом пачки, `sent` —
  число шагов, присланных автором), `error { code: schema | protocol }`.
  Автор получает `accepted`, остальные — `steps`. `snapshot` приходит только на `hello` с
  `version: null`.
- Шаг на проводе — объект с полем `kind` (`WireStep`). Клиент и комната знают шаг только через
  адаптеры: `CollabDocument` у клиента и `RoomAuthority` у комнаты, поэтому шаги листа поедут тем же
  конвертом. Сообщение `steps` и есть конверт `ChangeEnvelope` из плана: документ задаётся `hello`.
- `stepToJSON`/`stepFromJSON` в ядре редактора. Чтение проверяет форму, типы узлов и пометок и
  атрибуты по схеме: сервер не доверяет клиенту. Закрытые узлы среза проверяются полностью, у узлов
  на открытых краях содержимое может быть неполным, поэтому у них только тип и атрибуты.
- Клиент (`createCollabClient`): в полёте одна пачка, её подтверждает `accepted` с тем же `seq`.
  `accepted` со `steps` и своя пачка с `sent` из `pull` проходят через `CollabDocument.settle`:
  записанные шаги сравниваются с отправленными; совпали — подтверждение, нет — отправленные шаги
  откатываются, записанные применяются как чужие, остаток очереди перебазируется. Клиент не
  полагается на то, что сервер переносит шаги так же, как он: одинаковый результат — частый случай
  (в свойствах на fast-check все подтверждения редактора идут быстрым путём), а не условие сходимости.
  При `stale` клиент догоняет `pull` и отправляет заново, пока он позади известной версии, новые
  шаги не уходят. Переподключение — экспоненциальная задержка 200 мс … 10 с со случайной половиной,
  сброс после `welcome`. Свои шаги, пришедшие через `pull` (потерялся `accepted`), считаются
  подтверждением. Статус — размеченное объединение: `failed` несёт причину (`schema`, `invalid`,
  `protocol`, `diverged`, `document`), и после него клиент не переподключается.
- Плагин `collab()` хранит `{ version, unconfirmed: { step, inverted }[] }`. Удалённые шаги одной
  транзакцией: откатить неподтверждённые, применить чужие, перебазировать свои. Шаг, который после
  отображения не применился или стал пустым, отбрасывается.
- Отображения с зеркалами. `rebaseSteps` и `mirrored` вынесены из истории и экспортируются из ядра:
  перебазирование шагов и истории — один механизм. Транзакция с неподтверждёнными шагами содержит
  откаты и повторы, поэтому прямое отображение через неё схлопнуло бы всё, что внутри своего текста.
  Плагин кладёт в мету `remoteChain` цепочку отображений с зеркалами, у которой для откатов
  восстанавливаются и границы диапазонов (`edges`). По ней история перестраивает свои записи, по ней
  же отображается выделение.

- Присутствие. `presence { state | null }` от клиента, `presence { clientId, state | null }` от
  сервера, список в `welcome`. Канал отправляет не чаще раза в 60 мс и только когда все локальные
  шаги уже ушли: тогда позиция в сообщении относится к документу после пачки, которая идёт перед ним
  в том же сокете. Состояние редактора — `{ user, selection, version }`, точки выделения заданы id
  текстового блока и смещением, смещение за концом блока прижимается; о версии — абзац про находку L4
  ниже. После приёма позиции двигаются транзакциями. Слой курсоров
  (`NuiCollabCarets`) лежит поверх текста в слоте `overlay` у `NuiEditor` и не трогает DOM блока, а
  выделение рисуется inline-декорациями; цвет выбирается по id пользователя из восьми `--nui-chart-*`.

- Комментарии. Адаптер `CommentsAdapter` (`list`, `create`, `reply`, `resolve`, `remove`, необязательные
  `move` и `subscribe`) лежит в `.`, панель `NuiEditorComments` и `useEditorComments` — в `./vue`. Якорь
  хранится как `AnchorJSON` (id текстового блока и смещение), живые позиции держит плагин ядра
  `commentAnchors`, поэтому редактор сам двигает их через локальные и чужие шаги: чужие идут по
  `remoteChain`, как история. Изменившийся якорь пишет в `move` только автор сдвинувшей его правки, не
  чаще раза в секунду и после её подтверждения (абзац про находку E11 ниже). Каретка внутри
  якоря активирует его ветку прямо в `apply` плагина, без второго прохода. Решённые ветки не держат
  якорь и ставят его заново при открытии. Панель получает контроллер из `useEditorComments` и тексты
  из каталога, `labels` перекрывает отдельные. Эталонный сервер комментарии не хранит: их доставка —
  дело адаптера, в песочнице он живёт в памяти вкладки.
- Комментарий живёт у своего текста (ревью 2026-11-09): кнопка стоит в панели над выделением через
  `selectionActions` у `NuiEditor` (на телефонах панели над выделением нет, кнопка та же в панели
  инструментов), черновик и ветка открываются в `NuiEditorCommentPopover` — поповере, привязанном к
  координатам якоря. Поповер открывается только действием: кнопкой, щелчком по подсвеченному тексту или
  из списка; каретка, проходя через якорь, только подсвечивает его, иначе поповер всплывал бы при
  наборе и стрелках. Поэтому открытая ветка (`opened`) — отдельное состояние, а не `active`.
  `NuiEditorComments` остался сводным списком, в песочнице он открывается кнопкой «Обсуждения».
- Выделение всего документа (`all`, в том числе единственная строка целиком) становится якорем по краям
  его текста: иначе весь текст нельзя было бы прокомментировать. Показ, решение и удаление ветки —
  кнопки-иконки с подсказками, ответ — текстом, чтобы действия не переносились в панели шириной 20rem.

- Версия у присутствия (2026-11-10, находка L4). Порядок сообщений в одном сокете не спасал получателя:
  присутствие автора приходит от сервера отдельным сообщением и может обогнать шаги, после которых оно
  верно, — каретка участника вставала со сдвигом на символ и оставалась так до его следующего движения.
  Теперь `presenceOf` пишет `version` — версию клиента плюс шаги в пути, а плагин `remotePresence` хранит
  `{ peers, held }`: состояние с версией выше своей лежит в `held`, участник показан на прежнем месте
  (новый — без позиции) и встаёт на заявленное, когда транзакция довела версию. `setRemotePresence`
  передаёт плагину сырую карту состояний, разбор и ожидание — в `apply`. Отправитель повторяет
  присутствие по `presenceChanged`: выделение то же, но заявленная версия больше нынешней, либо меньше
  при шагах в пути (его шаги получили другие номера из-за чужих). Журнал отображений для этого не нужен:
  точка задана id блока и смещением, ждать приходится только самих шагов. Без плагина `collab` версии нет
  и всё ставится сразу.

- Версия у якорей комментариев (2026-11-10, находка E11, решение пользователя 3). Раньше каждый клиент
  писал якорь из своего документа: N участников — N записей на одну правку, и запись клиента, у которого
  шаги ещё в пути, ставила якорь у остальных не туда. Теперь плагин `collab` хранит хвост из 512 карт
  позиций подтверждённых шагов (`trail`), `positionsSince(state, version)` собирает из него и своих
  неподтверждённых шагов отображение от версии к нынешнему документу. Текстовый якорь несёт
  `at: { version, from, to }` — позиции в документе этой версии. Правила приёма в `useEditorComments`:
  версия якоря впереди своей — ветка ждёт шагов и ставится, когда версия дошла; версия в пределах хвоста —
  позиции ведутся картами, id блока и смещение не читаются; версия старше хвоста или якорь без `at` —
  ставится по id блока и смещению, а уже поставленный живой якорь таким не заменяется. Пишет якорь только
  тот, чья правка его сдвинула, и только когда все его шаги подтверждены: тогда его документ равен
  серверному и `at` верен для всех. Комментарий, созданный при шагах в пути, уходит без `at`, запись с
  версией следует после подтверждения. Без плагина `collab` версии нет и всё работает по id и смещению.
  Отвергнуто: сервер комментариев, который сам двигает якоря, — ему пришлось бы применять шаги документа,
  а адаптер комментариев о документе не знает.

- История версий. Адаптер `HistoryAdapter` (`versions`, `load`, необязательный `save`) лежит в `.`, панель
  `NuiEditorHistory` и `useEditorHistory` — в `./vue`. Сравнение делает `diffDocs(before, after)` в ядре:
  блоки сопоставляются по id, текст внутри блока — по словам, результат — обычный документ в производной
  схеме с пометками `diff_added` и `diff_removed` (`<ins>`, `<del>`), поэтому предпросмотр рисует тот же
  `NuiContent` без отдельного рендера. Версия сравнивается с предыдущей сохранённой. Удалённый блок стоит
  после своего уцелевшего соседа; блоки без текста в разметке не помечаются, удалённые не показываются,
  перемещённые блоки изменением не считаются. Блок, у которого произведение числа слов двух версий больше миллиона, заменяется целиком, чтобы не
  строить большую таблицу. Восстановление — одна обычная транзакция `replaceDocument`: она отменяется и
  уходит остальным участникам как любая правка.

- Хранилище без сети. `@numior/offline` держит базу `nui-offline:<docId>` из хранилищ `meta`, `snapshot` и
  `steps`. Шаг лежит под версией, от которой он отправляется. Чтение отдаёт журнал только до первого
  разрыва, повреждённый снимок считается отсутствующим. Уплотнение проигрывает журнал поверх снимка в той
  же схеме и пишет новый снимок одной транзакцией вместе с удалением покрытых шагов; если шаг не
  применяется, журнал остаётся как есть. Более старый снимок не заменяет новый, поэтому две вкладки одного
  документа не портят базу.
- Очередь и восстановление. Коллаборация объявляет `CollabPersistence` (`restore`, `track`, `close`), а
  `offlinePersistence` из `@numior/offline` её реализует, поэтому зависимость идёт в одну сторону. В хранилище
  `outbox` одна запись `{ clientId, baseVersion, steps }`, не по записи на шаг, как планировалось: перебазирование
  переписывает всю очередь. Шаги журнала и очередь пишутся одной транзакцией, иначе база окажется в состоянии, где
  очередь отправляется не от той версии, что в журнале. Записи идут по одной, накопленное склеивается в следующую.
- `clientId` сохраняется и после перезапуска возвращается, чтобы шаги, подтверждение которых потерялось, пришли из
  `pull` как свои. Id блоков получают новый префикс на каждый запуск, иначе новые блоки совпали бы с прежними. Если
  из `pull` приходит больше своих шагов, чем лежит в очереди (сбой между отправкой и записью), остаток применяется
  как чужие шаги, а не теряется.
- Хранилищем документа владеет одна вкладка, через Web Locks. Вторая работает как обычный клиент без сохранения, и
  запись второй не затрёт очередь первой. После закрытия первой хранилище достанется следующей открытой вкладке.
  С восстановленным документом клиент стартует только когда редактор смонтирован: иначе `hello` ушёл бы с пустой
  версией и сервер прислал бы снимок поверх восстановленного.

**Конфликт одного значения.** Шаг `attrs` теперь патч: несёт только изменённые ключи, а обратный ему
восстанавливает только их. Прежний шаг записывал объект атрибутов целиком, поэтому перебазированная
локальная правка и отмена затирали устаревшим значением чужое изменение соседнего ключа. Арбитр один —
порядок сервера: локальный шаг перебазируется и приходит на сервер позже, значит его значение
побеждает, а проигрывает значение из чужого шага. Конфликт — это чужой шаг `attrs` или `markup` и
неподтверждённый локальный, которые пишут в один ключ одного узла разные значения; сравниваются
итоговые значения пачки и очереди, поэтому промежуточные правки в список не попадают. Проигравшее
значение становится `CollabAlternative { version, nodeId, attr, value, clientId, author, createdAt }`:
`version` — номер проигравшего шага в журнале сервера, `createdAt` — только для показа. `NuiEditorHistory`
с пропом `alternatives` показывает список: значение, автор, «Вернуть» (новый обычный шаг), «Показать в
документе», «Скрыть». С `offlinePersistence` список лежит в хранилище `alternatives` и пишется одной
транзакцией с журналом шагов.

Отклонения от плана: метода `HistoryAdapter.alternatives` нет, список локальный (память и IndexedDB),
а не серверный. Поэтому проигравшее значение видит только тот, чья правка победила: только его клиент
перебазирует шаги и знает о совпадении; второй участник видит лишь новое значение. Конфликт в тексте
(`replace`) значением не считается: шаги сливаются, оба текста остаются. Шаг `markup` по-прежнему несёт
атрибуты целиком, потому что меняет и тип узла; при пакетной смене разметки сосед по ключу может быть
затёрт. Если узел уже удалён, «Вернуть» только убирает запись.

**Версии схемы и плагинов.** `offlinePersistence` сверяет сохранённые `meta.schema` и `meta.plugins`
с текущими до выдачи документа. Для каждого расхождения ищется цепочка `migrations` (`{ subject, from,
to, document, step }`, `subject` — `schema` или имя плагина, отсутствующий плагин считается версией 0).
Цепочка переводит снимок, журнал и очередь и пишется одной транзакцией, штамп схемы ставит сам `offline`.
Нет цепочки, сменилось имя схемы, `step` вернул `undefined` или документ не проигрывается — восстановление
возвращает `CollabBlocked` с отчётом `CollabReport { blocks, unsent }`, и хранилище больше не трогается.
Шаги никогда не отбрасываются: чего нельзя перевести, то блокирует весь документ. `useCollabEditor`
закрывает хранилище, ставит `readOnly` и `report`. Читаемую копию показывает без соединения, иначе
открывает документ с сервера без записи на устройство. `NuiCollabReport` выводит отчёт, проп `readonly`
редактора потребитель связывает с `readOnly` сам. Откат приложения обратно к сохранённой версии снимает
блокировку, и очередь уходит как обычно. Раньше нечитаемая копия молча заменялась снимком сервера вместе
с очередью; теперь это блокировка `damaged`.

**Отказ синхронизации.** Раньше после `failed` клиент молча принимал набор, который никуда не уходил, а
человек видел только слово статуса. Теперь `useCollabEditor` при `failed` ставит `failure { reason, unsent }`
и `readOnly`, а `rejoin()` останавливает клиента, снимает редактор (`ready = false`), после перерисовки
создаёт нового клиента и берёт документ с сервера; локальная копия на устройстве заменяется снимком сервера,
очередь очищается. `NuiCollabFailure` — сообщение `role="alert"` с причиной, числом неотправленных правок и
действием «Открыть заново»; слот `actions` принимает свои действия (сохранить копию). При причине `schema`
действия по умолчанию нет. Автоматического повторного входа нет: без решения человека неотправленные правки
не выбрасываются. Клиент ядра не изменён — для книги то же собирает приложение (новые книга, документ и
клиент), потому что снимок книги — журнал шагов и поверх живой книги не загружается.

**Yjs.** Точка входа `@numior/collaboration/yjs`, `yjs` — необязательный peer: `.` и `./vue` его не
импортируют (проверяет `check-artifacts.mjs`). `yjsBinding(ydoc, fragment, { schema, getState, dispatch,
onInvalid })` заменяет `collab()`: элементы — `Y.XmlElement` с атрибутом `nui:id` (значения атрибутов в
JSON), подряд идущий текст — один `Y.XmlText`, пометки — форматирование. Отклонение от плана: локальная
правка сравнивает дерево Yjs с документом, а не переводит шаги. Узлы не пересобираются по ссылке (карта
`Y.XmlElement → узел`), поэтому незатронутые блоки стоят одной проверки ссылки. Событие Yjs читается обратно
в дерево и становится одним шагом замены минимального диапазона, а смена только атрибутов — шагом `attrs`,
с `remoteChange`, поэтому своя история отменяет только свои правки. Несколько несвязанных изменений в одном
событии сливаются в один диапазон, и каретка внутри него уезжает в конец. Если слияние Yjs оставило узел с
недопустимым содержимым или дублем id, такой узел удаляется и эта правка пишется обратно: все клиенты делают
одно и то же. Неизвестный тип, пометка или нечитаемые атрибуты — `onInvalid`, дерево не трогается. Атрибуты
корня не синхронизируются: у фрагмента их нет, и схемы кита их не задают.

**Площадка в песочнице.** `/collab` без параметра `user` открывает две панели (Анна и Борис) в iframe над одной
комнатой: вкладки «Редактор» и «Книга», список сценариев, «Новая комната», перезагрузка панели и переключатель
«Связь», который обрывает соединение одной панели. `pnpm dev` сам поднимает эталонный сервер на порту 4175: плагин
`apps/playground/collab-dev-server.ts` загружает `server/reference-server.ts` через SSR Vite; занятый порт только
предупреждает. Порт меняет переменная `COLLAB_PORT` (2026-11-10): плагин кладёт его в `<meta name="nui-collab-port">`
страницы, приложения лаборатории читают его оттуда, e2e — из той же переменной. Без неё второй dev-сервер на
машине молча ходил в сервер первого. Офлайн-хранилище включено у левой панели: панели делят один origin и одну IndexedDB.

### Перенесённые блоки

Отступ пункта (`sinkListItem` = удаление + вставка) и перенос блока с преобразованием (один шаг
`replace` с теми же id) для отображения позиций выглядят удалением. Перенос блока как есть с 2026-11-10 —
шаг `move`, позиции в нём не удаляются. Правило одно для всего класса:
позиции и перебазируемые правки идут за id узла.

- `followPosition(pos, mapping, before, after, assoc)` в `state/selection.ts`: если позиция удалена, а её
  блок с тем же id есть в новом документе, позиция встаёт на то же смещение в нём. На нём стоят
  `mapSelection`, якоря комментариев и каретки участников.
- `rebaseSteps` получает `RebaseDocs { written, current }`. `history/retarget.ts`: текстовые шаги в
  пределах одного блока, `attrs` и `markup` идут за id; снятые узлы запоминаются по id, в том числе из
  того же шага; узлы в срезе шага заменяются последней версией, если шаг их не менял.
- Перенос блока — шаг `move` (2026-11-10, `.archcore/editor.adr.md`, «Шаг move»): узлы не копируются, чужие
  правки в перенесённом блоке и между блоками сохраняются при любой очерёдности доставки.
- Текстовый шаг идёт за id блока, только если его позиция попала в удалённый диапазон (2026-11-10, находка E5).
  Раньше хватало того, что позиция оказалась в другом блоке: после чужого Enter перед правкой набранный текст
  уезжал в конец левой половины абзаца, а удаление и пометка схлопывались и терялись.
- Отмена удаляет только своё (2026-11-10, находка E6). Обратный шаг вставки — удаление диапазона; при
  перебазировании истории оно растягивалось на текст, который участник набрал внутри вставленного слова, и Ctrl+Z
  стирал чужой текст. `rebaseHistory` (`history/rebase.ts`) режет такое удаление на части вокруг чужих вставок:
  один шаг истории становится несколькими, карта позиций у них общая. Повтор возвращает слово вокруг чужого текста.
  Одновременные правки это не меняет: удаление, которое ещё не подтверждено, по-прежнему побеждает чужую вставку
  внутри своего диапазона, а вставка внутрь уже удалённого диапазона отбрасывается (как в ProseMirror).
- `receiveSteps` и `settleSteps` отвечают `undefined`, когда чужой или перебазированный сервером шаг не
  применяется (2026-11-10, находка E9). Раньше они бросали исключение: клиент оставался `online`, отправка
  останавливалась, правки копились молча. Теперь адаптер документа отвечает `false`, клиент переходит в
  `failed: document`, документ остаётся прежним.
- Обрыв без события закрытия (2026-11-10, находки E10 и E14). Сон ноутбука и смена сети оставляют сокет
  полуоткрытым: браузер не сообщает о закрытии, клиент оставался `online` и ждал `accepted` вечно. Теперь
  клиент ждёт ответа на `hello` и на пачку шагов 10 секунд, а после 15 секунд тишины шлёт `ping` и ждёт
  `pong` (`client/liveness.ts`, опция `liveness`). Не дождавшись, он бросает соединение и переподключается
  (`reconnecting.restart`), события брошенного соединения не слушает. `ping`/`pong` — сообщения протокола,
  а не кадры WebSocket: кадрами браузер не управляет. `pull` для проверки не годится, сервер молчит, когда
  новых шагов нет. Сервер-эталон закрывает молчащие соединения сам (ping-кадры WebSocket, `heartbeat`,
  30 секунд), иначе присутствие ушедшего участника висит до таймаута TCP.
  Соединение открывает `link.start()` после сборки клиента, события транспорта до возврата из `open`
  откладываются. Раньше транспорт с синхронным `opened` падал на обращении к ещё не созданной связи.
- Известный пробел: история отмены документов не хранит. Если участник B перенёс блок, Ctrl+Z участника A
  пропускает текст, набранный A в этом блоке до переноса. Текст не теряется, не отменяется только этот
  набор. Хранить документы ради этого случая слишком дорого по памяти.

## Rejected

- Отображать историю чужими шагами, перенесёнными поверх своих. При вставке в одну точку порядок
  получался обратным серверному, и отмена удаляла чужой текст; при удалении вокруг своего текста
  запись истории пропадала.
- `rejected: schema` из плана. Несовпадение схемы проверяется один раз на `hello` и отвечается
  `error { code: schema }`: отдельная проверка каждой пачки ничего не добавляет.
- Каретка виджетом внутри строки из плана. Виджет ядра ставится только между блоками, а DOM внутри
  текста мешал бы вводу и IME соседа и перерисовывал бы блок при каждом движении чужого курсора.
  Версия в присутствии сначала тоже была отвергнута, с 2026-11-10 она есть (находка L4).
- Общий разбор сообщений клиента и сервера. Клиенту нужны только сообщения сервера, серверу — только
  клиента, а сервер запускается в Node напрямую и из `src` берёт только файл протокола без импортов
  значений.

## Consequences

- `.` не содержит кода Vue. UI присутствия, комментариев и истории — точка входа `./vue`, зона
  fallow `collaboration-vue`. `useCollabEditor` даёт `NuiEditor` плагины, источник id и документ из
  снимка, поэтому редактор монтируется только после `welcome`.
- Каждый клиент обязан передавать в `createState` свой источник id (`createIdSource` с префиксом
  клиента): при совпадении id новых узлов сервер отвергнет шаг как `invalid`. `useCollabEditor` делает
  это сам через проп `ids` у `NuiEditor`.
- Вставка внутрь диапазона, удалённого другим участником, теряется, как и в модели ProseMirror.
- Другие плагины видят сырое `tr.mapping`. Якоря комментариев и история идут по `remoteChain`.
- Протокол для внешних серверов описан в `docs/collaboration-protocol.md`, этот файл хранит решения и их
  причины. Изменение сообщений или обязанностей сервера правит оба документа.
- В протоколе нет ответа на `pull` из удалённой части журнала, поэтому журнал сервера нельзя укорачивать.
  Аутентификации и прав в нём тоже нет: они решаются при установке соединения.
- Конверт не знает вида шага, поэтому шаги листа идут тем же сообщением `steps`, а отличается только
  `RoomAuthority`.

## Тесты

Свойства на `fast-check`: два и три клиента, случайные чередования правок (набор, удаление, пометки,
разбиение, отмена, повтор) и доставок сообщений, в итоге все документы равны серверному и очередей
нет. Клиент — на поддельном транспорте с фейковыми таймерами, комната — напрямую, сервер — через
настоящий WebSocket.
