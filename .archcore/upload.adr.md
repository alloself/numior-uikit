## Context

Базовый состав 1.0 требует контрол загрузки файлов. Приложения загружают по-разному: через
SDK, presigned URL, чанки, с авторизацией и повторами, поэтому кит не может владеть HTTP.
При этом очередь, прогресс, отмена, повтор, валидация и превью одинаковы везде, и их
разумно держать в одном месте с доступной разметкой.

## Decision

- Сеть — только адаптер `upload(file, { onProgress, signal }) => Promise<R>`. Кит не знает про
  URL, заголовки и формат ответа; результат адаптера кладётся в `result` элемента. Пример
  XHR-адаптера (единственный способ получить прогресс отправки) живёт в документации.
- `v-model` `NuiUpload` — массив `NuiUploadItem` с `id`, именем, размером, типом, статусом
  `queued | uploading | done | error`, прогрессом `0…1`, `file?`, `url?`, `result?`, `error?`.
  Форма редактирования передаёт уже загруженные файлы без `file`; форма видит pending по
  статусам. Object URL превью в модель не попадают: они живут в компоненте и отзываются при
  удалении и размонтировании.
- Очередь (`useUploadQueue`) стартует загрузки сразу с лимитом `concurrency` (по умолчанию 3);
  `auto=false` держит файлы в `queued` до `start()`. Очередь держит собственный список и
  пишет его в модель заменой массива, поэтому под контролируемым `v-model` последовательные
  операции в одном тике не теряют друг друга; внешняя замена списка (сброс формы) абортит
  активные загрузки. Элемент ищется по индексу `id → позиция`, а не проходом по списку; отчёты
  `onProgress` копятся и попадают в модель одной заменой массива за кадр
  (`requestAnimationFrame`), так что частые события прогресса нескольких загрузок стоят одну
  копию списка на кадр, а не на событие. Неизменяемая модель требует новой копии массива при
  каждом изменении, поэтому меньше O(N) на запись не бывает; реже — можно. Следующий файл в
  очереди ищется от курсора первого `queued`, поэтому запуск всей очереди линеен.
- Валидация (`validateFiles`): `accept` (расширение, точный тип, `type/*`), `maxSize`,
  `maxFiles` с учётом уже лежащих в модели, свой `validate(file)`. Проп `rejected: 'list' |
  'drop'` решает, попадает ли отклонённый файл в список с причиной (`type`, `size`, `count`,
  `custom`) или отбрасывается; событие `reject` уходит в обоих режимах. Порядок файлов в
  списке совпадает с порядком выбора.
- Действия: отмена абортит и удаляет элемент; повтор есть только у ошибок адаптера; удаление
  готового файла меняет модель и шлёт `remove`, адаптера удаления нет — сервер чистит
  приложение при submit.
- Виды: dropzone со списком (`NuiRow` + `NuiProgress`) и dropzone с сеткой миниатюр
  (`layout="grid"`). Вся зона кликабельна, с клавиатуры работает видимая кнопка «Выбрать
  файлы», на которой id поля и `aria-describedby` из `NuiField`; тексты — пропами, слот по
  умолчанию заменяет содержимое зоны. Статусы объявляются через `aria-live`.
- Направление письма и локаль берутся из конфига: размеры форматируются `formatFileSize`
  через `Intl.NumberFormat` с единицами байтов по степеням 1024.

### Уточнения после аудита (2026-09-28)

В одиночном режиме замена происходит только после проверки: отклонённый файл не удаляет уже
выбранный. `disabled` закрывает и приём файлов, и действия строк — кнопки строки выключены,
`discard` и открытый метод `remove` ничего не делают.

## Alternatives Considered

- `action`-URL с XHR внутри компонента (Element/Ant): проще старт, но SDK, presigned S3 и
  чанки всё равно требуют адаптер, а в ките появился бы HTTP-клиент.
- Модель только из результатов адаптера: чище для формы, но прогресс и ошибки снаружи не
  видны, а pending пришлось бы выводить отдельно.
- Только события без модели: не ложится в будущие контракты forms (value/reset/pending).
- Кнопочный вариант без зоны и режим аватара: сделаны 2026-09-28 в волне 7 — `variant="button"`
  у `NuiUpload` (скрытый input общий для обоих вариантов, drop не принимается) и отдельный
  `NuiAvatarUpload` (одно изображение, `v-model: item | null`, превью в `NuiAvatar`, замена по
  клику или сбросу файла на аватар, отклонённый файл не трогает текущее изображение, тексты
  ошибок из общего модуля `upload-errors.ts`).
- Значок загрузки на аватаре (2026-10-02): центр значка лежит на краю круга под 45°, а у
  квадрата значок выступает за угол на те же два пикселя и кольцо. Раньше он стоял в углу
  описанного квадрата, то есть внутри круга, и закрывал инициалы. Кольцо — тень цвета
  `--nui-ring`, как у статуса `NuiAvatar`, а не рамка цвета поверхности. Глиф занимает две
  трети значка с утолщённым штрихом: лоток иконки `upload` иначе упирался в край круга.

## Consequences

`@numior/primitives` получает `validateFiles`, `useFileDrop`, `useUploadQueue`,
`formatFileSize`; `@numior/vue` — `NuiUpload`, алиасы иконок `upload` и `refresh`. Проверка:
unit через `UploadDriver` и харнессы очереди и drop-зоны, SSR-сценарий, e2e
`tests/e2e/upload.spec.ts` (выбор, drop, прогресс, отклонения в двух режимах, повтор, отмена,
миниатюры, клавиатура, axe). Дальше: 5d layout и sidebar.
