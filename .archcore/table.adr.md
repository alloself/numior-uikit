## Context

План 1.0 требует DataGrid на миллион локальных строк с сортировкой, фильтрами, группами,
деревом, закреплением, виртуализацией, редактированием, диапазонами и copy/paste в двух режимах:
локальном и серверном. Интервью волны 7 (2026-09-27) отказалось от выбрасываемых прототипов:
первый коммит модуля — настоящее ядро плюс воспроизводимый бенчмарк, а цели плана (1 000 000
строк, p95 обычного ввода ≤ 100 мс, первый кадр сортировки/фильтра ≤ 250 мс, куски работы
≤ 16 мс) — пороги приёмки, а не пожелания. Решение 2026-09-29: `NuiTable` из `@numior/vue` и
`NuiDataGrid` объединяются в один `NuiTable` на этом ядре, пакет переименован в `@numior/table`;
имя компонента, блок `nui-grid`, словарь `dataGrid` и типы `NuiGrid*` держатся до удаления старой
таблицы, потому что два `NuiTable` не уживаются в справочнике доков, реестре словарей и стилях
песочницы.

## Decision

- Пакет `@numior/table` (до 2026-09-29 `@numior/grid`) с точками входа `.` (`NuiTable`, колонки, типы моделей) и
  `./engine` — ядро без Vue и DOM. Проверка `check-artifacts.mjs` требует, чтобы `dist/engine.js`
  не импортировал `vue`; тесты ядра идут в Node-проекте vitest (`*.node.test.ts`).
- Строки остаются объектами потребителя без копирования. Ключи колонок строятся лениво и только
  для колонок запроса: числа, даты и булевы — `Float64Array` с битовой картой пропусков `nulls`,
  строки — в два уровня. Уровень `codes` (словарь уникальных значений и коды строк `Uint32Array`)
  нужен фильтрам; уровень `string` добавляет ранги — позиции в словаре, отсортированном
  `Intl.Collator` (`numeric: true` по умолчанию, коллатор настраивается), — и нужен сортировке,
  группам и `distinct`. План прогона просит у каждого ключа свой уровень, готовые коды
  доранжируются без повторного прохода по строкам (2026-09-28, коммит 6: быстрый фильтр по всем
  строковым колонкам иначе ранжировал бы миллион уникальных email ради поиска подстроки).
  Хранилища кешируются до смены строк. Словарь собирается одним `Map`: при последнем удвоении
  таблицы на миллионе уникальных значений V8 перестраивает её за один вызов (24 мс — единственный
  кусок длиннее 16 мс на холодном построении, замер 2026-09-28); если это станет заметно во вводе,
  словарь можно разбить на несколько `Map` по дешёвому хешу строки.
- Результат прохода — `Uint32Array` индексов. Сортировка массивов от 1024 индексов —
  устойчивая поразрядная LSD-сортировка по 16-битным разрядам (2026-09-28, коммит `perf`):
  числа, даты и булевы переводятся в беззнаковые 64-битные ключи с сохранением порядка
  (инверсия отрицательных, флаг знака у положительных, `-0` сливается с `0`), строки — ранги
  словаря в 32 бита; пропуски получают максимальный ключ и остаются последними в обоих
  направлениях, убывание — инверсия ключа (для рангов — `size − 1 − rank`). Ключи по одной
  колонке собираются в выровненные буферы вместе с индексами, разряды, одинаковые у всех строк,
  пропускаются по гистограмме, а несколько колонок сортируются от младшей к старшей. Маленькие
  массивы (братья в дереве) сортируются устойчивым слиянием с тем же сравнением; равные ключи
  всегда сохраняют исходный порядок строк.
- Любой проход длиннее бюджета режется на куски: работа идёт до `deadline`, проверяя время каждые
  2048 элементов, затем уступает хосту (`scheduler.yield()`, иначе `MessageChannel`) и
  продолжает с того же места. `run(query, { signal, onProgress })` отдаёт прогресс по фазам
  (`keys`, `sort`), отменяется сигналом и устаревает при следующем `run` или `setRows`; результат
  — размеченное объединение `done | cancelled`, исключений для отмены нет. Неизвестный ключ
  колонки — ошибка программиста и бросается сразу.
- Прогон — один возобновляемый конвейер этапов (хранилища → фильтр → сортировка → группы или
  сортировка братьев), который строит следующий этап из результата предыдущего и сообщает
  прогресс по завершении каждого этапа. `run` ведёт его кусками с уступками, а `runSync` —
  тот же конвейер без уступок для первого рендера и SSR, поэтому сервер и клиент получают один
  порядок строк; оба вытесняют незавершённый прогон.
- Фильтры — размеченное объединение по типу колонки: `text` (contains/equals/starts/empty без
  учёта регистра, проверка один раз на запись словаря), `number` и `date` (открытые диапазоны,
  пропуски не проходят внутрь диапазона), `set` (значения, включая `null`) и `quick` (contains по
  всем строковым колонкам). Проход фильтра даёт битовую карту, затем уплотняется в индексы;
  фильтр не того типа для колонки — ошибка программиста. Текстовые условия, наборы строк и `quick`
  сначала проходят словари отдельным заданием этапа фильтра с той же нарезкой по времени: карта
  совпадений на код словаря, нижний регистр кешируется на словаре и заполняется по ходу прохода,
  поэтому новый текст фильтра платит только за `includes` по уникальным значениям. Затем проход по
  строкам читает готовые карты; `quick` проверяет строку только по колонкам, в словаре которых есть
  совпадения, одним циклом без замыкания на колонку, а пустой `quick` выпадает из плана. Пустая строка и `null` для `set` — одно
  значение «пусто»: `distinct` отдаёт одну метку `null`, а `set` с `null` пропускает и пустые
  строки, как условие `empty` текстового фильтра.
- Группы: ключи `groupBy` встают впереди пользовательской сортировки, один линейный проход по
  отсортированным индексам открывает и закрывает группы и копит агрегаты (`sum`, `count`, `avg`,
  `min`, `max` по хранилищам или функция от индексов группы) плюс итоги по всем строкам. С коммита
  7a проход идёт отрезками между границами групп: агрегаты отрезка считаются плотным циклом по
  типизированным массивам и только в самой глубокой открытой группе, родители и итоги получают их
  слиянием накопителей при закрытии группы (группировка по двум ключам на миллионе строк — 136 мс
  вместо 289). Итоги и
  хранилища агрегируемых колонок строятся только при группировке или флаге запроса `totals`
  (подвал с итогами), иначе обычная сортировка платила бы за них на каждом прогоне; узлы
  групп имеют `id` — JSON пути значений; развёрнутость хранится множеством переключённых `id`
  относительно `defaultExpanded`, видимый список пересобирается синхронно при `toggle`.
- Дерево: `children(row)` разворачивается в плоскую таблицу DFS с массивами родителей и глубин,
  хранилища строятся по ней; фильтр проходит снизу вверх (предок остаётся, если прошёл потомок),
  сортировка идёт внутри братьев тем же резюмируемым слиянием, обход даёт полный и видимый
  порядок; `keyOf` даёт id строк для развёрнутости. Группировка дерева не поддерживается.
- `distinct(key, { limit, signal })` строит хранилище кусками и отдаёт значения в порядке
  коллатора (строки — из отсортированного словаря, числа — уникальные ключи) с флагом усечения;
  лимит считает только непустые значения, метка пустых идёт сверх него. Числа проходят хранилище
  нарезаемым заданием, которое держит только `limit + 1` наименьших уникальных ключей в
  отсортированном массиве, поэтому миллион уникальных сумм не собирается в множество целиком.
- Рендер (`NuiTable`, вход `.`): один скроллер `role="grid"` с липкой шапкой (`rowgroup`) и
  телом высотой в холст. Каждая строка — один flex-элемент шириной в холст с тремя панелями
  `role="presentation"`: начало (`position: sticky` к `inset-inline-start`), середина (оконные
  ячейки, позиция — `inset-inline-start` в пикселях) и конец (sticky к `inset-inline-end`).
  Горизонтальная и вертикальная прокрутка у панелей общая по построению, без синхронизации в
  JS, а RTL получается из логических свойств. Строки окна идут подряд в `<tbody>`, а на место
  их ставит сама `<table>` между двумя спейсерами вьюпорта: она липкая по оси y с границами, за
  которые окно не уходит (с 2026-10-01; до этого — липкие ячейки по `--_top`, ещё раньше —
  строки-пропуски).
- Окна — два `useVirtualList` на одном скроллере: строки (ось y, `inset` — высота шапки,
  `maxSize` 15 000 000 px — ниже потолка Firefox ≈ 17,9M, `pinned` — активная строка) и колонки
  середины (ось x, `inset` — ширина закреплённых панелей, `pinned` — активная колонка).
  Первый экран на сервере — 30 строк и 12 колонок середины.
- Строка — компонент `NuiTableRow` с примитивными пропсами (позиция, смещение, активная
  колонка, ревизия данных) и одним стабильным слотом, через который грид отдаёт содержимое
  ячеек. Поэтому строка перерисовывается только при смене своих пропсов или данных, которые
  читают её ячейки; компонента на ячейку нет.
- Доступность и фокус: `aria-rowcount`/`aria-colcount`, `aria-rowindex` (шапка = 1),
  `aria-colindex` в визуальном порядке, `columnheader`/`gridcell`. Roving tabindex: у активной
  ячейки `tabindex="0"`, у остальных `-1`; шапка — строка −1 в навигации. Обработчик клавиш
  (стрелки через `listMoveFor` с учётом RTL, Home/End, Ctrl+Home/End, PageUp/PageDown) решает
  цель и прокручивает окна до рендера, post-flush наблюдатель только ставит фокус с
  `preventScroll`; `focusin` синхронизирует активную ячейку после клика.
- Колонки — размеченное объединение по `type` (`text`, `number`, `date`, `boolean`): `value` и
  `format` типизированы по виду и один к одному ложатся на виды колонок движка. `format` получает
  строку вторым аргументом; вне строки (список значений фильтра, дальше — заголовки групп) строка
  равна `undefined`, и тип требует это учесть. Ячейки и подписи значений форматирует одна
  функция `valueTextOf`. Форматирование
  по умолчанию: числа — `formatNumber` локали, даты — `Intl.DateTimeFormat` со `dateStyle:
  'medium'` в UTC (день даты без времени не сдвигается часовым поясом, SSR детерминирован),
  булевы — словарь `dataGrid`. Пустой грид — строка с `gridcell` на все колонки с `NuiEmpty` или
  слотом `empty`.
- Сортировка из шапки: интерактивна сама ячейка `columnheader` (она в roving-навигации), клик
  или Enter/Space идут по кругу «по возрастанию → по убыванию → без сортировки», Shift
  добавляет колонку следующим ключом или меняет её направление в списке. `v-model:sort` —
  сериализуемый список `{ key, direction }`; `aria-sort` стоит только у главного ключа, у
  остальных — видимый номер ключа и скрытый текст «ключ сортировки N», а изменение
  объявляется в вежливом живом регионе. `sortable: false` выключает колонку.
- Фильтры из шапки (коммит 6): у фильтруемой колонки в заголовке есть кнопка-воронка с
  `aria-haspopup="dialog"` и `aria-expanded`; она видна при наведении и фокусе, на устройствах без
  hover, пока фильтр открыт и пока он активен (цвет акцента). С меню колонки (коммит 8a) воронка
  стоит в заголовке, только пока фильтр активен или открыт, как в MUI: узкие колонки иначе отдавали
  кнопкам почти всю ширину, и клик по заголовку попадал в них вместо сортировки. Кнопка и пункт
  «Фильтр…» меню колонки (без меню — Alt+ArrowDown на заголовке) открывают поповер `role="dialog"` в верхнем слое: `usePopover` в режиме auto и `useFloating`
  снизу от заголовка с выравниванием по началу строки (в RTL — по правому краю) и сдвигом внутрь
  экрана. Поверхность и анимация — класс `nui-popover` кита в BEM-миксе с `nui-grid-filter`
  (`NuiPopover` берёт якорь только из своего слота-триггера, а якорь фильтра — ячейка шапки), поэтому
  гриду нужны стили поповера из `@numior/vue`, как и стили кнопок и флажков формы фильтра. Вид формы берётся из `column.filter` или типа колонки, `false` выключает фильтр: text —
  условие и значение, number — от и до, date — с даты по дату (целые дни в UTC), set — флажки
  значений из `distinct` (первые 100, подписи через `format` колонки, пустые — одной меткой).
  «Применить» и Enter пишут условие в `v-model:filters`, «Сбросить» удаляет его, Escape
  закрывает без изменений; фокус возвращается в заголовок, новое число строк объявляется в живом
  регионе. `v-model:quick` — текст быстрого фильтра. Обе модели — данные без функций: они
  сериализуются в JSON и применяются при монтировании, в том числе на сервере. Содержимое
  поповера остаётся смонтированным до выбора другой колонки, потому что Chromium теряет фокус при
  удалении фокусированного узла из верхнего слоя.
- Группы в интерфейсе (коммит 7a): `v-model:groupBy` — ключи колонок по уровням; непустой список
  меняет роль на `treegrid`, строки получают `aria-level`, строки групп — `aria-expanded`. Строка
  группы — обычная строка с тремя панелями: в ячейке сгруппированной колонки шеврон, значение
  (через `format` колонки без строки, пустое — «(пусто)») и число строк, в колонках с `aggregate`
  — агрегат группы (`count` — простым числом, остальные — форматом колонки), прочие ячейки пусты.
  Строка на всю ширину отвергнута: она спорила бы с закреплёнными панелями, а подпись в своей
  колонке остаётся видимой, если колонку закрепить. `v-model:expanded` — id развёрнутых групп
  (JSON пути значений), по умолчанию все свёрнуты, как в `NuiTree`; движок создаётся с
  `defaultExpanded: false`, модель передаётся ему целиком через `setToggled`. Enter или Space на
  любой ячейке строки группы и клик по шеврону или подписи меняют развёрнутость, изменение
  объявляется в живом регионе. Модели строк групп кешируются до смены ревизии, колонок или
  локали, поэтому мемоизация строк сохраняется. Ячейки строк групп — контейнеры по ширине: если
  содержимое ячейки уже 8rem, счётчик скрывается визуально (скринридер его читает), и место
  остаётся подписи. `groupFooter` из плана не делается: агрегаты уже
  стоят в строке группы, отдельная строка-подвал группы повторяла бы их.
- Корень грида обрезается `clip-path: inset(0 round …)`, а не `overflow: hidden` со скруглением:
  Chromium при дробном масштабе (125 %, 150 %, 2,625 у Pixel 7) пропускал прокручиваемые строки
  сквозь скругленную обрезку, и под липким подвалом проступали верхушки букв. Подвал стоит на
  пиксель ниже края области прокрутки с подложкой своего цвета: шов снапа липкого слоя при том же
  масштабе иначе оставлял полоску строк под ним.
- Группы заголовков (коммит 7b): колонка-группа `{ key, label, children }` в `columns` (вложенность
  любая) рисует полосы над заголовками — по строке на уровень, сверху вниз. Полоса — ячейка
  `columnheader` с `aria-colindex` первой колонки и `aria-colspan` числа колонок; группа, чьи
  колонки попали в разные панели, делится на сегменты по панелям. Полосы рисуются целиком без окна
  колонок (их единицы), не входят в roving-навигацию и не сортируют. Число строк шапки сдвигает
  `aria-rowindex` строк данных и подвала, окно строк вычитает высоту всех строк шапки, а полоса
  занятости и пустое состояние отсчитываются от неё. Тексты ячеек получают `unicode-bidi:
  plaintext`: направление определяется содержимым, поэтому русская дата в RTL-сетке не
  переставляет знаки.
- Строки дерева (коммит 7c): `getChildren` включает данные-дерево (движок разворачивает их в
  плоскую таблицу, `groupBy` при этом не передаётся), `treeColumn` — колонка с отступом по уровню
  и шевроном (по умолчанию первая). Строка с `hasChildren` и без загруженных детей раскрывается:
  грид отдаёт событие `load(row)`, ставит на строку `aria-busy` и крутит спиннер вместо шеврона,
  пока потребитель не обновит источник; любое обновление источника завершает ожидание. Развёрнутые
  строки хранятся в той же модели `expanded` по ключам `getKey`, Enter или Space раскрывают строку
  только в колонке дерева (в остальных ячейках Enter достанется редактированию), изменение
  объявляется «строка развёрнута/свёрнута». После смены источника движок получает модель
  развёрнутости заново: `setRows` сбрасывает её, и без этого раскрытые группы и строки визуально
  схлопывались при каждом обновлении данных. Строки тела собираются одним вычисляемым списком
  (позиция, смещение, ключ, уровень, группа, раскрываемость, загрузка), чтобы шаблон не вызывал
  движок несколько раз на строку. Шапка, тело, подвал и строки тянутся минимум на ширину области
  прокрутки, а горизонтальный разделитель рисует строка, а не ячейки: сетка уже контейнера больше
  не обрывает фон и линии посреди строки.
- Меню колонки (коммит 8a): рядом с воронкой в заголовке — кнопка «⋯» с `aria-haspopup="menu"`,
  `aria-expanded` и именем «Меню колонки «X»»; видимость как у воронки, у колонок `align: 'end'`
  обе кнопки стоят перед подписью. Меню одно на грид: `NuiMenu` с `anchor` на ячейке шапки и
  `show(focus)`, пункты собирает чистая функция по состоянию колонки. Alt+ArrowDown на заголовке
  открывает меню на первом пункте, а при `columnMenu: false` (кнопки нет) — фильтр. Разделы:
  сортировка (по возрастанию, по убыванию, снять; текущее состояние отключено), «Фильтр…»,
  группировка и её снятие (не для дерева), закрепление радиогруппой «В начале / Не закреплять / В
  конце», «Скрыть колонку» и подменю «Колонки» с флажками всех листовых колонок. Проп
  `columnMenu` принимает и функцию `({ column, anchor }) → пункты` (2026-10-16): её пункты идут
  первыми и отделены чертой, `anchor` — ячейка шапки для своих всплывающих окон; так блок
  таблицы редактора добавляет переименование, тип и вставку колонок, не трогая разделы таблицы.
  `v-model:pins` — запись «ключ → `start` | `end` | `null`», она побеждает `pin` колонки, `null`
  открепляет закреплённую по умолчанию, отсутствующий ключ оставляет `pin`; `v-model:hidden` —
  ключи скрытых колонок; обе модели сериализуемы. Если закреплённые панели не оставляют
  прокручиваемой области места хотя бы на самую узкую колонку (48px), раскладка рисует все колонки
  в прокручиваемой области в том же визуальном порядке: на телефоне закреплённая из меню колонка
  иначе закрывала бы остальные. Решение принимает `pinsFit` по измеренной ширине области
  прокрутки и отдаёт булево значение, поэтому ресайз не пересобирает раскладку и не перерисовывает
  строки; до измерения (и на сервере) панели закреплены, модель `pins` не меняется, и закрепление
  возвращается, когда места становится достаточно. `hideable: false` и последняя видимая колонка
  не скрываются (флажок заблокирован). Скрытая колонка выпадает из раскладки, навигации,
  `aria-colcount` и быстрого фильтра, но её фильтры и сортировка действуют: фильтр `quick`
  движка принимает `keys`, а список без текстовых колонок ничего не находит, потому что поиск по
  невидимым значениям выглядел бы как ошибка. Фокус: смена раскладки синхронно (`flush: 'sync'`)
  переносит активную ячейку на ту же колонку по ключу, а если колонка исчезла — на вставшую на её
  место; действие меню запрашивает фокус заголовка отложенно, и он ставится в pre-flush, когда
  раскладка уже учла модель, в том числе контролируемую, которую родитель обновит своим рендером
  (немедленный фокус брал бы индекс и прокрутку из старой раскладки). Флажки «Колонок» оставляют
  меню открытым и фокус в нём, скрытие колонки самого меню закрывает его и ставит фокус на место
  колонки. Изменения объявляются в живом регионе. Область прокрутки получает `scroll-padding` по
  высоте шапки и подвала и ширинам закреплённых панелей: нативная прокрутка к элементу
  (`scrollIntoView`, фокус без `preventScroll`, поиск по странице) больше не прячет ячейку под
  ними.

- Ячейки в потоке (объединение с `NuiTable`, 2026-09-29): панель — flex-контейнер, ячейки —

- Выбор строк (объединение, коммит 4): `selectable: 'single' | 'multiple'` добавляет служебную
  колонку флажков в панель `start` первой (`kind: 'select'`, 40px, ключ `__select`); служебные
  колонки входят в `aria-colcount` и `aria-colindex`, а ключи данных везде идут через
  `dataKeysOf`/`dataKeyAt`. Модель `v-model:selected` хранит значения строк; ключ выбора —
  `getKey(row)`, а без него сама строка (идентичность объекта): карта индексов на миллион строк не
  нужна. «Все» действует на строки-узлы в поле зрения после фильтров (не на группы и не на
  закреплённые строки), состояние флажка шапки считается по этой области и кешируется по ревизии.
  Пробел на любой ячейке строки-узла переключает строку, пробел или Enter на ячейке флажка шапки —
  все; обработчики идут в порядке выбор → шапка → раскрытие → фокус, поэтому пробел на строке
  дерева выбирает при `selectable` и разворачивает без него. Флажки с `tabindex="-1"`: сетка
  остаётся одним tab stop. `rowClick` — делегированный клик на теле вне флажка, подписи группы и
  переключателя дерева. `striped` красит нечётные позиции из модели строк (`:nth-child`
  бессмыслен при окне). `caption` — `<p>` над скроллером, на который ссылается `aria-labelledby`,
  когда нет `label`; `role="caption"` внутри сетки отвергнут (пришлось бы учитывать его в липких
  смещениях и окне). `loading` — `aria-busy`, строки-скелетоны отдельным циклом (не ветками в
  цикле данных: когнитивная сложность шаблона) или слот `loading` строкой на всю ширину, флажок
  «все» отключён, активная ячейка прижимается к шапке. Скроллер и полоса занятости обёрнуты в
  `nui-grid__frame`, чтобы подпись над ними не сдвигала позицию полосы. Переключатель дерева
  приходит в строку именованным слотом `tree` (без `v-if` в слоте ячейки — он оставлял
  `<!--v-if-->` в каждой ячейке).

  отдельный композитный слой из каждой видимой ячейки (213 из 230 слоёв песочницы, 444 на
  странице бенчмарка) и двигал строки только из главного потока; sticky на `<tbody>` Safari не
  держит, на `<tr>` — ненадёжно, а на `<table>` работает во всех движках. Закреплённая активная
  строка вне окна идёт первой или последней в `<tbody>` и стоит сразу за краем окна, границы
  липкости не пускают её в кадр. Ячейки тела вне закреплённых колонок — `position: relative;
  z-index: 0`: как и липкие ячейки до этого, каждая остаётся контейнером для абсолютно
  позиционированного содержимого слотов и своим контекстом наложения, но слоя не получает.
  `content-visibility: auto` на вьюпорте пробовали и убрали: Chromium выбрасывает запись
  `scrollTop` в пропущенный скроллер и возвращает прежний сдвиг, поэтому `scrollToRow()` для
  таблицы за пределами экрана терялся, а в песочнице выигрыша по слоям не было. При сжатии
  окна у конца холста таблица могла бы на миг стать короче, а Chromium в этот момент клампит
  `scrollTop` и назад не возвращает; поэтому рост `--_window-lead` и `--_window-rest` пишется
  во вьюпорт watcher'ом `useVirtualFrame` до рендера, а уменьшение — привязкой в шаблоне, и высота холста никогда не
  проседает. Строки тела теперь лежат в слое самой таблицы, а подвал — отдельными липкими
  слоями, и при дробном масштабе (Pixel 7) под подвалом снова проступала полоска строк: липкие
  ячейки подвала стоят на `inset-block-end: -1px` с `padding-block-end: 1px` (содержимое на
  2px ниже высоты строки), как подвал грида до объединения. Ключ строки окна — слот
  `useVirtualList`, а не id узла: строки патчатся, не монтируются заново; фокус ячейки при
  переезде закреплённой строки в начало `<tbody>` возвращает `useTableFocus` (pre-watcher на
  диапазон окна запоминает, что фокус был внутри viewport, post-watcher вызывает `focus`
  с `preventScroll`). Оба окна слушают скролл одним обработчиком таблицы (`listen: false` у
  `useVirtualList`, `@scroll.passive` на viewport вызывает оба `measure()`): два listener'а
  на одном событии давали рендер между ними и принудительный layout во втором (в prod ~5ms
  на сдвиг). Закрепление — `position: sticky` на самих ячейках:
  колонки через `--_pin` (отступ внутри панели, для правой панели считается от её конца),
  шапка, полосы и закреплённые строки через `--_top` на `<tr>` (`calc(var(--_row) * (aria-
  rowindex − 1))`), итоги через `inset-block-end: 0`; фон ячеек `background: inherit` от
  строки, чтобы липкие ячейки закрывали прокрученные. Ячейка — `th`/`td` с классом
  `nui-table__cell`, ролью, `aria-colindex`, roving `tabindex` и обёрткой
  `.nui-table__content` (flex-выравнивание, высота `calc(var(--_row) - 1px)` в окне и
  `min-block-size` без `height`, контейнер для запросов у групп и итогов). Полосы
  заголовков строятся из отрисованных ячеек строки: подряд идущие ячейки одной группы и
  одной панели сливаются в `th[colspan]` (`aria-colspan` — число колонок в куске),
  остальные — пустые `th[role=presentation]` со своими sticky-классами. Пустое состояние —
  `<tbody>` с одной ячейкой на все дорожки и липким телом шириной `--_room` (ширина
  скроллера), чтобы текст стоял по центру видимой области. `wrap` действует только без
  `height`: в окне высота строки фиксирована, а ячейка таблицы растёт от содержимого.
  Ушли: панели `nui-table__pane--*`, абсолютные строки, `--_centre`; драйвер читает
  панель по классу `--pin-start|end` и пропуски `gapBefore`/`tailGap` вместо `transform`.

  (снимается весь отрезок от последней нажатой ячейки) отвергнуты: оба теряли строки в сценариях
  ревью. Любой клик делает нажатую ячейку активной, кроме правого клика внутри выделения, который
  её не переносит. Соседние прямоугольники, которые складываются в один, склеиваются
  (`tidyRanges`), поэтому модель не дробится. Без диапазонов активная ячейка в фокусе выглядит
  выделением из одной ячейки: её же копирует Ctrl+C, и от неё начнётся Shift+клик (ревью
  2026-09-30: «с шифтом кликаю на 3 2 4 и потом на 5 — выделены только 4 и 5»). Если снятие
  выделения оставило модель пустой, активная ячейка не выглядит выделенной до обычного клика или
  навигации, а кольцо фокуса на ячейках тела не рисуется, пока есть выделение;
  после протяжки и кликов с модификаторами `rowClick` не приходит; на таче протяжки нет.
  Попадание считается по прямоугольникам ячеек (строка — по первой ячейке, потому что ячейки
  окна липкие), закреплённые колонки проверяются первыми, точка зажимается в полосу тела между
  шапкой с закреплёнными строками и подвалом. Клавиатура: Shift со стрелками, Home, End,
  PageUp и PageDown двигают свободный угол последнего диапазона, с Ctrl — до края;
  Shift+Space, Ctrl+Space и Ctrl+A (по `code`, чтобы работала кириллическая раскладка;
  Ctrl+A работает с любой ячейки, включая шапку), Escape снимает, навигация без Shift снимает
  и двигает фокус. Escape гасит и подсветку активной ячейки (класс корня `nui-table--deselected`,
  тот же, что после снятия последней ячейки Ctrl+кликом), фокусная рамка клавиатуры остаётся;
  второй Escape уходит дальше, например закрывает диалог. Нажатие вне таблицы (`pointerdown` на
  документе, пока есть диапазоны) очищает их; элементы из `keepEditing` выделение не снимают,
  меню и фильтры таблицы лежат внутри её корня (ревью 2026-10-03: «ни esc ни клик вне таблицы не
  снимают»). Якорь считается, только пока фокус внутри таблицы; Shift+клик всегда гасит
  mousedown, чтобы браузер не растягивал выделение текста по соседним ячейкам, а без якоря
  диапазон начинается с нажатой ячейки и фокус переходит в неё (ревью 2026-09-30: «при shift +
  клик выделяется текст соседних ячеек», «ctrl+a и ctrl+c не пашет»). Сброс — при сортировке,
  фильтрах, быстром фильтре, группах, раскрытии, смене страницы, `rows`, набора и порядка
  колонок. Модель, которой управляет родитель, отстаёт до его рендера, поэтому композабл
  держит последнее записанное значение до конца микрозадач. `segmentsOf(row)` мемоизирован по
  ревизии диапазонов, `NuiTableRow` получает сегменты `ranged` только для пересечённых строк

  переменным, RTL через `:dir(rtl)`). Края идут по контуру объединения: край есть там, где
  соседняя ячейка не выделена, поэтому вырезы и соседние прямоугольники не дают внутренних
  линий, а вырезанная ячейка обведена. Заливка — `color-mix` фона строки с primary. Активная
  ячейка залита вместе с диапазоном, а выделенная ячейка не рисует кольцо фокуса даже при
  `:focus-visible`: незалитая ячейка Excel читалась как дыра, кольцо — как отдельно выделенная
  ячейка, а Chromium и WebKit включают `:focus-visible` уже от клавиши Shift при Shift+клике

  нажал»). Где фокус, показывает само выделение; без диапазонов кольцо обычное. Ячейки внутри несут `aria-selected="true"`, сетка —
  `aria-multiselectable`, размер выделения объявляется.

- Правка в ячейке (коммит 13 блока B, часть 1, 2026-09-30): Enter, F2, двойной щелчок и двойное

  `NuiTableCellEditor` держит `provideDraftCommits`, поэтому черновик числового поля фиксируется

  значение (в том числе дата как число и как `Date`) не создаёт правку. Сброс по сортировке,
  фильтрам, группам, странице, `rows`, `columns` и набору колонок закрывает редактор и возвращает

- Серверный источник (коммит 14 блока B, часть 1, 2026-09-30): свойство `source: TableSource<T>`
  (`fetch({ offset, limit, sort, filters, signal })` → `{ rows, total }` или `{ rows, hasMore }`,
  необязательные `values` для фильтра-списка и `totals` для строки итогов) включает второй движок
  `createSourceEngine` с тем же интерфейсом `TableEngine`, поэтому второго пути рендера нет.
  Интерфейс движка получил методы окна данных `pendingAt`, `ensure(from, to)`, `refresh`,
  `settled` и `collect(signal)`; у локального движка это пустые операции и выдача видимых строк.
  Строки хранятся блоками по `blockSize` (100, при пагинации — размер страницы) в кеше LRU на 50
  блоков. Смежные недостающие блоки окна идут одним запросом, одновременно не больше двух
  запросов, а после каждого ответа движок добирает текущее окно, поэтому при быстрой прокрутке
  промежуточные блоки не запрашиваются. Смена сортировки, фильтров или быстрого поиска поднимает
  версию, отменяет запросы общим `AbortController`, чистит кеш и держит прежнее число строк под
  скелетонами; опоздавшие ответы отбрасываются по версии. До первого ответа таблица в состоянии
  загрузки, дальше незагруженные строки рисуются скелетонами в ячейках под `aria-busy`. Без общего
  числа `hasMore` растит размер на блок, короткий блок фиксирует конец. Движок ходит в сеть только
  после первого `ensure` смонтированной таблицы, поэтому SSR рисует скелетоны без запросов.
  Итоги (`totals`) запрашиваются, когда таблица просит их для новых фильтров или вызван `refresh()`,
  но не раньше первого `ensure`. У них свой `AbortController`, а ответ принимается, пока фильтры те
  же: смена сортировки не выбрасывает итоги. Ответ приходит тем же `onChange`, и таблица
  перечитывает строку итогов.
  Изменения движка приходят в таблицу счётчиком и pre-flush watcher'ом, объявленным после
  `sync()`: синхронный `onChange` во время setup иначе попадал бы во временную мёртвую зону. Без
  `height` и `pagination` таблица с источником листает страницами, потому что нарисовать все строки
  сервера нельзя. Ошибка запроса — событие `error` и объявление, блок остаётся скелетоном до
  следующего окна или `refresh()`. Экспорт CSV берёт строки через `collect`: у источника это весь
  результат запроса порциями по 1000 строк. Правки идут по загруженным строкам (история не ищет их
  по `getKey`), выбор «все» отмечает загруженные строки, копирование пропускает незагруженные.
  Дерево и перетаскивание строк с источником выключены, ручной режим `remote` остаётся для
  потребителя, который загружает страницы сам.
- Группы с сервера (коммит 14 блока B, часть 2, 2026-10-02): `fetch` получает ключи `groupBy` и
  путь раскрытой группы `groupPath`. Пока путь короче списка ключей, источник отвечает уровнем
  групп `{ groups: [{ value, count, aggregates }] }`, на последнем уровне — строками группы;
  ответ не того вида — ошибка в событии `error`. Движок источника стал деревом постраничных
  хранилищ (`source-tree.ts`): корень и по хранилищу на раскрытую группу, у каждого свои `total`,
  `hasMore` и блоки в общем LRU-кеше (ключ — номер блока и id хранилища; строки и группы лежат
  в двух кешах). Плоская позиция переводится в «хранилище + индекс» по раскладке: размер
  хранилища — число его записей плюс размеры раскрытых веток; раскладки кешируются до
  следующего изменения. Группа раскрывается сразу на `count` строк под скелетонами, если ниже
  лежат строки, и на одну строку-заглушку, если ниже ещё уровень групп. Группы свёрнуты, пока
  их id (`JSON.stringify(path)`, как у локального движка) не попал в `v-model:expanded`;
  раскрытые группы открываются заново после смены сортировки и фильтров, когда приходит их
  уровень. Свёрнутая группа держит свои блоки в кеше и раскрывается без запроса. Смена
  `groupBy` сбрасывает и число строк корня, остальные смены запроса держат его под скелетонами.
  Число строк в итогах — сумма `count` загруженных групп корня. Меню колонки снова предлагает
  группировку при источнике; экспорт CSV по-прежнему выгружает строки без групп. Отклонения от
  плана: агрегаты групп приходят в самих группах, а не отдельным `aggregate`.
- Дерево с сервера (коммит 14 блока B, часть 2, 2026-10-02): `source.children({ row, sort,
  filters, signal })` возвращает детей строки и включает режим дерева вместо `getChildren`;
  строки с детьми отмечает прежнее свойство `hasChildren`. Раскрытая строка получает своё
  хранилище в том же дереве хранилищ движка: дети приходят одним ответом без страниц, режутся
  на блоки общего кеша и запрашиваются заново целиком, если блок вытеснен. Пока ответа нет, под
  строкой стоит одна строка-скелетон, а сама строка занята (`TableRowNode.loading` → `aria-busy`
  и спиннер в переключателе), событие `load` при источнике не приходит. Раскрытые строки лежат в
  `v-model:expanded` по `getKey`; без него id — индекс в корне или путь из индексов, поэтому
  дереву с источником нужен `getKey`. После смены сортировки и фильтров дети раскрытых строк
  запрашиваются заново с новым запросом. Группировка в дереве выключена, как у локального
  движка; экспорт CSV у дерева выгружает строки верхнего уровня, потому что обход всех веток
  означал бы запрос на каждую раскрываемую строку. Перетаскивание строк с источником остаётся
  выключенным.
- Детали строк (коммит 15 блока B, часть 1, 2026-10-02): слот `detail` включает детали, а
  `hasDetail(row)` оставляет переключатель только нужным строкам. Деталь — отдельная позиция
  плоского списка сразу за строкой (узел `kind: 'detail'` с id и строкой хозяина, уровень на один
  глубже), а не часть строки-хозяина: у неё свой `aria-rowindex`, а выделение диапазонов,
  копирование, вставка, правка, выбор и перетаскивание пропускают её тем же кодом, что строки
  групп. Раскрытые детали лежат в общем `v-model:expanded`; в дереве строк детали выключены,
  потому что ключи раскрытия и переключатель там заняты детьми. Локальный движок вставляет ссылки
  на детали в плоский список видимых строк, движок источника заводит ветку `holds: 'detail'` из
  одной позиции без запросов; `TableEngine.details()` отдаёт позиции деталей по возрастанию.
  Страницы считают слоты без деталей (`pageWindowOf(count, page, pageSize, details)`): страница
  держит те же строки, сколько бы деталей ни было открыто, а счётчик пагинации показывает строки.
  Полосы тоже считаются без деталей.
  Разметка — отдельный `NuiTableDetailRow`: `tr` с одной ячейкой `role="gridcell"` на
  `aria-colspan` всех колонок и липким блоком шириной видимой области внутри, поэтому деталь не
  уезжает при горизонтальной прокрутке. Таблица с деталями — `treegrid`: строка несёт
  `aria-expanded`, деталь — `aria-level` на единицу больше. Переключатель — тот же
  `NuiTableTreeToggle` в колонке `treeColumn` без отступа уровня; в колонке с выравниванием по
  концу он стоит у начала ячейки. Деталь — ячейка сетки: стрелки проходят через неё и помнят
  колонку курсора, фокус внутри содержимого переносит курсор на деталь, Tab уводит фокус внутрь.
  Нажатие на переключатель дерева или детали не переносит фокус (`mousedown` гасится): иначе
  ячейка с шевроном получала фокус и вид выделения из одной ячейки, и раскрытие читалось как выбор.
  Курсор остаётся там, где был; с клавиатуры строку раскрывают Enter и пробел на её ячейке.
  События из содержимого детали таблица не обрабатывает: клавиши, указатель, меню, вставка, щелчки
  и долгое нажатие проходят через проверку `ownDetailOf` (ближайший `.nui-table__detail`, лежащий
  в области прокрутки этой таблицы), поэтому вложенная таблица живёт сама и на любой глубине.
  Запросы DOM идут только по своей сетке (`table-dom.ts`, селекторы от `:scope`), а правила CSS,
  зависящие от режима корня, читают приватные свойства корня (`--_content-size`,
  `--_cell-position`, `--_foot-overlap`, `--_empty-min`) или идут цепочкой дочерних селекторов:
  потомковые селекторы от корня протекали во вложенную таблицу и снимали липкость её шапки.
  Высота в окне строк: пока деталей нет, модель размеров фиксированная; с деталями — `SizeIndex`
  из числа позиций, высоты строки и известных высот деталей (кеш по id, оценка — последняя
  измеренная высота или четыре строки). `NuiTableDetailRow` слушает `ResizeObserver` своей ячейки
  и шлёт `measure`, таблица вызывает `useVirtualList().resize`, который правит индекс и держит
  первую видимую строку на месте. Детали рендерятся с ключом по id, а не по слоту окна: состояние
  содержимого не переезжает между строками, а новая деталь — новый элемент, и `ResizeObserver`
  сообщает её высоту сразу. Ограничения: высота детали вне окна остаётся оценкой до первого
  рендера, содержимое детали размонтируется при уходе из окна, а раскрытие не анимируется, как и
  у строк дерева.
- Строки окна по содержимому (коммит 15 блока B, часть 2, 2026-10-02): `rowHeight="auto"` вместе
  с `height` оставляет окно строк, но высоту строки берёт из содержимого; без `height` значение
  ничего не меняет. Корень получает класс `nui-table--fluid`, который снимает фиксированную
  высоту только с ячеек тела: шапка, закреплённые строки и подвал остаются в одну строку, потому
  что от их высоты считаются липкие отступы. Раскладка включает перенос для колонок с `wrap`, и
  эти колонки рисуются при любом положении окна колонок: иначе высота строки менялась бы при
  горизонтальной прокрутке. Их номера считаются один раз на раскладку (`wrappedCentreOf`) и
  сливаются с окном колонок за один проход (`mergeIndices`). Режим строк — одно значение
  `flow | fixed | fluid` (`TableRowMode`), а не пара флагов: от него зависят и модель размеров,
  и набор измеряемых строк. Модель размеров — `SizeIndex` с высотой строки как
  оценкой и нижней границей; она пересобирается, когда строки переставлены (запрос, раскрытие,
  смена `rows`) или изменилось их число, но не при догрузке блока источника и не при правке ячейки.
  После пересборки вид держит pre-flush привязка `useVirtualList` по номеру строки.
  Измеряет одна на таблицу `ResizeObserver` в `use-table-row-sizes.ts`: после каждого рендера строк
  она заново наблюдает первые ячейки строк тела (в обычном режиме — только ячейки деталей), и
  браузер отдаёт все высоты одним колбэком в том же кадре, а таблица передаёт их одним
  `resize`. Отдельный наблюдатель на строку дал бы рендер таблицы на каждую строку: микрозадачи
  выполняются между колбэками разных наблюдателей. Повторное наблюдение нужно из-за переиспользования
  элементов по слотам окна: строка с другими данными, но той же высоты, иначе не сообщила бы
  размер. Наблюдаются ячейки, а не `tr`. Измерение деталей переехало туда же, поэтому
  `NuiTableDetailRow` снова только разметка. PageUp и PageDown считают шаг по смещениям строк
  (`pageStepOf`), пока модель размеров индексная: рядом с высокой строкой или деталью курсор
  уходит на последнюю строку, которая помещается в окно, а не на число строк базовой высоты.
  Ограничения: высота прокрутки уточняется по мере измерения, а после перестановки строк она
  возвращается к оценке, и ползунок сдвигается.
- Требования листа (коммиты 16–17 блока B, 2026-10-02): отдельного режима ячеек с `CellSource`
  в таблице нет. Каждое требование листа становится обычной возможностью `NuiTable` (оформление
  ячеек, заголовки строк, объединения, закреплённые строки, слой поверх ячеек, внешний редактор
  и буфер), а лист подключается адаптером поверх них. Второй путь рендера удвоил бы фокус,
  выделение, окна и правку, а правило «одна реализация строки» это запрещает.
- Оформление ячеек (коммит 16, часть 1, 2026-10-02): `cellStyle({ row, column, position, pinned })`
  возвращает `fill`, `color`, `align`, `borders`, `class` и `style` для ячеек тела и закреплённых
  строк, а `bordered` включает линии между колонками. Таблица отдаёт раскраску строке целиком
  (`TableRowPainter`), строка держит её в `computed`: функция вызывается один раз на показанную
  ячейку и повторно только при смене позиции, ревизии строки, набора колонок окна или
  реактивного состояния, которое она читает. Набор колонок окна теперь устойчив по идентичности
  (`sameIndices`): раньше движение курсора пересоздавало `rowCells` для всех строк.
  Заливка — слой `background-image` поверх унаследованного фона строки. Полупрозрачная заливка
  поэтому не просвечивает содержимое под закреплённой колонкой и сохраняет полосы, наведение и
  выбор строки, а оттенок выделения ложится вторым слоем поверх неё.
  Линии ячейки рисует её псевдоэлемент `::before` (класс `--edged`), а не рамка `td`: рамка
  увеличила бы высоту строки окна. Псевдоэлемент накрывает обе собственные линии сетки ячейки и
  заходит на одну линию вверх и в начало, на линии соседей, поэтому все четыре границы заменяют
  сетку, а не встают рядом с ней (ревью 2026-10-03: «причина жирных бордеров» — `top` раньше шёл
  внутри ячейки под линией строки выше, и линия итогов выглядела двойной). У объединённой ячейки
  `top` и `start` остаются внутри: её обрезает `clip-path`.
  Линия сетки — концевая рамка ячейки шириной `--_grid-x`. Её нет у последней ячейки строки и у
  ячеек-пропусков, а у последней прокручиваемой колонки (`tail` в раскладке) она появляется,
  только когда колонки уже области прокрутки (класс корня `nui-table--slack`): иначе линия
  удваивала бы рамку таблицы или линию закреплённой панели. Концевая линия полосы шапки подчиняется
  тому же правилу. Раскраска не анимируется: строки окна переиспользуются по слотам, и переход
  цвета срабатывал бы при прокрутке.
- Заголовки строк (коммит 16, часть 2, 2026-10-02): `rowHeaders` добавляет служебную колонку вида
  `rowhead` первой в начальной панели, перед флажками. Её ячейки — `th scope="row"` с ролью
  `rowheader`, а угол шапки несёт скрытую подпись из словаря. Подпись по умолчанию — порядковый
  номер строки среди показанных: детали не считаются, страницы продолжают счёт. Опции
  `{ label, width }` задают свою подпись и ширину, а ширина по умолчанию берётся из числа знаков
  общего числа строк.
  Заголовки выделяют линии. Сессия диапазонов получила вид `cells | rows | cols`
  (`TableRangeLines`), и каждый её шаг расширяет прямоугольник до целых строк или колонок
  (`widenRange`). Колонку выделяет только заголовок несортируемой колонки и только при
  `rowHeaders`: у обычной таблицы щелчок по заголовку остаётся сортировкой. Угол выделяет всё.
  На таче заголовок срабатывает по `click`, чтобы прокрутка пальцем ничего не выделяла.
  Активной становится ячейка линии в текущей колонке или строке курсора, без прокрутки.
  Автопрокрутка у края при протяжке по заголовкам идёт только вдоль оси протяжки. Shift со
  стрелками у диапазона из целых строк раскрывает только строку, а у целых колонок — только
  колонку (`revealAxisOf`): дальний угол такого диапазона больше не уводит вид на другой конец.
  Заголовок строки подсвечен, когда в строке есть выделение. Заголовки колонок подсвечены по
  слитым интервалам колонок из диапазонов (`columnSpansOf`); они считаются только при
  `rowHeaders`, чтобы обычные таблицы не менялись.
  Попутно рамка стала обрезать содержимое по внешнему краю корня: `clip-path: inset(-1px round
  радиус)` вместо `inset(0 round радиус - 1px)`. Когда таблица стоит на половине физического
  пикселя, Chromium сглаживает край скруглённой обрезки у слоёв, задевающих угол, и первая строка
  пикселей угловой ячейки шапки показывала слой под ней: подсвеченный заголовок колонки проступал
  синей полосой. Теперь край обрезки лежит под линией рамки, которую рисует непрозрачный
  `::after` корня, а первую строку пикселей содержимого режет только прямоугольная обрезка
  области прокрутки. Нижняя накладка липкого подвала в один пиксель остаётся.
  Шапка начинается на два пикселя выше области прокрутки (2026-10-02): у таблицы отрицательный
  верхний отступ, а ячейки первой строки шапки прилипают на эти два пикселя выше и получают
  такой же внутренний отступ. При дробном отношении пикселей Chromium ставит слой липкой ячейки
  на целый физический пиксель и мог опустить его на строку ниже обрезки: в щели проступали
  прокрученные ячейки, а под закреплённой шапкой — обычные заголовки. На масштабе 125 % так
  было при пяти дробных положениях из семи. Проверка прежнего сценария сдвигала таблицу внешним
  отступом, который схлопывался с отступом соседа и ничего не двигал; теперь таблицу сдвигает
  относительное смещение, а слои красятся контрастными цветами на четырёх дробях и на
  отношениях 1,25 и 1,5.
  Остаток (2026-10-03): ряд физических пикселей у дробного верхнего края области прокрутки
  липкие слои не закрывают — композитор обрезает их по целому пикселю, а остальное содержимое по
  дробному краю. При отношении 1,5 в Chromium на нечётных смещениях прокрутки в этот ряд попадает
  прокручиваемая строка: на настоящих цветах разница не больше 8 уровней из 255. В Firefox при
  1,25 там же виден обычный заголовок вместо закреплённого, а фон у них один. Правки поэтому
  нет. Проверка ставит таблицу на названную дробь заново перед каждым замером (раньше сдвиг
  накапливался, и после первой дроби проверялись другие положения) и ищет в шапке только
  пиксели тела.
- Высоты строк (коммит 16, часть 3, 2026-10-02): `v-model:rowHeights` хранит высоты по ключу
  строки, а `rowHeaders.resizable` показывает ручку у нижнего края заголовка строки — тот же
  `NuiTableResizer` с осью `y`. Двойной щелчок по ручке сбрасывает высоту, `Alt` со стрелками
  меняет её на 8 px, минимум — 20 px. Строка получает высоту инлайновыми приватными свойствами
  (`--_row` и размер содержимого ячеек): производные свойства корня уже разрешены на корне, и
  одним `--_row` на строке их не переопределить.
  В обычном окне строк высоты точные. `use-table-row-sizes` находит позиции строк модели одним
  проходом движка (`positionsOf` останавливается, когда найдены все ключи) и кладёт их в индекс
  размеров. Проход повторяется только при смене набора ключей или перестановке строк, а смена
  значения обновляет индекс точечно через `resize`: иначе каждое движение ручки пересобирало бы
  индекс на миллионе строк. Синхронный наблюдатель держит нереактивное зеркало высот, чтобы
  сборка индекса не зависела от значений.
  Когда строки растут по содержимому (без `height` или с `rowHeight="auto"`), высота из модели —
  минимум. С `source` высоты не действуют: позиции незагруженных строк неизвестны.
- Объединённые ячейки (коммит 16, часть 4, 2026-10-02): `merges` — список прямоугольников в
  координатах диапазонов. Список, а не функция по ячейке: расширять выделение до объединений
  по функции пришлось бы перебором периметра, а у целой колонки он в миллион ячеек. Индекс
  (`createMergeIndex`) раскладывает прямоугольники по блокам из 32 строк, отбрасывает одиночные
  ячейки и второй из двух пересекающихся.
  Рендер — нативные `rowspan` и `colspan`, но не одной ячейкой на объединение, а кусками
  (`mergeSpans`): кусок на каждую непрерывную серию показанных строк (окно, удержанная активная
  строка) и на каждую панель колонок. Пропуск окна колонок внутри объединения входит в кусок.
  Каждый кусок рисует содержимое первой ячейки объединения в блоке полного размера со сдвигом
  на своё место, поэтому текст не прыгает при движении окна и продолжается через границу
  закреплённой панели. Содержимое абсолютное и высоту строк не задаёт; ячейка режет его
  `clip-path` по своей рамке, чтобы линии из `cellStyle` остались видны. Редактор живёт в первом
  куске.
  Курсор хранит свою логическую позицию внутри объединения, а фокус получает кусок, который её
  накрывает (`activeLead`): стрелка выходит с дальнего края объединения по той же строке или
  колонке, с которой пришла. Щелчок ставит курсор на первую ячейку того куска, по которому
  пришёлся: фокус остаётся под указателем, а стрелка из высокого объединения в окне не уводит
  прокрутку к его началу. Остальные куски активного объединения получают класс `--allied` и
  ту же подсветку через `:has()` по сфокусированной ячейке тела; кольцо собрано из четырёх теней,
  и классы `--cut-*` гасят его стороны на разрезах, как края диапазона.
  Кусок наследует роль закрытых колонок: край закреплённой панели (`--edge`) и замыкающую линию
  последней колонки (`--tail`). Объединение из нескольких строк (`--tall`) не принадлежит одной
  строке, поэтому держит фон поверхности и не подсвечивает первую строку при наведении. Для
  вспомогательных технологий каждый кусок — отдельная ячейка сетки со своими `rowspan` и
  `aria-colspan` в логических колонках; пропуски окна колонок в счёт не идут.
  Выделение растёт до неподвижной точки (`expandToMerges`), а Shift со стрелкой шагает через
  объединение целиком.
  Строки и колонки, выделенные целиком, не растут: иначе объединённая строка заголовка превращала
  бы выделение колонки в выделение всего. Правка, копирование активной ячейки и контекстное меню
  берут первую ячейку объединения. При группировке, в дереве и с деталями объединения выключены.
  Вместе с объединениями стиль ячейки получил `wrap`: он ставит тот же класс `--wrap`, что и
  `wrap` колонки, потому что класс на `td` не может отменить `nowrap` вложенного содержимого.
- Перетекание текста (коммит 16, часть 5, 2026-10-02): `overflow` в стиле ячейки продолжает
  текст поверх пустых соседей без объединения. Ячейки остаются отдельными: шире становится
  только блок текста исходной ячейки, он не ловит указатель, а сама ячейка поднимается на слой

  перетеканию в липких строках.
  Соседей считает раскраска строки (`floodRow`): свободна ячейка с пустым текстом без своего
  слота, не входящая в объединение и не открытая в редакторе. Занятые ячейки помечаются, чтобы
  два текста не легли друг на друга; линии сетки под текстом гасит класс `--seamless`.
  Соседей занимается ровно столько, сколько нужно тексту (2026-10-18, после того как короткие
  подписи гасили сетку до конца строки): `needAt` строки — ширина текста по `measureText` на
  `OffscreenCanvas` шрифтом ячейки данных плюс два отступа её содержимого; текст, который
  помещается в свою ячейку, не перетекает вовсе. Шрифт и отступ берутся с первой ячейки данных тела

  тике и перерисовывает таблицу, только когда образец появился. На сервере и в jsdom
  (`OffscreenCanvas` нет) ширина неизвестна, и текст по-прежнему занимает все свободные ячейки до
  первой занятой, поэтому разметка гидратации совпадает. Жирный текст из `cellStyle` меряется
  обычным начертанием и может обрезаться многоточием на последних пикселях.
  Ограничения: текст по центру остаётся в ячейке, как и текст закреплённой колонки (панель
  липкая, текст пришлось бы резать по прокрутке) и закреплённых строк. В окне колонок текст
  виден, пока его ячейка в окне.
- Закреплённые строки тела (коммит 16, часть 6, 2026-10-03): `frozenRows` держит первые N
  позиций тела под шапкой. Это обычные строки того же `<tbody>` в том же порядке DOM: липкими
  становятся их ячейки (`position: sticky` через `--_cell-position`, смещение `--_top` = высота
  шапки с закреплёнными строками `--_head-size` плюс `offsetOf(k)` окна). Второго пути рендера
  нет, поэтому фокус, выделение, правка, высоты строк и объединения работают без своего кода.
  Окно строк узнаёт о них через `useVirtualList({ frozen })`: первые N элементов всегда в
  `items`, диапазон и `scrollTo` считаются для места под ними, а рамка липкого окна учитывает их
  высоту как отступ. Шаг PageUp/PageDown и `scroll-padding` вьюпорта уменьшаются на эту высоту.
  Объединение, пересекающее границу, режется на два куска (`consecutiveRuns(positions, edge)`),
  иначе липкая ячейка с `rowspan` утащила бы за собой прокручиваемую строку.
  Слои: ячейки закреплённых строк стоят на уровне липких строк (3), их закреплённые колонки на
  уровне 5, перетекающий текст в них на уровне 4. Нижняя линия последней закреплённой строки —
  `--nui-border-strong`.
  Нативный фокус на липкой ячейке (Tab в таблицу, `focus()` без `preventScroll`) в Chromium и
  WebKit прокручивал строки: ячейка лежит в зоне `scroll-padding`, и браузер пытался её показать.
  Пока фокус внутри строки шапки, закреплённой строки или подвала, вьюпорт обнуляет
  `scroll-padding-block` правилом с `:has()`. Ячейки первой строки шапки и подвала получают
  отрицательный `scroll-margin` на величину своего нахлёста, иначе браузер сдвигал строки на него.
  Ограничения: закрепление работает только в окне строк (`height`) и отключается при загрузке,
  группах, дереве, деталях строк и серверном источнике, потому что движок источника держит одно
  окно блоков. Строки закрепляются по позиции, поэтому сортировка и фильтр меняют их состав.
  Высота закреплённых строк не ограничена: если они выше области прокрутки, остальным строкам
  не остаётся места.
- Переход к краю (коммит 16, часть 7, 2026-10-03): Ctrl со стрелкой переводит курсор к краю

- Лист из источника ячеек (коммит 16, часть 8, 2026-10-03): `tableCells(source)` строит свойства

- Слой поверх ячеек (коммит 17, часть 1, 2026-10-03): слот `overlay` рисуется в
  `<caption class="nui-table__overlay" aria-hidden="true">` — первом ребёнке `<table>`, где
  разметка таблицы допускает произвольный блок. Слой обязан жить внутри `<table>`: в режиме окна
  строк она липкая и создаёт свой контекст наложения, и слой снаружи оказывался либо над шапкой,
  либо под всеми ячейками. Подпись абсолютная и нулевого размера, плоскость `nui-table__plane`
  внутри сдвинута на `--_head-lap` минус ведущий отступ окна (`--_plane-lead`), поэтому её начало
  совпадает с началом прокручиваемого содержимого; без окна строк `<table>` получает

  Элементы слоя прокручиваются вместе с ячейками без JS. Слой стоит на уровне 1 шкалы слоёв: над
  ячейками тела, под закреплёнными колонками и липкими строками, которые его перекрывают;
  указатель он пропускает (`pointer-events: none`, элементы включают его себе сами).

  положению в панели раскладки, `start` логический и в RTL отсчитывается справа. Высоты строк

  элементы слоя с указателем ей не мешают. Событие `window` сообщает отрисованные позиции строк и

- Внешний редактор (коммит 17, часть 2, 2026-10-03): модели `active` (активная ячейка в
  координатах `ranges`, `undefined` вне ячеек данных) и `draft` (`{ row, col, key, value }`
  открытой правки, где `value` — значение контрола, `undefined` без правки) и методы
  `startEdit('replace' | 'append', { focus })`, `commitEdit(move)`, `cancelEdit()` у ссылки на
  таблицу. Ячейка в `draft` нужна, потому что пустой контрол отдаёт `undefined` и голое значение
  не отличало бы пустую правку от её отсутствия; запись с другой ячейкой игнорируется. Черновик
  живёт в таблице и связан с моделью в обе стороны: запись родителя приходит в редактор через
  `watch`, свои изменения уходят событием, поэтому проверка и сохранение читают свежее значение
  синхронно, даже когда модель связана, а проп ещё не обновился. Эхо своих значений отсеивает
  очередь отправленных (`createEchoes`): родитель может перерисоваться со старым пропом уже после
  более нового события, и без очереди курсор возвращался на прежнюю ячейку. `focus: false` монтирует редактор пассивным: без фокуса, раскрытия
  списков и набора первого символа, и фокус остаётся в строке формул. Правку, которую ведут
  снаружи, завершает фокус, пришедший в таблицу не из редактора, с правилами ухода фокуса
  (неверное значение отбрасывается с объявлением). `keepEditing(target)` называет внешние
  элементы, переход фокуса на которые не завершает правку в ячейке; после ухода из них правку
  завершает приложение. `commitEdit` перед проверкой сбрасывает черновики полей редактора через
  обработчик, который редактор регистрирует при монтировании, поэтому ленивые поля не теряют
  последний ввод. Ctrl+Enter в редакторе — ход `fill`: значение уходит во все изменяемые ячейки
  выделения с тем же типом колонки одной командой `edit`, ячейки других типов и не прошедшие
  правила пропускаются с объявлением, курсор остаётся на месте. `columnIndex(name)` — обратная
  к `columnName` функция для адресов из событий правки листа.
- Выбор ссылок (коммит 17, часть 3, 2026-10-03): `picking(draft)` решает, ждёт ли черновик
  открытой правки ссылку; пока ответ `true`, нажатие мышью или пером на ячейке данных не завершает

- Свой формат буфера (коммит 17, часть 4, 2026-10-03): `clipboard.serialize({ ranges, headers,

  диапазонах проверяется до вызова, а `copyLimit` к нему не применяется — объём решает

- История правок приложения (коммит 17, часть 4, 2026-10-03): `commands: { push, undo, redo }`
  заменяет встроенный стек. Каждая правка по-прежнему приходит событием `edit` и вслед за ним в
  `push`, а Ctrl+Z, Ctrl+Y и методы `undo`/`redo` ссылки вызывают историю приложения; та сама
  возвращает данные и отвечает числом изменённых ячеек. Таблица после такого шага пересобирает
  хранилища движка по всем колонкам данных (какие ключи изменились, знает только приложение) и
  объявляет итог; событий `edit` с видами `undo`/`redo` при этом нет. Лист ведёт правки через
  `Workbook.apply`, поэтому его история шагов и становится историей таблицы.
- Перерисовка по диапазонам (коммит 17, часть 5, 2026-10-03): `invalidate(ranges)` у ссылки
  нужен, когда данные источника меняются без правки в таблице (пересчёт формул, ответ сервера).
  Строка окна читает свою ревизию из реактивной карты по позиции (`shallowReactive(Map)` следит за
  каждым ключом отдельно), а `invalidate` пишет в карту только строки диапазонов внутри окна.
  Сама таблица при этом не перерисовывается: заново рисуются лишь эти строки, ячейка получает
  ревизию строки свойством, и адаптер `tableCells` читает её `cellAt` заново (по одному разу на
  ячейку за рендер). Первая версия поднимала ревизию строки через вычисленный список строк, и тест
  показал перерисовку всего окна: список пересобирался, и каждая строка получала новый объект.
  Если таблица сортирует, фильтрует, группирует или считает итоги, или диапазонов нет,
  `invalidate` пересобирает хранилища движка по колонкам данных и перерисовывает всё — порядок и
  итоги могли измениться.
- Правки по отзыву пользователя (2026-10-03): `cellSelection` по умолчанию выключено — обычная

  уровня без потомков и без детали не держит место под переключатель, поэтому плоская таблица и
  строки без детали не получают пустого отступа; вложенные листья сохраняют это место и стоят
  вровень с раскрывающимися соседями.

- Прототип «на выброс» для проверки миллиона строк: отвергнут интервью — тот же код должен
  стать релизным, а бенчмарк — регрессионным тестом.
- Поразрядная сортировка чисел: быстрее слияния на одном ключе, но не даёт устойчивого
  многоключевого порядка и не режется на куски так же просто; вернёмся, если бенчмарк
  покажет, что слияние не укладывается в пороги.
- Воркер с первого коммита: усложняет передачу строк-объектов; движок написан без DOM, чтобы
  позже стать хостом воркера без переписывания.
- Canvas-рендер: решение отложено до бенчмарка DOM-грида (коммит 5 блока B).

- Границы колонок на дробном масштабе экрана (2026-10-17): Chromium округляет ширины `<col>` до
  целых CSS-пикселей, и на 125% граница колонки шириной 170 px попадала на полпикселя и
  рисовалась размытой на два тусклых пикселя, а соседняя — чёткой. `tableLayout` получает
  `scale` (`useDevicePixelRatio`, после монтирования, чтобы SSR и гидратация совпадали) и
  выравнивает накопленные границы по шагу в целое число CSS-пикселей, кратное физическому
  пикселю: 4 px на 125% и 175%, 2 px на 150%. Ширины меняются не больше чем на половину шага,
  модель `widths` не трогается; при масштабе без такого шага (110%) раскладка остаётся прежней.
  Дробная привязка ширин и линии фоном проверены и отвергнуты: первая не доходит до раскладки
  Chromium, вторая оставляет полупрозрачный пиксель.
## Consequences

Появляется пакет `@numior/table` (приватный, как и остальные), зона `table` в fallow, корень
тестов `packages/table/test`, скрипты `bench:engine` и `bench:check`, каталог результатов
бенчмарков. Первая запись результатов на машине разработки лежит в `bench/results` и
обновляется на каждом майлстоуне; цифры и устройство — в этом ADR по мере коммитов.

сдвиг окна таблицы заказов вырос с 11,3 до 12,5 мс по p50 в парных прогонах; без демо серверного
источника HEAD совпал с базой, а число композитных слоёв страницы — 230 против 291 с демо. Причина —
приём «липкого окна»: каждая видимая ячейка тела оконной таблицы становится отдельным слоем
(«overlaps other composited content»), и каждая дополнительная оконная таблица на странице добавляет
десятки слоёв и около миллисекунды на кадр всей страницы. Демо серверного источника в песочнице
монтируется по кнопке. Скелетоны загрузки скрыты от чтения и больше не получают `aria-rowindex`
(совпадал с номером строки итогов), а строка итогов во время загрузки не показывает число строк.
Снижение числа слоёв (липкие строки вместо ячеек там, где движок это держит, или меньший запас окна)
требует проверки на реальном экране и вынесено отдельным решением.

на странице песочницы 230 → 92, у таблицы заказов 213 → 75, на странице бенчмарка со 100 000 строк
450 → 101. Оставшиеся слои — ячейки шапки и подвала и закреплённые колонки тела, по слою на ячейку
в строке окна. Шаг прокрутки на 8 px без сдвига окна: 9,4 → 4,1 мс главного потока по p50 в
песочнице и 8,0 → 1,1 мс на странице бенчмарка (строки больше не перерисовываются на каждый кадр).
Сдвиг окна на экран: 12,0 → 11,0 мс в песочнице, 15,4 → 13,8 мс на странице бенчмарка; в бенчмарке
на миллионе строк 18,8 → 15,1 мс по p50, сортировки и фильтры до отрисовки быстрее на 10–25 %,
остальные операции в пределах шума. Отрисовка при сдвиге окна дороже примерно на миллисекунду: слой
один, и при переезде строки из начала `<tbody>` в конец перезаписываются все строки окна.

Общий примитив окна и выровненный диапазон (2026-10-01, парные прогоны 670ff24 и правки, шаг
прокрутки 8px, главный поток). Расчёт рамки переехал в `useVirtualList().frame`, стили и запись
растущего спейсера — в `useVirtualFrame`; на них же переведено дерево. `<table>` сбрасывает у себя
переменные спейсеров в `initial`: наследуемые `--_lead` и `--_rest` на вьюпорте перестилизовывали
всю таблицу на каждом сдвиге окна (1716 элементов на странице бенчмарка, теперь 45). Регистрация
через `@property` с `inherits: false` отвергнута: WebKit не обновляет псевдоэлемент, который берёт
такое свойство через `inherit`, и тест серверного источника в нём падал. У строк одинаковой высоты конец окна считается
от его начала, поэтому обе границы меняются на одном пикселе прокрутки: раньше пересечение строки
давало два обновления окна, когда высота области не кратна высоте строки. Таблица бенчмарка на
100 000 строк: в среднем на шаг 5,1 → 2,7 мс, шаг со сдвигом окна 11,2 → 8,5 мс, шаг внутри
строки 3,6 → 1,25 мс (p95 11,0 → 1,6 мс). Таблица заказов в песочнице: 6,8 → 4,8 мс. Остаток
шага со сдвигом окна — рендер всех строк в JS (слоты строк динамические, около 3,5 мс) и
отрисовка окна вместе с 66 слоями закреплённых ячеек (около 4,5 мс). Бенчмарк на миллионе строк:
сдвиг окна на экран p50 14,4 мс, стрелка вниз 25 мс, Page Down 27 мс.

Долгий кадр при прокрутке колесом на миллионе строк (120–180 мс раз примерно в 25 секунд
непрерывной прокрутки) — фоновая разметка major GC V8 (`V8.GC_MC_BACKGROUND_MARKING`) на куче с
миллионом объектов строк. Он воспроизводится и на 670ff24 в тот же момент, от устройства окна не
зависит и на дереве со 100 000 узлов не появляется; p95 кадра колеса остаётся 16,7 мс.

движка теперь берут 20 проб вместо 5: при пяти пробах p95 равен максимуму, и одна пауза сборки

не регрессия; порог групп по стране пересчитан по 20 пробам (1,5 × p95 = 190 мс).

### Бюджет задержки 100 мс (2026-10-22)

Правило из `editor.adr.md`: действие пользователя на целевых данных (здесь миллион строк) доходит
до нарисованного результата за 100 мс p95; долгие задания режутся на куски с прогрессом, пороги
стерегут цель.

- Подготовка в простое. `engine.prepare(wishes, { sliceMs, yieldTo, signal })` строит недостающие
  хранилища колонок кусками; задание хранилища общее с запросами (`building` по ключу), поэтому
  сортировка или фильтр, начатые посреди подготовки, продолжают недостроенное хранилище, а не
  начинают заново. `NuiTable` со строками без `source` (с `source` ключи считает сервер) после
  монтирования и смены строк или колонок заказывает: словари всех текстовых колонок (быстрый
  фильтр), хранилища сортируемых нетекстовых колонок, ранги сортируемых текстовых колонок. Куски
  по 5 мс идут только в простое (`requestIdleCallback`, в Safari — таймер) и не раньше чем через
  0,5 с после любого ввода на странице (`useIdle` из vueuse: клавиши, `input`, указатель, колесо;
  `input` нужен, потому что редактор ячейки гасит всплытие `keydown`): первая версия с кусками по
  12 мс без паузы поднимала p95 стрелок с 32 до 67 мс и перемонтирование со 168 до 486 мс. Цена —
  память: на миллионе строк с 20 колонками хранилища всех колонок добавляют порядка 200 MB к
  ~400 MB строк. Выключателя нет (решение 2026-10-22): на малых таблицах подготовка ничего не
  стоит, на больших нужна почти всегда.
- Группировка. Ключи группировки ведут сортировку, поэтому строки одной группы лежат подряд:
  конец группы ищется галопом с двоичным поиском по типизированным массивам ключей уровней
  (раньше — сравнение каждой строки через `tokenOf` и `Object.is`). Агрегат `count` не читает
  ключи. Видимый список групп собирается в заранее выделенный `Int32Array` и отдаётся
  `subarray` без копии: копия на миллион ссылок через раз вызывала большую сборку мусора (+300 мс).
  Группировка по двум колонкам в движке: 145–190 → 70–78 мс, проход групп 95 → 20 мс.
- Проверено и отвергнуто: ранжирование миллиона уникальных строк через приближённый ключ
  сортировки (регистр, диакритика, числовые серии, пунктуация ниже цифр) со слиянием по ключу и
  починкой вставками по `collator.compare` давало 3,6 → 2,8 с ценой миллиона строк-ключей и
  сборки мусора. Стоимость упирается в сам `compare` (100–450 нс на пару с промахами кеша), так что
  такие хранилища строятся в простое заранее.
- Бенчмарк: перед первой клавишей быстрого фильтра — пауза 2 с, как у читающего пользователя
  (операция «first quick filter keystroke after a two-second pause»). Без паузы сразу после
  непрерывных действий первая клавиша ждёт словари: 0,9–1,5 с кусками с полосой занятости.
- Пороги `bench:check`: все действия в браузере на миллионе строк и на листе — 100 мс (кадр
  прокрутки — 34, сдвиг окна — 22/45 мс главного потока); тёплые операции движка, которые стоят на
  пути действия (сортировка чисел, мультисортировка, группы, быстрый фильтр), — 100 мс. Построение
  хранилищ с нуля остаётся с прежними порогами: это фоновая работа подготовки.

цифры хуже приёмки 2026-10-03: перемонтирование 137 / 151 против 120 / 129), p50 / p95, мс:

### Сортировка словаря строк в воркере (2026-10-22)

- Ранги строковой колонки — это сортировка её словаря коллатором. На миллионе уникальных email
  нарезанная сортировка слиянием на странице шла 3,4–5 с: упор в `Intl.Collator.compare`, а
  нативный `Array.sort` с тем же коллатором в 3–4 раза быстрее, но одним длинным заданием. Теперь
  словарь от 10 000 строк сортируется в воркере: страница кусками собирает строки в части по 8192
  и отправляет их (каждое сообщение — доли миллисекунды), воркер склеивает части, режет по
  длинам, сортирует нативно коллатором с теми же параметрами (`resolvedOptions`: локаль,
  `numeric`, чувствительность, `caseFirst`, `ignorePunctuation`) и возвращает порядок
  `Uint32Array` с передачей буфера. Ответ ждёт `SliceJob.waiting()`: `runSliced` ждёт обещание,
  а не крутит пустые куски; ожидание проходит через задания хранилищ и конвейер.
- Воркер встроен в бандл (`?worker&inline`): отдельный файл с путём `/assets/…` не разрешился бы
  у потребителя библиотеки, а пребандлинг зависимостей Vite ломает и относительный путь. Если
  `Worker` нет (Node, SSR) или воркер не создался или упал (CSP без `worker-src blob:` и
  `data:`), ранги строятся прежней сортировкой на странице. Правило Oxlint `import/default`
  выключено только для `rank-host.ts`: экспорт по умолчанию у `?worker&inline` создаёт Vite, и
  резолвер его не видит.
- Холодная сортировка по колонке миллиона уникальных email сразу после монтирования, до первой
  паузы, когда подготовка ещё не началась (Docker Chromium 153):
  3365 → 1688 мс, длинных задач на главном потоке нет ни в одном варианте. Остаток — построение
  словаря на странице (`Map` на миллион строк, ~0,6 с кусками: значения достаются функциями
  колонок из объектов приложения, их в воркер не передать) и сама сортировка в воркере (~0,9 с).
  Порог `bench:check` (набор `unique`): длиннейшая задача главного потока ≤ 50 мс; общее время
  записывается.

### Итоги после первого кадра и куски подготовки (2026-10-22)

- Трасса перемонтирования миллиона строк: кадр со строками был готов через ~45 мс, но до него
  таблица синхронно считала итоги подвала (чтение трёх колонок агрегатов и сумма по миллиону строк,
  ~50 мс). Теперь синхронный запуск при монтировании и смене строк делается, только если строки
  меняют сортировка, фильтры или группы. Итоги без такой работы считаются тем же нарезанным
  движком после следующего кадра; это отдельный вид запуска: без полосы занятости, без
  перерисовки строк и без события `settle`, подвал заполняется по готовности. На сервере (SSR) и с
  `source` итоги по-прежнему считаются сразу.
- Куски фоновой работы уступают поток обычной задачей в конце очереди (`yieldInLine`, через
  `MessageChannel`), а не через `scheduler.yield`: продолжения `scheduler.yield` обгоняют другие
  задачи, и фоновые итоги задерживали всё, что страница поставила в очередь после кадра.
- Подготовка в простое выполняла куски микрозадачами внутри одного `requestIdleCallback` — задачи
  по 46 мс, за которыми ждал ввод. Теперь каждый кусок (8 мс) — отдельная задача, пока у окна
  простоя есть запас; после ввода работа ждёт тишины.
- Трасса: перемонтирование 52–82 мс (было ~104), стрелки 26 / 29 мс, самый длинный кусок
  подготовки 15,6 мс; длинные задачи — только сами монтажи (17–55 мс).
