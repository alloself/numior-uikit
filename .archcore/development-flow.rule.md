## Rule

Разработка идёт по одной задаче за раз в основном рабочем дереве репозитория. Git worktree и другие
рабочие копии для разработки не создаются: ни `git worktree add`, ни `EnterWorktree`, ни клон или
копия каталога, ни субагент или workflow с `isolation: worktree` или `remote`. В уже созданных
worktree ничего не правят и не коммитят.

Задача начинается с актуального `master`: своя ветка `<тип>/<тема>` в терминах Conventional
Commits, коммиты только в ней, полная проверка (`pnpm check`, для браузерного поведения
`pnpm test:e2e`) на последнем коммите. Готовая ветка уходит в merge request, и в `master` её вливает
владелец после ревью. Агент не коммитит в `master`, не вливает и не пушит в него ветки и не двигает
его указатель (`reset`, `branch -f`, `update-ref`, `fetch …:master`). После того как MR влит,
`master` обновляется через `git pull --ff-only`, а влитая ветка удаляется.

Следующая задача начинается только после того, как MR предыдущей влит или закрыт: в репозитории нет
второй локальной ветки с коммитами вне `master`. Параллельные сессии агентов в одном репозитории не
ведутся. Побочная находка во время задачи записывается в план и становится следующей задачей, а не
частью текущей ветки.

MR — pull request в приватном репозитории GitHub `alloself/numior-uikit` (remote `origin`): агент
пушит ветку задачи и открывает PR с описанием и результатами проверок, владелец смотрит его и
вливает на GitHub.

Снимок дерева для прогона в Docker или для A/B-бенчмарка (rsync, `git archive <ref> | tar -x`) —
одноразовая копия только для запуска: в ней ничего не правят и не коммитят, а все изменения вносятся
в основном дереве.

## Rationale

Параллельная работа в worktree приносит в `master` несколько потоков коммитов сразу, и владелец
перестаёт контролировать код, который в него попадает. На 2026-11-23 у репозитория было семь
worktree рядом с основным деревом и восьмой в каталоге сессии, тринадцать локальных веток и
39 файлов с незакоммиченными изменениями в одном из worktree. 2026-11-10 падение WSL стёрло worktree в `/tmp`
вместе с готовыми, но не закоммиченными исправлениями. Одна ветка за раз и MR дают одну точку
контроля: в `master` попадает только то, что владелец посмотрел и влил сам.

## Examples

Good: агент переключается на свежий `master`, создаёт `fix/table-window`, коммитит исправление с
тестами, прогоняет `pnpm check` и передаёт ветку на MR; следующую задачу он начинает после того, как
владелец влил MR, а ветка удалена.

Good: для прогона e2e в Docker агент снимает rsync-копию основного дерева, запускает в ней тесты и
правит упавший код в основном дереве.

Bad: агент заводит `~/numior-uikit-docs` через `git worktree add` и ведёт там документацию, пока в
основном дереве идёт исправление таблицы.

Bad: агент сам делает `git merge --ff-only fix/x` в `master`, потому что ветка «очевидно готова».

Bad: субагент с `isolation: worktree` делает часть задачи в своей копии, а результат переносится в
ветку пачкой.

## Enforcement

Хук Claude Code `.claude/hooks/git-guard.mjs` (PreToolUse в `.claude/settings.json`) отклоняет:

- `git worktree add`, `EnterWorktree`, `isolation: worktree` и `remote` у Agent и Workflow,
  `git clone` этого репозитория;
- правку файлов и любые команды git, кроме чтения (`status`, `diff`, `log` и подобных), в linked
  worktree;
- на `master`: `commit`, `merge` (кроме `--ff-only` с remote-ветки и `--abort`), `pull` без
  `--ff-only`, `rebase`, `cherry-pick`, `revert`, `am`, `reset` на другой коммит и `push` текущей
  ветки;
- с любой ветки: `push`, `fetch`, `branch -f/-m/-c/-d`, `update-ref`, `checkout -B` и
  `switch -C` с целью `master`;
- создание новой ветки, пока другая локальная ветка содержит коммиты вне `master`.

`worktree.bgIsolation: none` в тех же настройках оставляет фоновые сессии в основном дереве, без
обязательного `EnterWorktree`. `git worktree list`, `remove` и `prune` разрешены для уборки старых
worktree. Команды владельца хук не трогает: ветки вливает и `master` двигает он сам.
