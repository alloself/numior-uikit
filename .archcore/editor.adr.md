## Context

План 1.0 требует собственный редактор: rich text, таблицы, медиа, блоки в духе Notion, вставку из
Office, совместную работу, комментарии и историю — без ProseMirror или Tiptap в основе. Viewer и
SSR не загружают runtime редактора, а документ на 10 000 смешанных блоков редактируется без
задержек ввода. Волна 7 начинает блок C с ядра `@numior/editor-core`: модель документа, схема и
позиции. Шаги и транзакции, вид, Vue-обёртка и содержимое для публикации идут следующими коммитами
(план волны, коммиты C1–C24).

## Decision

- Пакет `@numior/editor-core` (приватный) без зависимостей. Точки входа: `.` (модель, схема,
  документ; дальше — шаги, состояние, команды, HTML, история) и `./fixtures` (схема фикстур и
  генератор документов). DOM появится только в будущей точке входа `./view`. `check-artifacts.mjs`
  проверяет, что сборка не импортирует `vue`, `@vueuse/*` и пакеты `@numior` и не трогает
  `document`, `window` и `navigator`. Тесты ядра идут в Node-проекте vitest (`*.node.test.ts`).
- Узлы — неизменяемые объекты двух видов: текст `{ kind: 'text', text, marks }` и элемент
  `{ kind: 'element', id, type, attrs, content, leaf, size }`. У элемента стабильный строковый
  `id` для якорей комментариев, истории и совместной работы. У текста id нет: соседние тексты с
  одинаковыми пометками сливаются, пустые выбрасываются. `size` и `leaf` вычисляет фабрика схемы.
- Позиции — плоские целые в единицах UTF-16, как смещения DOM Selection. Текст занимает свою
  длину, элемент с содержимым — содержимое плюс два токена границ, лист — одну позицию.
  Содержимое корня начинается с 0, размер документа — размер содержимого корня. Смещения детей
  элемента кешируются в `WeakMap` по самому узлу, ребёнок по позиции ищется двоичным поиском.
- Схема: `createSchema({ nodes, marks, top })`. Узел объявляет `content` (выражение), `group`
  (группы через пробел), `inline`, `marks` и `attrs` с `default` и гардом `verify`. В `marks`
  `_` — все пометки, пустая строка — никакие, иначе имена и группы; по умолчанию все пометки
  разрешены узлам со строчным содержимым. Узел без `content` — лист, `text` объявляется в схеме как
  строчный узел.
- Выражения содержимого: имена узлов и групп, последовательность, `|`, скобки, `*`, `+`, `?`,
  `{n}`, `{n,}`, `{n,m}`. Разбор идёт в дерево, компиляция — в автомат Томпсона, детерминизация
  подмножествами даёт `ContentMatch` (`validEnd`, `next`, `matchType`, `matchContent`), поэтому
  неоднозначные выражения вроде `paragraph* paragraph` работают. Неизвестные имена, смешение
  строчных и блочных узлов в одном выражении и типы без достижимого правильного содержимого
  отвергаются `SyntaxError` при создании схемы.
- Фабрики `schema.element(type, { id, attrs, content })`, `schema.text(text, marks)` и
  `schema.mark(type, attrs)` заполняют умолчания и бросают `RangeError` на неизвестные,
  недостающие и неверные атрибуты. Пометки упорядочиваются по схеме, повтор типа заменяет прежнюю.
  Содержимое фабрика не проверяет: это делает `schema.check(root)`, который возвращает `{ ok:
  true }` или проблемы с путём — тип, содержимое, пометка, атрибут, id (пустой, повтор), текст
  (пустой, не слитый) и размер.
- `schema.restrict({ nodes, marks })` строит схему-подмножество для пресетов автора. Корень и
  `text` остаются всегда, имена вне исходной схемы дают `RangeError`, повторное ограничение только
  сужает. Типы, которым без выкинутых узлов не собрать правильное содержимое (список без пунктов),
  выпадают каскадом. Ограничения значений атрибутов (уровни заголовков, палитры) придут вместе с
  пресетами редактора.
- Документ `createDoc(schema, root)` даёт `size`, `resolve(pos)` (глубина, родитель, индекс,
  смещение в тексте, соседние узлы, `start/end/before/after` предков), `nodeAt`, `byId` и
  `positionOf` (документ после шага ищет id через предыдущий документ, раздел «Поиск узла по id»
  ниже; иначе — ленивый индекс, один раз на версию документа), `nodesBetween`
  (`false` отменяет спуск), `textBetween` с разделителем блоков и `slice(from, to)` с открытыми
  глубинами слева и справа. Частично вырезанные элементы среза сохраняют id: срез не часть
  документа, а перевыдача id — работа шагов.
- Генератор `generateDoc(schema, { blocks, seed, mix })` на mulberry32 строит документ из блоков
  схемы фикстур: 55 % абзацев, заголовки, вложенные списки трёх видов, таблицы, код, картинки,
  callout, toggle, колонки, цитаты и разделители. Одно зерно даёт один и тот же документ.
  Отклонение от плана: генератор опирается на имена узлов `fixtureSchema`, а не на любую схему;
  схема `@numior/content` получит свой набор вместе с пакетом.

- Проверка рамки `replaceAround` при разборе JSON (2026-11-09): срез такого шага — рамка с зазором в
  `insert`, узлы вокруг зазора законно неполные, и закрытая проверка отвергала обёртку абзаца в пункт
  задач на сервере. `checkSlice` получает позицию зазора и открыто проверяет только узлы, его
  содержащие; всё вне зазора проверяется как обычно, итог проверяет `applyPlan`.
- Шаги (коммит C2, 2026-10-03): `replace`, `replaceAround`, `addMark`, `removeMark`, `attrs` и
  `docAttrs`. `applyStep` возвращает новый документ или причину отказа: `range`, `depth`,
  `content`, `id`, `target`, `attrs`. Замена идёт по потоку токенов: открытие, закрытие, текст и
  целый узел. Раскрываются только узлы, в которых лежит граница, поток склеивается и собирается
  заново, а узел получает id своего открывающего токена: левый край среза сливается с узлом у
  `from`, узлы правого края приходят из среза.
- Правила замены: глубины среза должны сойтись (`depth(from) - openStart = depth(to) - openEnd`),
  пересобранные узлы проверяются по выражению содержимого и пометкам текста, целые узлы среза —
  полной проверкой. Id вставляемых узлов не должны совпасть с id, которые остаются в документе вне
  заменяемого диапазона. `replaceAround` вставляет плоский зазор документа в срез по `insert` и
  сводится к той же замене, поэтому обёртка и подъём блока обратимы.
- Отображения: `createStepMap` хранит диапазоны `{ start, oldSize, newSize }`, `map` учитывает
  сторону (`assoc`), `mapResult` сообщает, удалено ли что-то до, после или вокруг позиции.
  `createMapping` — неизменяемый список карт со `slice`, `concat` и `invert`. Зеркала для
  перебазирования добавятся вместе с совместной работой.
- `invertStep` берёт документ до шага, `mapStep` отбрасывает шаг, чей диапазон удалён, а
  `mergeSteps` склеивает набор текста, серии Backspace и Delete и смежные пометки.
- Транзакции: `createTransform(doc, { ids })` копит шаги, документы до них и карты. `replace`
  выдаёт новые id вставленным узлам, чьи id заняты вне диапазона; `insertText` берёт пометки текста
  перед позицией. `addMark` сначала снимает пометку того же типа с другими атрибутами, поэтому
  обратный шаг точен; `removeMark` снимает пометки по типу или экземпляру. Есть ещё `split` (с
  новым id и необязательным новым типом), `join`, `setNodeAttrs` и `setDocAttrs`. Удаление через
  границы разной глубины с подбором открытых глубин придёт с командами (коммит C4).
- Свойства на fast-check: случайные правки документов генератора сохраняют валидность, обратные
  шаги возвращают исходный документ, отображение монотонно и обратимо для неудалённых позиций.

- Выделение и состояние (коммит C4, 2026-10-03): выделение — объединение `text { anchor, head }`,
  `node { id }`, `block { anchorId, headId }`, `cell { tableId, anchor, head }` и `all`.
  Узловые виды держатся за id, поэтому переживают правки вокруг; если узел исчез, выделение
  переходит в ближайший текст. Текстовое выделение после отображения и при установке приводится к
  позициям внутри текстовых блоков (`nearestCursor`, `validSelection`).
- `createState({ doc, selection, storedMarks, plugins })` и `state.tr`: транзакция — обёртка над
  трансформацией с выделением (отображается через новые шаги, пока его не задали явно),
  сохранёнными пометками (сбрасываются при изменении документа) и типизированными метаданными через
  `createMetaKey<T>()`. `insertText` без позиций заменяет выделение и ставит курсор после текста,
  есть `replaceSelection` и `deleteSelection`.
- Плагины — `definePlugin<S>({ name, state, filterTransaction, appendTransaction })`. Состояние
  плагина хранится в самом плагине по объекту состояния редактора (`plugin.getState(state)`), без
  ключей и приведения типов. `filterTransaction` отменяет транзакцию, а `appendTransaction`
  дописывает следующие: каждый плагин видит ещё не виденные транзакции, раундов не больше 32.
  Клавиатурные карты, правила ввода, декорации и node views войдут в спецификацию плагина вместе с
  видом.
- Команды `(state, dispatch?) => boolean`: `splitBlock` (в конце заголовка новый блок получает
  первый текстовый тип, который родитель допускает дальше), `joinBackward` и `joinForward` (склейка
  с соседним текстовым блоком или удаление соседнего листа), `deleteSelection`, `selectAll`,
  `toggleMark` (на курсоре — сохранённые пометки) и `setBlockType` (одним шагом `markup` на все
  текстовые блоки диапазона, id не меняются), плюс `chainCommands`. Удаление через границы разной глубины сохраняет оба края (левая цепочка
  закрывается, правая открывается заново), склейку таких краёв добавят команды списков (коммит C11).

- Вид (коммит C5, 2026-10-03): точка входа `@numior/editor-core/view` — единственная с DOM.
  `createEditorView(root, { state, editable })` делает переданный элемент корнем `contenteditable`
  (`role="textbox"`, `aria-multiline`, `white-space: pre-wrap`) и рисует в нём документ. `update`
  сверяет новое дерево со старым, `posAtDOM` и `domAtPos` переводят позиции, `nodeDOM(id)` отдаёт
  элемент узла, `destroy` оставляет хост пустым.
- Отрисовку задаёт схема: `render` у узла и пометки возвращает спецификацию без DOM
  (`renderTag(tag, attrs, children)` и `contentHole`). Её же прочитают сериализатор HTML (C9) и
  `@numior/content` (C10). Без `render` блок — `div`, строчный лист — `span`, пометка — `span`.
  Дыра содержимого одна и единственный ребёнок своего элемента. Статичные соседи на пути к ней и
  листья, кроме `br`, получают `contenteditable="false"`; нарушения дают `RangeError`.
- Сверка: у каждого узла есть дескриптор с DOM, детьми и индексом. Равные ссылки неизменяемых
  узлов пропускают поддерево целиком. Дети элемента сопоставляются по id: при том же типе и
  атрибутах дескриптор переиспользуется и переставляется, иначе узел рисуется заново. Тексты
  сопоставляются по порядку и пометкам, и у того же `Text` меняется только `data`.
- DOM детей переставляется одним проходом с курсором, лишние дескрипторы снимаются. Каждый текст
  рисуется своей цепочкой обёрток пометок в порядке схемы. Пустой текстовый блок и блок, который
  кончается переводом строки, получают служебный `br`: иначе строка в браузере не получит высоту.
- Дескриптор не хранит позицию: начало считается по цепочке родителей и кешу смещений детей,
  поэтому блоки ниже правки ничего не пересчитывают. `posAtDOM` поднимается от точки DOM до
  ближайшего дескриптора. Внутри текста это смещение, в обёртке пометки и листе — край узла, в
  статичной части — начало или конец содержимого.
- Блоки верхнего уровня лежат в чанках по 32, и `content-visibility: auto` с
  `contain-intrinsic-block-size: auto` (оценка по размеру узлов) стоит на чанке; ключевое слово
  `auto` хранит измеренный размер в браузере. Блоки из DOM не выбрасываются. До C8 свойство и кеш
  высот с `ResizeObserver` были на каждом блоке; почему это изменилось — в разделе бенчмарка C8.
- Отклонения от плана: ввод, синхронизация выделения и композиция переходят в C6, декорации и
  node views — к плагинам вида. Сверка обходит всех детей корня: сравнить 10 000 ссылок дешевле,
  чем разбирать диапазоны `tr.mapping`, а бенчмарк ввода (C8) покажет, нужно ли сужать обход.

- Ввод (коммит C6, 2026-10-15): вид принимает `dispatch` в опциях и без него применяет транзакции
  сам. `beforeinput` переводится в `InputIntent` (`insertText`, `insertParagraph`,
  `insertLineBreak`, `delete` с направлением и единицей, `format`, `history`, `paste`, `compose`)
  и отменяется; намерение идёт сначала в `props.handleIntent` плагинов, затем в
  `intentCommand`. Диапазон `getTargetRanges()` уточняет удаление и замену проверки орфографии.
  Транзакции ввода несут `inputSource` (`type`, `delete`, `compose`, `paste`, `key`, `pointer`):
  его прочтёт группировка истории.
- Команды ввода живут в ядре и работают без DOM: удаление по графемам и словам через
  `Intl.Segmenter`, по строке до края блока; Enter разбивает блок, Shift+Enter в коде даёт перевод
  строки, иначе жёсткий перенос схемы; вставка простого текста разбивает строки на блоки.
  Выделить всё и удалить оставляет один пустой текстовый блок. Узел схемы с `code: true` хранит
  переводы строк как текст.
- Выделение: `selectionchange` читает DOM в модель (атом шириной в одну позицию становится узловым
  выделением); вид пишет выделение в DOM только при расхождении, с фокусом и не во время
  композиции. Узловое выделение отмечает элемент классом `nui-editor__selected`. Клик по атому и
  стрелки рядом с ним выделяют узел (`selectAtom`), стрелки из узла ставят курсор за ним, в RTL
  горизонтальные стрелки зеркальны.
- Непрочитанное выделение (2026-11-10, находка E22). `selectionchange` приходит задачей позже щелчка, и
  обновление состояния снаружи (чужой шаг, присутствие, подтверждение) в этом промежутке писало в DOM
  прежнее выделение: щелчок терялся, набор уходил на старое место. Замер в Chromium при печатающем
  участнике: 37 потерянных щелчков из 240, после правки 0. Вид помнит выделение DOM, которое последним
  прочитал или записал (`seen`); обновление, пришедшее не через `dispatch` вида, не пишет выделение,
  если DOM-выделение с тех пор изменилось и не совпадает с состоянием, — его дочитает
  `selectionchange`. Признак снимается до синхронизации DOM, чтобы сдвиг каретки самим обновлением не
  считался действием человека. Собственные транзакции вида (клавиши, ввод, мышь) пишут выделение
  всегда. Текстовый узел обновляется `replaceData` по общему началу и концу, а не заменой `data`
  целиком: браузер сам сдвигает непрочитанную каретку через чужую вставку в том же узле. Отвергнуто:
  читать DOM-выделение перед каждой внешней транзакцией — транзакция уже построена от прежнего
  состояния и несёт прежнее выделение.
- Режим чтения (2026-11-10, находки E12 и X1). Вид знает, редактируем ли он: транзакция с правкой
  документа, пришедшая из ввода (клавиша, набор, вставка, перетаскивание), в нередактируемом виде
  отбрасывается в одном месте — `host.dispatch`; выделение читается как обычно. Раньше защитой был
  только `contenteditable="false"`, и перетащенный текст менял документ. `NuiEditor` в `readonly`
  получает `tabindex="0"`: поле достижимо с клавиатуры и щелчком, как родное поле только для чтения.
  Если заданы `selectionActions`, над выделением открывается панель только с ними, на сенсорном экране
  они стоят в панели инструментов без остальных групп (`ToolbarOptions.actionsOnly`): роль
  «комментирует, но не правит» получает вход в комментарий. Программные команды (`editor.run`) режим
  чтения не ограничивает — это решение владельца.
- Композиция: `compositionstart` замораживает запись в DOM и чтение выделения,
  `insertCompositionText` не отменяется. Корневой `MutationObserver` копит изменённые текстовые
  блоки; на `compositionend` или сразу для правки вне композиции (Android, автозамена) текст
  блока сравнивается с моделью общим префиксом и суффиксом, разница становится намерением
  `compose`, блок перерисовывается из модели. Свои правки вида наблюдатель пропускает.
- `coordsAtPos` берёт прямоугольник схлопнутого диапазона, а при нулевом (WebKit) — диапазона в
  один соседний символ; `posAtCoords` идёт через `caretPositionFromPoint` или
  `caretRangeFromPoint`. Сценарии jsdom проверяют ввод, выделение, композицию и атомы; геометрия
  каретки и настоящий IME проверяются в браузерах вместе с `NuiEditor`.
- JSON (2026-10-15, перенесён из C9): `toJSON(doc)` даёт `{ format: 1, schema: { name, version },
  root }`, где элемент — `{ id, type, attrs?, content? }`, текст — `{ text, marks? }`; пустые
  атрибуты, содержимое и пометки не пишутся. Схема получает `name` и `version` (по умолчанию
  `document` и 1). `fromJSON(schema, unknown)` возвращает `{ ok, doc }` или `{ ok: false, issues }`:
  чужой формат, другая схема или версия, ошибки формы с путём по индексам детей, затем проблемы
  `schema.check`. Атрибуты по умолчанию дописываются, пометки упорядочиваются схемой. Миграции
  версий схемы появятся вместе с offline (блок E), до тех пор другая версия отклоняется.
- HTML (коммит C9, 2026-10-15): `toHTML(doc)` и `contentToHTML(schema, nodes)` пишут разметку
  теми же спецификациями `render`, что вид и `@numior/content`; общий обход `renderTree` переехал из
  `@numior/content` в ядро. `fromHTML(schema, html, { ids, whitespace })` читает HTML без DOM:
  свой токенайзер (сущности, атрибуты в любых кавычках, сырой текст `script`/`style`, комментарии)
  и построитель дерева с неявным закрытием `p`, `li`, `td`, `tr` и потолком вложенности 256.
- Правила разбора живут в схеме: `parse` у узла (`{ tag, priority, attrs }`) и у пометки
  (`{ tag | style, attrs }`); `attrs` получает элемент с `attr`, `hasClass`, `classWith`, `style`,
  `text` и `find` и возвращает атрибуты или `false`. Значения проходят `verify` схемы: неверное
  заменяется умолчанием, без умолчания узел или пометка отбрасываются — так ссылка `javascript:` и
  картинка с чужой схемой не попадают в документ. Из нескольких правил одного тега выигрывает узел,
  который текущий контейнер принимает сразу (`li` в списке задач становится пунктом задачи).
- Построитель держит стек открытых узлов с автоматами содержимого: то, что контейнер не принимает,
  оборачивается кратчайшей цепочкой (текст в корне — абзац, `li` без списка — маркированный
  список, ячейка — таблица и строка) или закрывает контейнеры выше (картинка внутри абзаца режет
  его). Узел, который закрывается неполным, достраивается пустыми узлами (пустая цитата получает
  абзац). Неизвестные теги прозрачны, блочные из них закрывают текущий текстовый блок;
  `script`, `style`, `head`, формы и медиа пропускаются. Пробелы схлопываются как в браузере, в
  `pre` и в узлах `code` сохраняются, служебный `br` в конце текстового блока отбрасывается.
  Если результат всё же не проходит `schema.check`, `fromHTML` отдаёт пустой документ.
- Вставка: намерение `paste` несёт `html`. `insertHTML` читает его схемой документа и ставит
  блоки так: пустой текстовый блок заменяется вставкой как есть; одна строка встаёт в текущий
  блок; несколько блоков разрезают текущий блок, и крайние текстовые блоки сливаются с его
  половинами (контейнер с краю получает пустую половину). Если контейнер не держит вставленные
  блоки (заголовок в пункте списка), текстовые блоки вставки становятся блоками текущего типа,
  код — по строке на блок. В коде и когда HTML ничего не дал вставляется простой текст. Вся
  вставка — одна транзакция и один шаг отмены.
- Копирование и вырезание любого непустого выделения идут через свой обработчик: `text/plain` —
  текст с переводом строки между блоками, `text/html` — разметка среза в обёртке с атрибутом
  `data-numior-editor`. По нему вставка узнаёт свою разметку и сохраняет пробелы, а чужая
  разметка, включая скопированную браузером публикацию, схлопывает их.
- Текст узла без текстовых детей (2026-11-10): `NodeSpec.plainText(node)` отдаёт строку, которой
  узел представлен в `textBetween` и в `text/plain` буфера; внутрь такого узла обход не идёт.
  В `contentSchema`: перенос строки — `\n`, упоминание — `@имя`, файл — имя или адрес, embed и
  закладка — адрес, таблица — строки через `\n` и ячейки через табуляцию с именами колонок первой
  строкой (табуляция и перевод строки внутри ячейки становятся пробелом, флажок — `TRUE`/`FALSE`).

- `contentSchema` получила правила для своих классов и для разметки других сайтов: `h1`–`h6`

  списком задач, `details`/`summary` — toggle, `figure` с `figcaption` и голый `img` — картинкой,
  `pre` с классом `language-*` — кодом с языком, `mark` — жёлтым выделением; полужирный, курсив,
  подчёркивание и зачёркивание читаются и из тегов, и из `style` (обёртка Google Docs

  `class="language-*"`, иначе их нельзя прочитать обратно; язык кода проверяется по
  `[\w#+.-]{1,32}`. Корпус Word и Google Docs с нормализаторами по источнику остаётся коммиту

  Новая правка очищает ветку повтора, транзакции с `addToHistory: false` отображают шаги истории.
  Полное перебазирование по `meta.remote` придёт с совместной работой (блок E): пока шаги старых
  событий отображаются той же картой, что и последние.
- `keymap(bindings)` нормализует имена (`Mod-Shift-z`: `Mod` — Ctrl или Cmd) и при модификаторе
  ищет букву ещё и по `code`, поэтому Ctrl+Я работает как Ctrl+Z. `baseKeymap`: Ctrl+B/I/U,
  Ctrl+Z, Ctrl+Shift+Z и Ctrl+Y, Tab и Shift+Tab в списках. Enter и Backspace приходят
  намерениями: `intentCommand` сначала пробует `splitListItem` и `liftAtStart`.
- Правила ввода — плагин `inputRules(rules)`: напечатанный или составленный текст сначала
  вставляется, затем правило проверяет текст перед курсором и правит ту же транзакцию.
  Backspace сразу после срабатывания откатывает только шаги правила, напечатанное остаётся.
  `markdownRules`: `#`–`###`, `>`, `-`/`*`, `1.`, `[ ]`/`[x]`, ```` ``` ````, `---` в начале
  блока и `**`, `*`, `` ` ``, `~~` в строке; в коде правила молчат, блок, который не может
  стать целью (таблица, пометки в коде), остаётся текстом.
- Команды блоков: `splitListItem` (пустой пункт выходит из списка, новый todo без отметки),
  `liftListItem` (список режется вокруг пункта; вложенный пункт уносит следующих соседей в свой
  подсписок), `sinkListItem` (в подсписок предыдущего пункта), `liftAtStart` (Backspace в начале
  пункта или первого абзаца цитаты и выноски), `turnIntoList`, `wrapInBlock` и помощники
  транзакций для правил. Перенос узлов идёт вставкой и удалением с теми же id: транзакция
  пропускает удаление, после которого документ пуст, поэтому вставка идёт первой.
- `@numior/editor-vue` (2026-10-15): `NuiEditor` — поле кита вокруг вида. Рамка, метка,
  описание и ошибка идут через `useFieldControl` и `NuiFieldFrame`; корень `contenteditable`
  получает имя из `aria-labelledby` метки, `aria-describedby`, `aria-invalid`, `aria-required`,
  `aria-readonly`, `aria-disabled` и `aria-placeholder`, а пустой документ показывает подсказку
  через `attr()` под классом `nui-editor--empty`. Схема по умолчанию — `contentSchema`, плагины —
  правила markdown, `baseKeymap` и история.
- `v-model` с `format="json"` (до C21 — `v-model:document`) получает JSON после каждой меняющей транзакции. `toJSON` запоминает JSON
  элемента по ссылке на неизменяемый узел, поэтому нажатие пересобирает только путь до правки.
  Своё эхо редактор узнаёт по `toRaw`: `v-model` родителя возвращает реактивный прокси того же
  объекта. Новый документ снаружи создаёт новое состояние, история начинается заново.
  С 2026-11-10 эхо узнаётся и по содержимому: владелец модели, который хранит копию значения
  (`@numior/forms` клонирует каждое значение, сторы с `structuredClone`), возвращал другой объект с
  тем же документом, и редактор на каждое нажатие сбрасывал каретку, историю и загрузки.
  `sameDocJSON` (ядро) сравнивает пришедший JSON с последним записанным: формат, штамп схемы, id,
  типы, атрибуты, текст и пометки; отсутствующие `attrs`, `marks` и `content` равны пустым. На
  документе в 10 000 блоков сравнение занимает около 6 мс и выполняется только когда объект другой.
  Копия более старого значения (владелец с задержкой) по-прежнему считается новым документом.
- SSR: сервер рисует на месте корня разметку `NuiContent`, после монтирования вид забирает
  документ, статичная копия уходит; гидратация проходит без расхождений.
- Попутно в ядре: `createEmptyDoc` и `isEmptyDoc`; Ctrl+A выделяет весь документ, а DOM-выделение
  от первого до последнего текстового места читается как `all` (иначе удаление оставляло пустой
  заголовок первого блока); перед клавишей и `beforeinput` вид читает DOM-выделение; правка DOM
  без событий ввода оставляет курсор там, где его держит DOM, а не за вставкой.
- Редактор пишет текстом контента (`--nui-font-size-*` по `size`), а не шрифтом контролов: правка
  и публикация совпадают по кеглю. Блоки с `content-visibility: auto` получают paint containment,
  поэтому кольцо выделенного строчного атома рисуется без отступа, иначе абзац срезает его край.
  Строчный код и выделение цветом повторяют поля на каждом куске переноса
  (`box-decoration-break: clone`); в редакторе строчный код схлопывает пробелы, иначе висячий
  пробел `pre-wrap` в конце строки остаётся внутри фона и поля выходят разными.
  Блок кода в редакторе переносит строки вместо собственной прокрутки: под `content-visibility`
  Firefox и WebKit считают его прокручиваемой областью без фокуса, и axe находит нарушение
  `scrollable-region-focusable`.
- Страница бенча: `/bench.html?view=editor&blocks=10000&seed=1` (сгенерированный документ на
  `contentSchema`). Страница документации `NuiEditor` — в долге блока F, описания пропов — в
  `apps/docs/api/editor.ts`.

### Node views (C14, 2026-10-16)

- `EditorViewOptions.nodeViews` — фабрики по типу узла, `(node) => NodeView { dom, contentDOM,
  update(node), destroy() }`. Вид спрашивает фабрику вместо спецификации `render`; узел с видом
  переживает смену атрибутов, если `update` вернул `true` (без вида смена атрибутов пересоздаёт
  DOM узла), а `destroy` вызывается при удалении узла и при закрытии вида. `renderNodeDOM`
  отдаёт фабрике DOM по спецификации схемы, чтобы вид не повторял разметку `NuiContent`.
- Всё внутри `dom` узла с видом, но вне его `contentDOM`, принадлежит виджету: мутации там не
  читаются как ввод, а `keydown`, `beforeinput`, вставка, копирование, `mousedown`, композиция
  и `selectionchange` оттуда редактор не обрабатывает. Отдельных `stopEvent` и
  `ignoreMutation` у вида нет: правило одно для всех, пока свой блок не попросит другого.
- `@numior/editor-vue` строит node views из `defineBlock({ name, view, at, handle, keymap, slash, menu })`
  (проп `blocks` у `NuiEditor`, читается при монтировании). Фабрика берёт DOM узла по схеме,
  убирает статичную обвязку рядом с дыркой (её место занимает виджет), у узла без дырки внутри
  корня заводит тело `nui-editor__body`, а виджет `nui-editor__widget` (`contenteditable=false`)
  ставит в начало или конец. Компонент блока телепортируется в виджет из хоста
  `NuiEditorNodeViews` внутри того же приложения (работают конфиг, иконки, словарь) и получает
  `node`, `element`, `selected`, `editable` и `editor` (`setAttrs`, `remove`, `run`, `focus`,
  `setStyle` — временный стиль элемента блока, например ширина посреди протяжки; следующая
  отрисовка узла его переписывает; `element()` — элемент блока, например чтобы взять его
  документ), а также `focused` — фокус внутри редактора (плавающие панели блока видны, только
  пока он есть). Пункты slash-меню — объединение `kind: 'command'` (команда
  после удаления запроса) и `kind: 'open'` (удалить запрос и открыть панель, например вставку
  картинки); команда больше не служит открытием интерфейса. Список вставки один: базовые блоки,
  пункты `slash` всех блоков из `blocks` и «Картинка»/«Файл»; из него строятся и меню «/», и кнопка
  «Вставить» (+) в шапке сразу после отмены и повтора (пункты, чья команда сейчас неприменима,
  отключены). Плавающая панель над выделением «Вставить» не показывает.
  `update` всегда принимает узел и переносит на корень только то, что поменялось между двумя
  отрисовками схемы, поэтому классы, которые ставит сам блок, не стираются. Состояние просмотра
  (`defineBlockState`) живёт на редактор и узел, без шагов истории, и переживает пересоздание
  DOM. `extendContentSchema(nodes)` добавляет узлы к `contentSchema` для редактора и
  `NuiContent`; `insertLeaf(type)` вставляет блок-лист, как разделитель.
- Компоненты блоков монтируются лениво: хост рисует только виды, чей узел хоть раз попал в
  `IntersectionObserver` (наблюдается элемент узла: у виджета может не быть коробки, `display: contents`) с запасом в экран, и получает id выделенного узла, а не всё состояние,
  поэтому транзакция не перерисовывает хост. `update` перерисовывает разметку узла только при
  смене атрибутов. Без этого встроенные блоки на документе в 10 000 блоков поднимали холодный
  монтаж с 0,85 до 1,52 с и p95 набора с 17 до 26 мс; после — в пределах шума относительно
  HEAD без блоков на той же машине (2026-10-16: монтаж 1,09 против 1,10 с, набор p95 21 против
  19 мс, жирный по всему документу 0,49 против 0,45 с).
- Встроенные блоки (`editorBlocks`, по умолчанию в `blocks`): флажок todo (`NuiCheckbox`, клик и
  Ctrl+Enter — шаг истории), toggle (та же кнопка раскрытия, что у `NuiContent`, с теми же стилями; раскрытие — состояние просмотра без
  шага истории, Enter в конце заголовка закрытого toggle создаёт абзац после него, «Открыт по
  умолчанию» в меню ручки пишет атрибут), выноска (кнопка с иконкой тона и меню тонов, то же
  подменю «Тон» у ручки). Иконка тона в `NuiContent` — маска на псевдоэлементе с путями Lucide:
  у статического рендера нет рантайма иконок, поэтому это исключение из правила реестра иконок.
  Наведение на виджет блока не показывает ручку: иначе сдвиг уводил флажок из-под указателя.
- Перенос между контейнерами (C14, часть 2): `NodeSpec.slots` говорит, чьи дети — самостоятельные
  блоки (`'all'` у корня, списков и колонки, `'rest'` у выноски, цитаты и toggle: их первая строка
  представляет сам контейнер). `moveBlock(from, { parent, index })` сначала вынимает блок и убирает
  опустевшие контейнеры (список и колонка исчезают, колонки из одной колонки распаковываются,
  выноска получает пустой абзац), затем вставляет его по соседям-якорям с преобразованием: абзац или
  заголовок между пунктами становится пунктом, пункт вне списка — списком своего вида, пункт другого
  списка меняет вид, соседние списки одного вида сливаются. Итоговое дерево собирается от ветки ближайшего
  общего предка, документ приходит к нему шагами без копий узлов (с 2026-11-12, см. «Шаг move»: до этого —
  один шаг `replace` над всем участком); отмена одна, нетронутые узлы остаются теми же объектами. `containerSlot` даёт ближайший контейнер для
  пункта меню ручки «Весь список / Вся выноска / Все колонки…».
- Перетаскивание ручкой (C14, часть 2) идёт своим двухосевым сеансом (`use-block-drag.ts`: порог,
  автопрокрутка у края, Escape) вместо индексного `useReorder`: цель — самый глубокий контейнер
  под указателем (между блоками, под первой строкой выноски, цитаты или открытого toggle, между
  пунктами), а если схема не принимает блок даже с преобразованием — следующий контейнер выше.
- Колонки: разметка `columns > columns-track > column`, доля ширины — атрибут `width` колонки
  (`flex-grow`, по умолчанию 1); колонки встают в ряд или все в стопку по контейнерному запросу
  на ширину блока (< 24rem), без переноса «две плюс одна». В редакторе разделители — виджет
  поверх колонок: протяжка показывает доли сразу в стиле колонок и пишет их одной правкой при
  отпускании, стрелки на разделителе меняют долю на 5 % (не меньше 15 % пары). Боковой сброс:
  блок, брошенный у края блока корня или колонки, оборачивает их в колонки или добавляет колонку
  (не больше четырёх, вложенных колонок нет), `placeBeside` в ядре получает имена типов
  параметром. Сброс «к началу» требует увести указатель от точки захвата: ручка стоит у начала
  блока, и обычное вертикальное перетаскивание иначе создавало бы колонки. Бенчмарк на 10 000
  блоков 2026-10-16 — в пределах шума относительно HEAD без колонок (монтаж 0,83–0,86 против
  0,84 с, p95 набора 18 против 18 мс, кадр прокрутки 16,7 мс).

### Таблица данных (2026-10-16)

Решение пользователя: таблица в документе — это `NuiTable`, а не текстовая таблица с абзацами в
ячейках; данные живут в документе, типы колонок — текст, число, дата, флажок и выбор, вставка из
Excel, Google Sheets и Word создаёт такой же блок, опубликованный вид рисует `NuiTable`, а HTML —
обычную `<table>`.

- Модель — узлы, а не атрибуты: `table > table_head (table_column+ > table_option*) +
  table_body > table_row* > table_cell`. Колонка хранит `name`, `type` и `width`, варианты выбора —
  дети `table_option { label }`, ячейка — лист со значением `value` (строка, число, флажок или
  `null`; дата — строка `YYYY-MM-DD`), ячейки строки идут в порядке колонок (с 2026-11-11 ячейка
  несёт ключ своей колонки и порядок ячеек в строке ничего не значит — см. «Ячейки по ключу
  колонки» ниже). Так у строк, колонок
  и ячеек есть стабильные id, правка ячейки — один шаг `attrs`, а совместная правка в блоке E
  сможет разрешать конфликты по ячейке, а не по всей таблице. JSON-атрибуты (массивы в `attrs`)
  отвергнуты: каждая правка переписывала бы всю таблицу. Версия `contentSchema` поднята до 2.
- `NodeSpec.atom` — новое понятие ядра: узел с содержимым ведёт себя как лист для курсора.
  Backspace после такого узла сначала выделяет его, второе нажатие удаляет (у листа удаление
  сразу, как раньше); щелчок внутри выделяет самый внешний атом; без node view его разметка
  получает `contenteditable=false`; node view атома не получает `contentDOM` — всё внутри
  принадлежит виджету.
- `NodeParseRule.read(element, make)` — правило, которое строит содержимое узла из всего
  элемента целиком, без обхода детей; `tableGrid(table)` в ядре раскладывает `<table>` в сетку с
  учётом `thead/tbody/tfoot`, `colspan` и `rowspan`. Чтение таблицы: своя разметка
  (`nui-content__table-column--type-*`, варианты в `<datalist>`) читается без потерь; чужая —
  первая строка становится именами колонок, если в ней `th`, `thead` или только текст при
  следующих строках, иначе имена — буквы A, B, C; тип колонки угадывается по всем непустым
  значениям (флажок — TRUE/FALSE/ИСТИНА/ЛОЖЬ или `<input type=checkbox>`, число — с пробелами
  или запятыми групп и десятичной запятой, дата — ISO или `ДД.ММ.ГГГГ`), объединённые ячейки
  разворачиваются пустыми, оформление текста в ячейках теряется.
- `@numior/content`: `contentTableData(node)` читает таблицу в колонки и строки с запоминанием
  по узлам, значения приводятся к типу колонки (`cellValueOf`). `NuiContent` получил проп
  `views` — компоненты для типов узлов; без него таблица — обычная `<table>` без рантайма таблицы.
  Вид `NuiContentTable` с `NuiTable` (сортировка, фильтры, плашки вариантов выбора) лежит в
  отдельной точке входа `@numior/content/table`: `@numior/table` и `@numior/vue` — необязательные
  peer-зависимости, базовый бандл их не импортирует (проверка в `check-artifacts`, зона
  `content-table` в fallow).
- `@numior/editor-vue`: `tableBlock` входит в `editorBlocks`, его вид грузится по требованию
  (`defineAsyncComponent`, отдельный чанк), поэтому редактор без таблиц не тянет движок таблицы;
  у ещё не смонтированного вида виджет держит высоту-заглушку (иначе пустая коробка не попадала в
  `IntersectionObserver` WebKit). Правки ячеек, вставка, очистка и перетаскивание строк из
  `NuiTable` идут командами редактора (`setTableCells`, `insertTableRows`, `moveTableRow`…) —
  одна транзакция на действие; Ctrl+Z и Ctrl+Y внутри таблицы через `commands` таблицы зовут
  историю редактора, поэтому история одна. Меню колонки (`columnMenu` функцией): переименовать
  (поповер с полем у ячейки шапки), тип (смена типа приводит значения, для «Выбора» собирает
  варианты из значений), вставить колонку перед/после, удалить колонку. Контекстное меню ячейки:
  вставить строку выше/ниже, удалить строку. Кнопки «Строка» и «Колонка» под таблицей.
  Значение, набранное в ячейке выбора, которого нет в вариантах, добавляет вариант той же
  транзакцией. Ширины после протяжки пишутся в колонки одной правкой через 400 мс тишины,
  перестановка колонок переставляет колонку и ячейки каждой строки. Сортировка и фильтры по
  решению пользователя (2026-10-16) — часть документа: `sort` и `sortRank` у колонки,
  `table_filter { kind, op, text, min, max, from, to, exclude }` с детьми `table_value` для
  фильтра по набору (`exclude` — прятать названные значения); в редакторе изменение — одна правка истории, опубликованный вид и режим чтения
  применяют их же и не дают читателю ни сортировки, ни фильтров, ни меню колонок, ни ресайза и
  перестановки колонок: таблица выглядит так, как её оставил автор.
- Ячейки рисуются через реестр видов по типу колонки (`cells` у `NuiContentTable`,
  встроенные `contentCellViews`: флажок — `NuiCheckbox`, выбор — `NuiBadge`), а не отдельным
  шаблоном на каждый тип: вид получает `value`, `row`, `column`, `label`, `editable` и сообщает
  новое значение событием `change`, которое редактор превращает в правку ячейки. Свой вид для
  типа — одна запись в `cells`. Статичная
  `<table>` (HTML, `NuiContent` без `views`) показывает строки в порядке документа и без
  фильтров, а копирование таблицы через HTML не переносит сортировку и фильтры.
- Корень вида — сам `NuiTable` без обёрток и без своих стилей поверх него: прокрутка статичной
  таблицы — на её `<table class="nui-content__grid">`, поэтому рамка и фокус `NuiTable` не
  обрезаются. Куски документа (`content-visibility: auto`) получили поле `--_halo`, иначе их
  ограничение отрисовки срезало рамку выделения блока на всю ширину. В ките попутно: диапазоны
  ячеек не считали `[contenteditable="true"]` вне таблицы своим «интерактивным» элементом (в
  редакторе протяжка не работала), а ячейка под контекстным меню остаётся отмеченной, пока
  меню открыто (`nui-table--cell-menu`).
- Ограничения первой версии: удалить строку из контекстного меню можно по одной; варианты
  выбора нельзя переименовать или удалить (они растут из набранных значений и пересобираются при
  смене типа); вставка блока ячеек больше таблицы обрезается её границами, как у `NuiTable`.


### Декорации (C15, 2026-10-17)

- Плагин отдаёт `props.decorations(state) → DecorationSet` из основного входа ядра (без DOM):
  `inlineDecoration(from, to, class)` и `decorationSet(list)`, набор сортирован, пустые диапазоны
  и классы отброшены, `map(mapping)` растит декорацию набранным внутри текстом и убирает её
  вместе с удалённым. Обычно набор живёт в состоянии плагина и отображается шагами транзакции.
- Вид группирует декорации по текстовым блокам (смещения от начала содержимого блока, всё,
  что выходит за документ или не в текстовом блоке, отбрасывается) и рисует текстовый узел
  частями: `span`-контейнер, внутри — `Text` и `span` с классами сегментов. Дескриптор текста
  хранит `parts` вместо одного узла; перевод позиций (`posAtDOM`, `domAtPos`) идёт через части,
  чтение правки и так проходит сквозь вложенные элементы.
- У инлайн-декорации есть тег (`inlineDecoration(from, to, class, tag)`, `'span'` по умолчанию
  или `'mark'`; 2026-10-18). Сегмент, который накрывает хотя бы одна декорация с `mark`,
  рисуется `<mark>`, остальные — `span`. Подсветка комментариев (`commentAnchors`) идёт через
  `<mark>`: это выделенный по смыслу фрагмент, и скринридеры его так объявляют, а токены кода
  остаются `span`. Стиль комментария наследует цвет текста, чтобы `<mark>` не красил текст
  браузерным чёрным. Декорации живут только в отображении, в HTML документа их нет.
- Текст блока с декорациями не переиспользуется при сверке, а блоки, у которых сменилась
  подпись набора, после сверки перерисовываются целиком; соседние блоки не трогаются. Пока идёт
  композиция, новые декорации не применяются (перерисовка сорвала бы IME) и приходят со
  следующей транзакцией.
- Кроме абсолютных диапазонов, набор держит декорации, привязанные к блоку:
  `blockDecoration(id, from, to, class)` со смещениями внутри текста блока. Шаги их не трогают,
  поэтому перенос блока ручкой (для отображения это удаление и вставка) их не теряет; вид
  кладёт их в группу блока без `resolve` и отбрасывает, если блока нет или диапазон вышел за
  его текст. Подсветка кода живёт на них.
- Виджеты (C16): `widgetDecoration(pos, key)` в поле `widgets` набора называет место между
  блоками и ключ; элемент даёт сам вид через опцию `widget(key)` (основной вход ядра остаётся без
  DOM). После каждой сверки вид ставит элементы перед ребёнком контейнера с индексом позиции или
  после последнего (внутри куска корня, в цитате, колонке), несколько виджетов одного места — в
  порядке набора; места внутри текста отбрасываются, исчезнувшие ключи снимаются. Элемент
  получает `contenteditable="false"` и считается виджетом: мутации и события внутри него не
  читаются как ввод, позиции и сверка его пропускают, перерисовка контейнера после чужой мутации
  ставит виджеты заново.

### Блок кода (C15, 2026-10-17)

- Ввод: ```` ``` ```` превращает абзац в блок кода по пробелу или Enter, язык пишется сразу после
  (```` ```ts ````, в нижнем регистре); Enter внутри повторяет отступ строки; Enter на пустой
  последней строке и Mod+Enter откуда угодно выходят абзацем ниже; Tab и Shift+Tab сдвигают
  строку под кареткой или все выделенные строки (кроме строки, на начале которой выделение
  кончается) на два пробела; Backspace в начале пустого блока делает его абзацем.
- Подсветка: плагин `code-highlight` держит токены по блоку (диапазоны внутри его текста) и
  отдаёт их декорациями блока; набор внутри блока сдвигает диапазоны до нового ответа, перенос
  блока их не трогает. `createCodeHighlighter` после каждой смены состояния обходит только
  узлы, не совпадающие по ссылке с прошлым документом, и спрашивает подсветчик (проп `highlighter`, иначе из `createNuiConfig`) о
  блоках, у которых сменились текст или язык. Очередь блоков обходится кусками по 8 мс с
  уступкой хосту между ними, ответы куска приходят одной транзакцией только с мета (без
  истории и без изменения документа), плагин принимает ответ, только если текст блока тот же;
  до ответа старые токены отображаются шагами. Классы скоупов `nui-content__token--scope-*`
  красят `--nui-syntax-*`.
- Панель блока: ghost-кнопка с названием языка открывает поповер с `NuiCommand` (поиск по
  названию и алиасам, «Обычный текст» снимает язык, текущий язык отмечен галочкой и активен при
  открытии через `selected` у `NuiCommand`, поиск очищается при закрытии), фокус уходит в поиск по нативному
  `toggle` поповера и возвращается в текст после выбора; «Копировать» берёт текст блока. В
  чтении — подпись языка. Редактор отдаёт свой подсветчик блокам через `provideHighlighter`.
- Опубликованный вид — `@numior/content/code` (`NuiContentCode` на `NuiCode`: название языка
  из подсветчика шапкой, копирование, подсветка из конфига); без него блок остаётся `<pre>`.
  Блок кода не становится пунктом списка при переносе: пункт держит только абзацы и списки, а
  превращение в абзац теряло язык и строки, поэтому такой перенос отказывается (линии нет).
  Переключателя переноса строк нет: в редакторе код переносится всегда (см. выше про
  `scrollable-region-focusable`), опубликованный `NuiCode` прокручивается.
### Загрузки, файл и картинка (C16, 2026-10-17)

- Ядро: плагин `pendingUploads` держит ожидающие загрузки как пары id → позиция между блоками,
  позиции идут за шагами (вставка в ту же точку оставляет загрузку после вставленного), рисуются
  виджетами; `startUploads(ids, pos?)` ставит их (место по умолчанию — после текстового блока под
  кареткой, перед ним, если он пуст), `finishUpload(id, build)` одной транзакцией вставляет узел в
  ближайшее место, где схема его принимает (из пункта списка — после списка), `dropUploads` снимает
  без следа; `placeBlock(build, pos?)` вставляет блок по тем же правилам. Транзакции без шагов в
  историю не попадают, поэтому отмена и ошибка не оставляют следа, а успех — один шаг отмены.
- Вставка и перетаскивание: намерение `files` приходит, когда в буфере есть файлы и нет простого
  текста (у Excel и Word вместе с текстом лежит картинка-снимок — такая вставка остаётся текстовой).
- `@numior/content`: схема версии 3 — атом `file { url, name, size, type }` (только http(s) и
  относительные адреса; карточка-ссылка с `download`, иконка вида маской по типу и расширению,
  размер в байтах в `data-size`), у `image` ширина — доля строки 0,2–1 (`inline-size: N%` на
  `figure`, без ширины — натуральная, не шире строки), выравнивание `start | center | end` полями
  `margin-inline`, подпись ограничена шириной картинки (`contain: inline-size`). Адрес картинки —
  http(s), относительный или `data:image/{png,jpeg,gif,webp,avif}` (вставка из Word); `blob:` в
  документ не пускается: такой адрес умирает с вкладкой. Статический рендер файла пишет только имя
  (размер — данные в `data-size`), потому что у схемы нет языка страницы; размер выводят виды через
  общий `formatFileSize` из primitives. `@numior/content/media` (`contentMediaViews`) даёт
  `NuiContentFile` с размером по локали и `NuiContentImage`: картинка — кнопка, открывающая
  `NuiDialog size="auto" bare` с картинкой целиком (Escape, фон, крестик; фокус возвращается).
  `size="auto"` у `NuiDialog` — новая ширина кита «по содержимому, не шире экрана».
- Редактор: проп `upload` (`UploadAdapter<{ url }>` из primitives) плюс `accept` и `maxSize`;
  очередь — `useUploadQueue`, проверка — `validateFiles`, отказы и итоги объявляются в живом
  регионе. Карточка загрузки (превью картинки из object URL, имя, `NuiProgress`, «Отменить»; при
  ошибке «Повторить» и «Убрать») рендерится Teleport'ом в элемент виджета. Адрес попадает в
  документ только после ответа адаптера; без адаптера вставка файлов отказывается с объявлением,
  а «Картинка» и «Файл» из slash открывают поповер только со ссылкой (с адаптером — вкладки
  «Загрузить» и «По ссылке»). data:-адреса редактор сам не пишет. Ответ адаптера проходит проверку
  атрибута схемы; адрес, который схема не примет (например `blob:`), или узел, которого уже нет
  (замену удалили посреди загрузки), снимают загрузку с объявлением «загружен, но вставить некуда».
  В режиме чтения файлы из вставки и перетаскивания молча игнорируются. Выбор картинки и «Заменить»
  берут из `accept` потребителя только типы картинок (`image/*`, расширения картинок); если их нет,
  у «Картинки» остаётся только ссылка, а «Заменить» скрыт.
- Ручка блока: блок с `handle: 'beside'` (картинка) не сдвигается под ручку, если перед ним есть
  место — ручка встаёт вплотную перед ним (отступ `--nui-space-2` прямо в стиле ручки), видна при
  наведении на любую часть блока и следит за его размером (`ResizeObserver`, в том числе посреди
  протяжки ширины); если места нет, блок сдвигается как обычный, а картинка на время сдвига
  сжимается до строки. Ручка любого блока стоит у его верхнего левого угла (верх ручки — верх
  блока), без подгонки под первую строку или внутренний отступ; наведение на виджет блока показывает ручку этого
  блока, а наведение на элемент управления в виджете (кнопка языка, флажок задачи) ручку не
  трогает: иначе сдвиг блока под ручку уводил бы кнопку из-под указателя.
- Вид картинки: только угловые ручки (боковые убраны по решению пользователя 2026-10-17), размер
  меняется с сохранением пропорций: ведёт та ось, по которой указатель ушёл дальше (вертикальный
  сдвиг переводится в ширину через пропорцию картинки), в документе по-прежнему только доля ширины.
  Нижняя ручка у конца строки — `role="slider"` для клавиатуры (стрелки ±5 %, PageUp/PageDown ±10 %,
  Home/End — 20 и 100 %), остальные скрыты от чтения. Протяжка пишет ширину через `setStyle` и
  коммитит долю на отпускании, у картинки по центру размер меняется симметрично; ручки 24 px внутри
  углов, видны как уголки-скобки (рамка 3 px с двумя сторонами и светлым ореолом `drop-shadow`). Свободная высота с обрезкой не делалась: она потребовала бы атрибута высоты и выбора кадра. Панель — плавающий `NuiPopover`
  (`mode="manual"`, над картинкой у её конца, переворачивается вниз при нехватке места, всегда
  полного размера; на время протяжки скрыта) над выделенной картинкой —
  выравнивание (`NuiToggleGroup`), «Заменить» (загрузка с прогрессом поверх картинки, меняет `src`
  тем же узлом), «Скачать», «Описание» (поповер с полем alt); выравнивание и «Скачать» есть и в
  меню ручки. Подпись — `textarea` под картинкой с `field-sizing: content` (там, где его нет, высота
  подбирается по `scrollHeight`), коммит по Enter, потере фокуса или
  изменению; Enter заводит абзац ниже, Escape возвращает прежний текст.
- Вид файла рисует ту же карточку с размером по локали; щелчок по ней в режиме правки не уводит со
  страницы (Ctrl/Cmd+щелчок открывает).
- WebKit не сообщает `IntersectionObserver` о детях куска, пропущенного `content-visibility`,
  поэтому хост видов наблюдает ещё и сами куски: вид ядра сообщает о создании и удалении кусков
  через опцию `chunks` (`ChunkWatch`), появившийся кусок показывает все ждущие виды внутри;
  пустой виджет картинки держит минимальную высоту.
- Перерисовка декораций: вид сравнивает наборы декораций плагинов по идентичности и не
  пересчитывает группы, если наборы те же; блок, у которого группа сменилась, перерисовывается
  один раз (сверка детей для него пропускается). Подсветчик кода сбрасывает запрошенное при
  смене документа через `v-model` и при смене подсветчика, чистит удалённые блоки, после ошибки
  блок запрашивается снова, при размонтировании очередь останавливается; Shiki не кэширует
  неудачную загрузку.
- Виджеты: `EditorView.inWidget(target)` отвечает, лежит ли цель внутри виджета (клавиши
  редактора там не срабатывают); файл, брошенный на виджет, уходит в намерение `files` с местом
  после блока виджета, а не открывается браузером.
- Ожидающие загрузки держатся на границе блоков: если склейка или удаление уводят их позицию
  внутрь текста, она переносится за текстовый блок. Смена документа через `v-model` снимает все
  загрузки; повторная замена той же картинки отменяет предыдущую.
- Бенч 2026-10-17 на 10 000 блоков (Chromium, тот же генератор, теперь ~4 % блоков — картинки с
  живыми видами) против C15: набор p95 19,8 / 18,9 мс, Enter 32,5 / 20,9, отмена 23,1 / 26,2,
  вставка 500 строк 28,8 / 25,1, жирный по всему 453 / 437, холодный монтаж 1003 / 906, тёплый 907 /
  832, кадр прокрутки 16,7 / 16,7 — в пределах шума машины.
- Кит: у `NuiPopover` появился `padding="none"`, у `NuiCommand` — `embedded` (без своей рамки
  внутри поверхности поповера или диалога); правила кита, подгонявшие поповер под `NuiCommand`
  через `:has`, убраны, `NuiCommandDialog` использует `embedded`. Размеры списка языков задаёт
  обёртка редактора, а не стили `NuiCommand` снаружи. Фокус в панелях вставки и описания ставит
  нативный `autofocus` (шаги фокусировки поповера), без поиска полей по разметке кита.
- Отклонения от плана: вход называется `@numior/content/media` (картинка и файл вместе); «Описание»
  в меню ручки не дублируется (поповер привязан к панели), замена картинки там же; поповер вставки
  не имеет зоны сброса — файлы бросают прямо в текст.

### Встраивания и закладки (C17, 2026-10-17)

- `@numior/content`: узлы `embed { url, provider, caption }` и `bookmark { url, title, description,
  image, icon, site }` в схеме версии 3 (добавлены без смены версии: старые документы читаются как
  были). Адреса — только http(s), `provider` — короткое имя `[a-z][a-z0-9-]*`. В документе хранится
  исходная ссылка и id провайдера; адрес окна выводится заново при отрисовке
  (`resolveEmbed(url, providers, provider)`), поэтому чужой `src` в документ не попадает, а правило
  провайдера можно ужесточить задним числом. Пресеты `EMBED_PRESETS`: YouTube (через
  `youtube-nocookie.com`), Vimeo, Loom, Figma, Google Maps (только адреса `/maps/embed`), CodePen;
  каждый — `{ id, label, aspect, source(url) }`, свой провайдер устроен так же.
- Статический рендер встраивания — ссылка-заглушка с названием провайдера внутри `figure`
  (`renderContent` и HTML без окон), окно рисует только вид `NuiContentEmbed` из
  `@numior/content/media`: `iframe` с `sandbox="allow-scripts allow-same-origin allow-popups
  allow-presentation"`, `loading="lazy"`, `title` из словаря, пропорция провайдера; ссылку, которую
  разрешённые провайдеры не узнают, вид оставляет заглушкой. Закладка рендерится карточкой-ссылкой
  (заголовок, описание, сайт с иконкой, картинка) и не требует адаптера в опубликованном виде.
- Редактор: проп `embeds` — белый список (id пресетов и свои правила), без него встраиваний нет
  нигде: ни в slash, ни в меню вставки, ни в виде. Проп `linkMetadata(url, { signal })` →
  `{ title, description, image, icon, site }`; ответ пишется снимком в атрибуты узла без шага
  истории, «Обновить» на панели закладки запрашивает заново, устаревший запрос отменяется. Без
  адаптера закладка показывает адрес и домен.
- Опубликованный вид: `NuiContent` принимает тот же проп `embeds` с тем же значением по умолчанию —
  без него окон нет, встраивание остаётся ссылкой (2026-11-10, находка X9). Раньше вид играл все
  шесть пресетов, какой бы список ни был у редактора: адрес, вставленный в хранимый документ мимо
  редактора, открывал окно чужого сайта. Список доходит до `NuiContentEmbed` через
  `provideAllowedEmbeds` (`content/embed-context.ts`); явный проп `providers` у вида сильнее.
  Ломка: странице с плеерами нужен `embeds`.
- Вставка ссылки: голая http(s)-ссылка без HTML при выделенном тексте становится ссылкой на нём;
  иначе вставляется текстом-ссылкой, и если строка была пустой, у каретки открывается `NuiMenu`
  «Встроить {провайдер}» (только для разрешённого провайдера), «Закладка», «Оставить ссылкой».
  Выбор заменяет абзац блоком одной транзакцией (один шаг отмены), Escape и закрытие оставляют
  ссылку. «Встраивание» и «Закладка» есть в общем списке вставки (slash и меню «Вставить» на
  панели) с полем ссылки; панель встраивания отказывает адресу, который ни один разрешённый
  провайдер не узнаёт.
- Вид встраивания: поверх окна лежит крышка, пока блок не выделен и не в фокусе, — щелчок выделяет
  блок, а не уходит в чужой фрейм; у выделенного блока плавающая панель «Открыть ссылку» и
  «Показать закладкой». Вид закладки: карточка в режиме правки — не ссылка (щелчок выделяет блок),
  во время загрузки метаданных показывает заголовок-заглушку; панель «Открыть ссылку», «Обновить»
  (при адаптере) и «Встроить» (если провайдер разрешён). «Открыть ссылку» есть и в меню ручки.
  Подпись встраивания и картинки — общий компонент `NuiEditorCaption`.
- Ядро: нажатие на неинтерактивную часть виджета листа выделяет узел сразу, а DOM-выделение
  пишется только на отпускании кнопки (`ViewHost.holding`). Иначе Chromium, у которого нажатие
  попало в текст виджета, после `click` сбрасывал записанный диапазон узла в начало документа, и
  узел терял выделение; у картинки текста нет, поэтому раньше это не проявлялось.
- Листовые блоки до монтирования вида (виды монтируются лениво у экрана) держат в виджете
  статичную разметку схемы: имя файла, картинку, карточку закладки. Хост очищает виджет прямо
  перед монтированием, смена атрибутов до него перерисовывает запасную разметку. Раньше виджет
  был пустым, и блок файла (корень — `<a>`) за экраном оставался ссылкой без текста (axe
  `link-name`); заглушки высоты `:empty` у картинки, встраивания и закладки больше не нужны.
  Атом с дыркой (таблица) по-прежнему пуст до монтирования: его статичная разметка без строк.
- «Изменить ссылку» на панели встраивания и закладки открывает поле с текущим адресом; новый адрес
  проверяется тем же правилом, что и при вставке (встраивание — разрешённым провайдером), и пишется
  одним шагом отмены. У закладки при этом метаданные сбрасываются и запрашиваются заново (снимок без
  истории), подпись встраивания сохраняется.
- У закладки та же форма («Изменить закладку») правит заголовок и описание руками. Поля, которые
  автор изменил, пишутся в том же шаге отмены и не перезаписываются ответом адаптера после смены
  адреса; «Обновить» запрашивает метаданные заново и заменяет всё. Песочница берёт живые
  метаданные через публичный сервис microlink.io (переключатель «Метаданные из сети»; e2e
  выключает его и работает на фейковом адаптере).
- Выделение узла с видом (листовые блоки и атомы с виджетом) DOM держит внутри узла, а не вокруг
  него: Chrome перед обработкой клавиши приводит выделение к ближайшей редактируемой позиции и,
  если её нет (узел между двумя нередактируемыми соседями: закладка после картинки, файл перед
  таблицей), сбрасывает его в начало документа; WebKit для такого выделения не присылает
  `beforeinput`. Поэтому Backspace, Delete, Enter и символы при выделенном узле ядро обрабатывает
  на `keydown`; символ поверх выделенного блока заменяет его абзацем с этим символом на том же
  месте (инлайновые атомы — как раньше). Копирование и вставка, чья цель — статичная часть
  выделенного узла, идут через ядро; пока фокус в элементе управления виджета (поле адреса,
  подпись), ядро не пишет выделение в страницу.
- Панель ссылки — квадратные кнопки-иконки с подсказками, как у панели форматирования; у
  `NuiPopover` появился `size="auto"` (ширина по содержимому без минимума 8rem и потолка 20rem),
  чтобы панель из двух кнопок не получала пустой хвост.

### Конец документа и выход из контейнеров (2026-10-17)

- Enter при выделенном блочном узле (файл, таблица, закладка, картинка) вставляет пустой абзац
  сразу после него и ставит туда каретку; раньше каретка уходила к ближайшему тексту, часто далеко
  выше, и набор шёл туда. У инлайнового узла каретка встаёт сразу за ним, как раньше.
- Enter в пустой последней строке блочного контейнера (сворачиваемый блок, выноска, цитата)
  выносит строку за контейнер, если в нём остаётся что-то ещё; списки выходят по своим правилам,
  колонки не отпускают строку (схема не принимает абзац вне колонки).
- Backspace или Delete в пустой строке, которую не с чем склеить (рядом список, таблица, начало
  документа), убирают саму строку и ставят каретку в соседний текст; раньше строка оставалась.
- Диапазон удаления, который браузер передаёт в `beforeinput` (`getTargetRanges`), используется только
  внутри одного текстового блока; удаление через границу блоков решают команды ядра (склейка или
  удаление пустой строки). Раньше Chrome отдавал диапазон от конца пункта списка до пустой строки
  под ним, и удаление этого диапазона лишь переносило каретку, оставляя строку.
- Стрелки вверх и вниз с крайней строки текста, за которой идёт атом (статус задачи, файл, таблица,
  картинка), выделяют этот атом, а с выделенного атома — следующий атом или ближайший текст; раньше
  браузер перескакивал нередактируемый блок, и до него нельзя было добраться с клавиатуры.
- Щелчок сбоку от блока без текста (в пустую часть строки справа от карточки файла, закладки,
  таблицы) или в щель между такими блоками ставит каретку рядом с ближайшим по высоте блоком (см.
  «Каретка рядом с блоком без текста»). Раньше такой щелчок не попадал ни в один блок, и браузер сам
  ставил каретку: Chrome и WebKit — в начало документа, Firefox — в текст карточки; Enter после этого
  создавал пустые строки в начале документа.
- Щелчок под последним блоком ставит каретку в конец последнего текстового блока, а если документ
  кончается блоком без текста (таблица, файл, картинка) — каретку после него, и набор открывает
  строку ниже; если кончается контейнером (список), добавляет пустой абзац, поэтому
  в конце документа всегда можно продолжить; нижний отступ области правки
  увеличен до `--nui-space-8`, чтобы под последним блоком было куда щёлкнуть.

### Блоки без текста: одно правило для каретки (2026-10-18)

Проход по всем действиям рядом с атомами (картинка, закладка, встраивание, файл, разделитель,
таблица, статус задачи) в трёх движках нашёл разнобой: Backspace в начале строки удалял соседний
лист-атом сразу (файл, разделитель), а таблицу только выделял; стрелки и удаление выделенного атома
уводили каретку к ближайшему тексту через соседние атомы; в WebKit Delete в конце строки перед
атомом ничего не делал. Теперь одно правило (`commands/atoms.ts`, `selectionNear`):

- Backspace в начале строки после атома и Delete в её конце выделяют атом, ничего не удаляя; пустая
  строка при этом убирается. Второе нажатие удаляет выделенный атом.
- Удаление выделенного атома ставит выделение по направлению клавиши: на соседний атом, если он
  вплотную, иначе в ближайший текст (Backspace — назад, Delete — вперёд). Если это был последний блок
  контейнера (документ, колонка), на его месте остаётся пустой абзац.
- Стрелки с выделенного атома переходят на соседний атом по одному, а не перескакивают их.
- Backspace и Delete на краю текстового блока решаются на `keydown`, а не по `beforeinput`: браузеры
  по-разному ведут себя у нередактируемых соседей.
- Склейка через границу контейнера (2026-11-10, `commands/join.ts`). До правки Backspace в начале
  строки и Delete в её конце работали только с соседом того же родителя: строка после списка, цитаты,
  выноски, toggle или колонок и последняя строка внутри них на клавишу не отвечали (матрица
  «контейнер × клавиша × граница» — 30 мёртвых сочетаний из 48). Правило одно: текст течёт к
  ближайшему видимому листу в порядке документа. Лист-атом выделяется, как раньше. Текстовый блок
  справа отдаёт содержимое блоку слева и удаляется; каретка встаёт в место стыка. Пустой блок под
  кареткой просто убирается, сосед не меняется.
- Что остаётся после ушедшего блока, решает `removalOf`: родитель без него допустим — остаётся
  (toggle, чей заголовок ушёл, делает заголовком следующую строку); родитель опустел — убирается
  сам; иначе его остаток поднимается на уровень выше, при необходимости раскрытый на один уровень
  (пункт с вложенным списком отдаёт пункты наружу, две колонки, оставшиеся одной, становятся
  обычными блоками). В код строка переходит простым текстом (`plainText` узлов), в остальные блоки —
  без пометок, которые блок не принимает.
- Скрытое содержимое: свойство плагина `conceals(parent, index, state)` говорит ядру, что ребёнок
  не показан, и поиск соседа его пропускает. Блок редактора объявляет это полем `conceals`
  (`NuiEditorBlock`); toggle скрывает тело, пока свёрнут у этого читателя, — строка после него
  склеивается с заголовком, а не уходит в невидимый текст.
- Ограничения: поднятые узлы переносятся копиями в одном шаге замены (тот же класс, что этап 2
  шага `move`): чужая правка внутри них при перебазировании такой склейки теряется. Начало первого
  пункта списка и первой строки цитаты по-прежнему сначала поднимает блок (`liftAtStart`).
- Escape, который виджет листа-атома не обработал (ячейка таблицы, подпись, закрытый список статуса),
  выделяет сам блок; из таблицы выход ступенчатый — отмена правки ячейки, сброс курсора ячейки,
  выделение таблицы.
- `focus()` из контекста блока возвращает фокус в этот блок: если выделение стоит в другом месте, атом
  выделяется, а у блока с текстом каретка встаёт в конец. Раньше Escape из подписи картинки или
  выбор языка блока кода отправляли каретку в начало документа.
- Вставка, которая кончается атомом, выделяет его.
- Панели картинки, закладки и встраивания стоят внутри блока у верхнего угла (у картинки — левее
  угловой ручки), а не над блоком, где они закрывали строку выше.
- Нативная подсветка внутри выделенного блока скрыта целиком, видна только в поле с фокусом и во
  всплывающих панелях: подпись картинки больше не подсвечивается при выделении блока.

### Каретка рядом с блоком без текста (2026-10-18)

Пользователь: щелчок перед блоком или после него «по горизонтали» должен ставить курсор, а не
выделять весь блок; справа от статуса задачи и картинки есть место, но писать туда нельзя, а у блока
кода щелчок сбоку ведёт себя иначе. Решение — отдельный вид выделения
`{ kind: 'gap', id, side: 'start' | 'end' }`: каретка перед блоком без текста или после него, как
курсор у картинки в строке текстового редактора. В документе это граница между блоками; блок
адресуется по id, поэтому каретка переживает правки и историю.

- Щелчок по содержимому блока (картинка, карточка, список статуса) выделяет блок; щелчок в пустую часть
  его строки или сбоку от него ставит каретку с той стороны, где был щелчок. Содержимое — объединение
  видимых частей (текст, картинки, кнопки, поля, элементы с фоном или рамкой), а не коробка блока на всю
  ширину. Щелчок справа от текстовой строки (абзац, код) ставит каретку в конец этой строки сам, а не
  полагается на браузер: Firefox оставлял её в начале документа.
- Набор и вставка у каретки открывают строку с этим текстом рядом с блоком; Enter после блока открывает
  пустую строку под ним, Enter перед блоком — пустую строку над ним, каретка остаётся у блока.
- Backspace после блока и Delete перед ним выделяют блок, второе нажатие удаляет; Backspace перед блоком
  убирает пустую строку над ним, выделяет блок выше или переводит каретку в конец текста выше; Delete
  после блока — зеркально. Пустая строка, убранная Backspace/Delete рядом с блоком, оставляет каретку у
  блока, а не выделяет его. Удаление выделенного блока ставит каретку на его место: к соседнему блоку
  без текста или в соседний текст по направлению клавиши.
- ←/→ ходят «текст → перед блоком → после блока → следующий»; с выделенного блока стрелка снимает
  выделение на соответствующую сторону; Home/End — к началу и концу строки блока, Shift+←/→ выделяет
  блок. ↑/↓ на строку блока ставят каретку со стороны, ближней к её горизонтальной позиции, с блока —
  в текст по той же позиции.
- Вставка блоков из панели и меню «/» при каретке рядом с блоком ставит блок туда же; вставка, которая
  кончается блоком без текста, оставляет каретку после него.
- Отрисовка: DOM-выделение пишется внутрь блока (как у выделенного узла, иначе Chrome сбрасывает его в
  начало документа на нажатии клавиши), подсветка скрыта; каретка — `::after` блока с классом
  `nui-editor__gap` и координатами из свойств `--_gap-start`, `--_gap-top`, `--_gap-size`, мигает,
  только пока редактор в фокусе, без мигания при уменьшенном движении. IME и клавиатуры без кода клавиши
  (`Process`, `Unidentified`) сначала открывают пустую строку и переносят туда каретку, чтобы
  композиция шла в редактируемый текст.

### Картинки и файлы в строке текста (2026-10-18)

Пользователь после каретки рядом с блоками: текст, набранный справа от картинки, уходил под неё, а
место справа оставалось пустым — «контент как будто сгруппирован в столбик, а должен идти в строку с
переносом». Из трёх вариантов (обтекание и чипы, всё в тексте как в Google Docs, блоки и колонки как в
Notion) выбран «всё в тексте, как Docs».

- `contentSchema` версии 4: `image` и `file` — строчные атомы (`group: 'inline'`) внутри текстовых
  блоков, как упоминание. Пока идёт разработка, прежние версии схемы не поддерживаются и не
  мигрируются (решение пользователя 2026-10-18: «версии прошлые не нужно обрабатывать»). Вставка
  HTML с чужих страниц читает `<figure>` и `<img>`: строчная картинка на уровне блоков заворачивается
  в абзац, `figure` даёт режим «отдельной строкой».
- У картинки атрибут `wrap`: `inline` — в строке, стоит на ней нижним краем, строка растёт до её
  высоты (по умолчанию для вставки в текст); `wrap` — обтекание, картинка уходит к началу или концу
  строки (`float`), текст абзаца и следующих блоков идёт рядом и переносится; `break` — отдельной
  строкой с выравниванием по началу, центру или концу (по умолчанию, когда картинка вставлена в
  пустую строку). Подпись показывается в режимах `wrap` и `break`, в строке хранится, но не видна.
  Ширина — доля строки, как раньше. Разметка — `<span class="nui-content__image
  nui-content__image--wrap-* --align-*">`, чтобы картинка была допустимым содержимым `<p>`.
- Файл — чип в тексте (иконка, имя, размер) на базовой линии; после него пишется в той же строке. В
  редакторе выделенный чип показывает панель «Скачать» и «Открыть».
- Панель картинки: режим (в тексте, обтекание, отдельной строкой), выравнивание (для обтекания — начало
  или конец, для отдельной строки — ещё и центр), заменить, скачать, описание. Панель стоит внутри
  картинки у верхнего угла, если помещается, иначе над ней. Подсказки у всех кнопок.
- Загрузки и вставка по ссылке ставят узел в точку каретки, где начата загрузка (точка отображается
  через правки с ассоциативностью вправо, поэтому несколько файлов из одной вставки идут по порядку);
  если каретка не в тексте (рядом с блоком, выделен блок), узел получает свою строку. Карточка
  загрузки по-прежнему стоит между блоками после строки.
- Ручка блока сбоку от строки ставится только у строки, которая начинается картинкой «отдельной
  строкой» с выравниванием по центру или концу (место перед ней есть); `handle` в `defineBlock`
  принимает функцию узла. Раньше ручка мерила всю строку, решение «сбоку или со сдвигом» менялось от
  самого сдвига, и строка с картинкой с обтеканием дёргалась каждый кадр.
- Каретка рядом с блоком остаётся у блоков на всю ширину: таблица, закладка, встраивание, разделитель,
  свои блоки.

### Проходы axe, RTL и SSR (C24, 2026-10-18)

- `tests/e2e/editor-a11y.spec.ts` проверяет axe по секции редактора в светлой и тёмной теме при каждом
  открытом состоянии: меню над выделением, правка ссылки, цвета, меню «/», меню ручки, тоны выноски,
  языки кода, меню колонки таблицы, панель файла, каретка рядом с блоком, отмеченный комментарий,
  карточка неудачной загрузки и панель над клавиатурой на телефоне. Проход нашёл нарушение
  `scrollable-region-focusable` в ките: меню, ограниченное высотой экрана, прокручивалось, а его
  контейнер и пункты имели `tabindex="-1"`. У открытых `NuiMenu` и `NuiMenuSub` контейнер теперь
  `tabindex="0"` (Tab в открытом меню и так закрывает его), у закрытых — `-1`.
- `tests/e2e/editor-rtl.spec.ts`: в RTL картинка с обтеканием прижимается к правому краю строки,
  щелчок справа от закладки ставит каретку перед ней (начало строки справа), ← после выделенного
  файла ставит каретку за ним, ручка блока стоит справа.
- SSR: `NuiEditor` рендерит на сервере документ со всеми видами блоков (сгенерированные блоки,
  картинка с обтеканием, упоминание, файл-чип, закладка, встраивание, таблица) из JSON и из HTML,
  дважды одинаково, и гидратируется без предупреждений; `NuiContent` с видами медиа и таблицы тоже.
  Попутно: модульный кэш Vitest 5 (`node_modules/.vitest-cache`) хранит скомпилированный SFC по его
  собственному содержимому и не сбрасывается, когда меняется тип свойств в другом файле; устаревший
  вид без `focused` дал ложное предупреждение гидратации — локально кэш нужно чистить.

### Якоря комментариев и чужие транзакции в истории (C23, 2026-10-18)

- История пересчитывает свои записи при транзакции с `remoteChange` (чужая правка) или
  `addToHistory: false` честным rebase: записи идут от новой к старой, шаги каждой отображаются через
  цепочку «обратный исходный шаг → накопленное отображение → пересчитанный шаг», а позиции, которые
  обратный шаг стёр, восстанавливаются в его зеркальной паре (`history/rebase.ts`, как mirror в
  ProseMirror). Раньше все записи отображались одним отображением чужой правки, хотя старые записи
  отсчитаны от более старого документа, и после пары локальных правок отмена портила текст. Шаг,
  чей текст чужая правка удалила, выпадает; запись без шагов исчезает; выделение записи отображается
  той же цепочкой. Property-тесты: после отмены всех локальных правок вперемешку с чужими вставками в
  другой и в ту же строку остаётся документ с чужими правками.
- Цена пересчёта (2026-11-10). Цепочка росла на две карты с каждым шагом истории, поэтому чужая транзакция
  стоила квадрат числа шагов: 125 мс при 1000 шагах набора, 1,1 с при 3000. Три правки. Первая: запись,
  к которой присоединяется набор, склеивает обратные шаги через `mergeSteps` — серия набора, Backspace
  или Delete отменяется одним шагом (`mergeSteps` научился ставить вставку перед вставкой для серии
  Delete). Вторая: шаг без карты позиций (пометки, атрибуты, разметка) цепочку не удлиняет. Третья:
  плоскую замену, которой не касается ни одна карта цепочки, история не отображает, а сдвигает, и цепочку
  переносит за неё сдвигом диапазонов (`carriedPast`) — длина цепочки остаётся прежней; касание (включая
  соседство вплотную) оставляет прежний путь через зеркальные пары. После правок чужая транзакция стоит
  0,05–0,1 мс при любой истории; бюджетный сценарий: 50 чужих транзакций при 100 сериях набора —
  49,5 с на старом коде, меньше 150 мс.
- Позиция на границе восстановленного текста (2026-11-10). Позиция на краю диапазона зеркальной пары
  восстанавливается в паре, если относится к тексту пары: левый край — при привязке вправо, правый — при
  привязке влево. Раньше восстанавливались только позиции строго внутри, и запись, чей текст позже
  покрыло и вернуло своё же удаление, после любой чужой правки теряла шаг: «набрал ab, удалил abt, сосед
  написал в другой строке, отменил дважды» оставляло лишнюю букву. Случайная проверка «после отмены
  всего остаются только чужие вставки» на 18 000 сценариев: 1659 ошибок до правки, ноль после. Со
  встречными чужими удалениями остаётся около 0,1 % сценариев с лишней своей буквой (было 7 %) — когда
  сосед удалил часть набранного, а остаток покрыло своё удаление.
- `commentAnchors` — плагин ядра с именованными якорями вне документа: диапазон текста
  `{ kind: 'text', from, to }` или узел `{ kind: 'node', id }`. Якоря отображаются через каждую
  транзакцию (локальную, чужую, отмену): набор внутри расширяет диапазон, набор у краёв — нет,
  удаление сужает; якорь, чей текст удалён целиком, или узел которого удалён, остаётся с пометкой
  `lost` (как комментарий к удалённому тексту в Google Docs) и не подсвечивается. Команды `setAnchor(id, range?)` (по умолчанию выделение),
  `removeAnchor`, `activateAnchor`; `anchorsOf`, `anchorsAt(pos)`; для хранения снаружи —
  `anchorToJSON`/`anchorFromJSON` в виде id текстового блока и смещения в нём. Подсветка —
  инлайн-декорации `nui-editor__comment` и `--active` (не `nui-editor__anchor`: это класс служебной опорной точки всплывающих панелей). `NuiEditor` ставит плагин всегда; панель
  комментариев, адаптер и сохранение якорей — блок E (`@numior/collaboration`). В песочнице кнопка
  «Отметить выделение».
- Отмена возвращает якорю его текст (2026-11-10, находка E13). Раньше `lost` был липким: удалил
  комментированный текст, нажал Ctrl+Z — комментарий навсегда «Текст удалён»; частично удалённый
  якорь после отмены оставался урезанным. Отображение позиций этого вернуть не может: схлопнутый
  диапазон сам не растёт. Плагин ведёт память удалённого (`anchors/ghosts.ts`): каждое своё удаление
  оставляет в точке схлопывания запись — размер, текст, какие якоря и в каком месте оно задело, и
  какое действие истории его вернёт (обычная правка и повтор — отмена, отмена — повтор). Позже
  удалённое поверх запись не теряет: куски нового удаления встают вокруг неё в порядке документа.
  Вставка отменой или повтором сверяется с записями в своей точке: подряд идущие по времени записи,
  чей суммарный размер и текст равны вставленному (история склеивает серию Backspace в один шаг),
  считаются вернувшимися, якоря получают свои куски обратно, остальные записи встают на место внутри
  вставленного. Обычный набор и чужие правки записей не возвращают: тот же текст, набранный заново,
  комментарий не оживляет (иначе автор и соавторы видели бы разное). Чужие транзакции только двигают
  точки записей. Узловой якорь оживает, когда узел с его id снова в документе. Записей не больше 256,
  первыми уходят старые без якорей; обычная правка стирает записи повтора вместе со стеком повтора.
  Проверка: `anchor-undo.node.test.ts` — девять сценариев и свойство «после отмены всех правок якорь
  снова на своём тексте» со случайным набором, удалением, чужими вставками, отменой и повтором
  (20 000 сценариев при разработке). Цена на 1000 якорей: нажатие 0,39 → 0,51 мс. Ограничение: чужое
  удаление вокруг точки записи и его отмена оставляют запись не на месте — такой якорь своя отмена
  не вернёт.
- Свой буфер узнаётся по секрету, а не по метке (2026-11-10, находка X10). Метка
  `data-numior-editor="1"` была известна любой странице: чужая разметка с ней и с
  `<span data-user="…">@Имя</span>` вставлялась упоминанием выбранного человека. Теперь метка несёт
  случайный ключ из 32 шестнадцатеричных знаков; ключ лежит в `localStorage`
  (`numior-editor-clipboard`), поэтому вкладки одного origin узнают буфер друг друга. Без
  хранилища ключ живёт в памяти страницы — вставка из другой вкладки тогда идёт как чужая.
  Правило разбора с `own: true` (`NodeParseRule.own`) действует только для хранимой модели и своего
  буфера: `fromHTML(…, { foreign: true })` (так зовёт вставка) пропускает его, и узел читается
  следующим правилом или текстом. У схемы контента так помечено упоминание. HTML-модель
  (`format="html"`) считается доверенной, как и JSON. Альтернатива — подпись содержимого — не
  даёт большего: страница, читающая `localStorage` origin, уже внутри доверенной границы.
- Подпись изображения в строке не теряется в разметке (2026-11-10, находка X21). Вид `inline`
  подпись не показывает, и рендер её не писал — копирование, вставка и HTML-модель теряли атрибут.
  Скрытая подпись пишется в `data-caption` держателя изображения и читается обратно; видимая
  по-прежнему идёт элементом `nui-content__caption`.
- Выделенный текст перетаскивается мышью (2026-11-10, находка X18). Раньше вид отменял любой `dragstart`,
  и решения об этом записано не было. Теперь `dragstart` из выделения кладёт в перенос текст и разметку
  своего буфера (тот же путь, что копирование), а `drop` внутри того же вида — одна транзакция: вставка
  в точку сброса тем же намерением `paste` и удаление исходного диапазона, отменяется одним шагом. С
  зажатым Ctrl или Alt исходный текст остаётся. Сброс на само выделение ничего не меняет. `dragstart` не
  из выделения (ссылка, картинка) по-прежнему отменяется. Вид только для чтения отдаёт текст наружу
  копией и сам сбросов не принимает. `dragover` отменяется только для файлов: для текста браузер сам
  показывает каретку сброса в редактируемой области и не пускает сброс в нередактируемую. Сброс в другой
  редактор или программу — копия: исходный текст не удаляется, даже если получатель выбрал перенос (как
  в ProseMirror). Комментарий на перенесённом тексте теряется, как при вырезании и вставке; отмена его
  возвращает. Источник переноса — выделение состояния в момент сброса, поэтому чужие правки во время
  перетаскивания его не сбивают.
- Backspace у блока без текста с клавиатуры, не называющей клавиш (2026-11-10, находка X22). Android
  шлёт `keydown` с `key: 'Unidentified'`, и вид заранее открывает строку в зазоре у картинки, чтобы
  композиции было куда писать. Следом приходил `beforeinput deleteContentBackward`, удалял только что
  открытую строку и возвращал зазор: картинку из зазора стереть было нельзя. Теперь вид помнит зазор,
  открытый этим `keydown`; если удаление вернуло выделение в тот же зазор, оно выполняется ещё раз —
  уже как Backspace в зазоре (выбирает блок, следующий стирает). Проверено матрицей «каретка после
  картинки, зазор до и после, выбранный блок» × «путь keydown, путь beforeinput» на событиях в jsdom;
  на устройстве не проверено.
- Слияние строк браузером во время композиции (2026-11-10, находка X23). Во время композиции вид не
  отменяет `beforeinput`, и браузер может сам слить две строки. Раньше по её окончании текст второй
  строки дописывался в первую, а сама строка возвращалась из модели — текст двоился. Теперь наблюдатель
  DOM (`view/dom-change.ts`) перед чтением текста зеркалит слияние: строка, чей DOM исчез, а
  предыдущая строка осталась, сливается в модели тем же намерением, что Backspace в её начале; затем
  обычная разница текста. Текст и каретка читаются из DOM до правок модели, текстовые строки
  обрабатываются раньше контейнеров, после перерисовки контейнера выделение пишется в DOM заново.
  Воспроизвести в Chromium не удалось: `Input.imeSetComposition` с диапазоном через границу строк
  блоки не сливает; механизм подтверждён подменой DOM в jsdom. Нативный разрыв строки во время
  композиции так же не зеркалится — текст после каретки при нём теряется (не проверено на устройстве,
  пункт для прогона на Android).
- Чужая правка в строку с идущей композицией (2026-11-10, находка E20). Составляемого текста в модели
  нет, он живёт только в DOM. Раньше вид сводил текстовый узел к тексту модели: составляемый текст
  стирался, Chromium молча бросал композицию (её диапазон схлопывался) и начинал новую у каретки,
  которая после замены данных стояла не там — слово уезжало в начало строки. Если клавиатура
  фиксировала слово сразу, `compositionend` не приходил, вид оставался в режиме композиции и
  дальнейший набор не попадал в модель. Теперь `syncText` (`view/desc.ts`) переносит в DOM разницу
  между прежним и новым текстом модели, а не между DOM и моделью: непрочитанный текст остаётся на
  месте, правка до него ставится как есть, правка после него — со сдвигом на его длину, вставка ровно
  в его месте — после него (иначе она попала бы в диапазон композиции и была бы стёрта следующим
  обновлением IME). Место непрочитанного текста берётся с запасом — от общего начала до общего конца,
  посчитанных независимо. Правка, задевающая это место, идёт прежним путём: DOM сводится к модели,
  композиция срывается. Страховка в `view/input.ts`: `beforeinput` без `isComposing` и не
  композиционного вида при режиме композиции завершает её так же, как `compositionend`. Ограничения:
  срыв остаётся, когда чужая правка меняет пометки в составляемом узле, убирает последний текст
  строки или строка несёт декорации; страховка не срабатывает на `keydown`. Проверено в Chromium через
  `Input.imeSetComposition` (тот же путь, что у настольного IME) на восьми расположениях чужой правки;
  на настоящем IME и на Android не проверено.

### HTML через v-model и черновик формы (C21, 2026-10-18)

- У `NuiEditor` одна модель — `v-model`; проп `format` (`html` по умолчанию или `json`) выбирает, что
  она несёт. Компонент обобщён по значению модели, поэтому тип выводится из привязки (строка в
  поле формы, `DocJSON` для JSON), а запись идёт только значением того же вида, что уже привязано
  (без привязанного значения — вида из `format`). `v-model:document` убран (решение пользователя
  2026-10-18: «зачем 2 vmodel»). Модель обязательна: без неё у редактора нет документа. HTML обновляется через 300 мс после последней правки, сразу при уходе фокуса и
  когда форма собирает черновики перед проверкой (`useFieldControl({ commit })`, `NuiFormField`
  зовёт его при отправке), поэтому отправка прямо из набора получает свежую разметку. HTML,
  заданный снаружи, читается схемой (`fromHTML`) и заменяет документ; JSON пишется на каждую
  правку; собственное значение назад не читается.
- `toHTML` документа на 10 000 блоков стоит около 90 мс, поэтому ядро даёт `createHTMLWriter()`:
  разметка блоков верхнего уровня кешируется по неизменяемому узлу (`WeakMap`), после правки
  рендерятся только заменённые блоки, остальные берутся из кеша; результат совпадает с `toHTML`.
- Отклонение от плана: кусочной сериализации с эпохами и асинхронного `commitAll` нет — с кешем по
  блокам запись укладывается в один синхронный проход, и черновик формы остаётся синхронным.
  Вместо `requestIdleCallback` — пауза 300 мс после последней правки.
- Песочница: поле «О себе» на `NuiEditor` в форме регистрации; e2e проверяет отправку кнопкой и
  отправку скриптом, пока фокус в редакторе.

### Панель на телефоне (C22, 2026-10-18)

- На сенсорном экране (`pointer: coarse`) панель форматирования не висит сверху, а прижата к
  верхнему краю клавиатуры (`position: fixed`, отступ снизу — разница между `innerHeight` и
  `visualViewport`, пишется прямо в стиль панели по событиям `resize` и `scroll` видимой области;
  без клавиатуры — отступ безопасной зоны). Ряд кнопок прокручивается вбок, появление — сдвигом
  снизу через motion-токены. Решение пользователя: «над клавиатурой», как в Notion и Google Docs.
- Панель видна, пока правят текст: признак «правка» включает фокус самой области текста и гасит
  уход фокуса из редактора. Касание флажка или кнопки внутри блока панель не открывает — иначе она
  выезжала под палец между нажатием и отпусканием, и касание у нижнего края попадало на неё.
- Только в нижней панели есть «Сдвинуть влево/вправо» (`liftListItem`/`sinkListItem`): на
  телефонной клавиатуре нет Tab. Кнопки не забирают фокус (`mousedown` с `preventDefault`), поэтому
  клавиатура не закрывается.
- Если после правки каретка оказалась под панелью (браузер прокручивает каретку только над
  клавиатурой), страница докручивается на перекрытие; только при фокусе в тексте и только когда
  каретка действительно спрятана за панелью.
- Режим `toolbar="bubble"` на телефоне остаётся пузырьком; `none` — без панели.

### Упоминания (C20, 2026-10-17)

- Проп `mentions(query, { signal })` → `{ id, label, description?, avatar? }[]`. Без него «@» —
  обычный символ. «@» в начале строки или после пробела открывает список у каретки на общем
  подсказчике ядра (`createSuggestion`); запрос уходит через 150 мс после паузы в наборе, новый
  набор отменяет и таймер, и запрос в пути (`AbortController`), поздний ответ отброшенного запроса
  не показывается. Пока ответа нет, список показывает «Ищем…» (прежние результаты остаются до
  нового ответа), пустой ответ — «Никого не нашли», ошибка — «Не удалось загрузить людей».
- Клавиши: стрелки, Enter и Tab выбирают, Escape закрывает до следующего «@»; щелчок тоже выбирает.
  Выбор заменяет «@запрос» узлом `mention { user, label }` и пробелом после него, каретка встаёт
  за пробел. Пробел в запросе закрывает список.
- Enter и Tab, нажатые пока идёт поиск, не берут человека из прежнего списка на экране (2026-11-11): выбор
  запоминается и применяется к ответу этого поиска, как если бы ответ был мгновенным. Дальнейший набор, Escape,
  пустой ответ и ошибка выбор сбрасывают. Раньше «@ol» и Enter до ответа вставляли первого человека из списка
  для «@».
- Меню «/» и список людей — один компонент `NuiEditorSuggestMenu` (поповер у каретки, `NuiList`
  с `aria-activedescendant` на корне редактора). Аватар — `NuiAvatar` в новом слоте `leading`
  у `NuiList` (часть перед текстом пункта из `items`), скрытый от чтения: имя уже есть в пункте.
- Песочница: команда из шести человек с задержкой 300 мс.

### Команды над многими блоками (2026-10-21)

- Браузерный бенчмарк на 10 000 блоков ронял вкладку Chromium (`Target crashed`) на «выделить всё
  + жирный». Причина — не жирный шрифт, а пересчёт панели: на каждое новое состояние тулбар
  спрашивает команды без `dispatch`, какие кнопки выключить (списки, цитата, разделитель, уровни,
  с 2026-10-17 ещё меню «Вставить» — абзац, заголовки, блок кода). `setBlockType` строил
  транзакцию до проверки `dispatch`: на выделении «всё» — `replaceAround` на каждый из ~15 000
  текстовых блоков, каждый шаг копировал детей корня, строил индекс id нового документа и
  проверял корень схемой, а транзакция держала все промежуточные документы. Проба в Node: 500
  блоков — 0,26 с и 122 МБ, 2000 — 4,1 с и 2 ГБ; на 10 000 — нехватка памяти. Тот же рост ждал и
  настоящую команду «выделить всё → Заголовок».
- Правило: команда без `dispatch` только отвечает, применима ли она, и не строит шаги. Проверка
  выходит на первом подходящем блоке. `toggleMark` без `dispatch` отвечает, есть ли такая пометка
  в схеме.
- Шаг `markup { changes: { pos, type, attrs }[] }` меняет тип и атрибуты многих элементов за один
  проход: дерево копируется по путям к изменённым узлам один раз, содержимое изменённых узлов и
  их родителей проверяется схемой, id не трогаются. Размеры узлов не меняются, поэтому отображение
  позиций тождественное: выделение, якоря комментариев и история внутри блоков остаются на месте,
  как при `replaceAround`. Обратный шаг — `markup` со старыми типами и атрибутами; `mapStep`
  переносит позиции и выбрасывает удалённые элементы. `tr.setNodesMarkup(changes)` склеивает
  повторы одной позиции (последний выигрывает, атрибуты складываются). Им пользуются
  `setBlockType` (блоки, которые родитель не примет, пропускаются, как прежде; блок уже нужного
  типа считается применимым, поэтому `/текст` на абзаце удаляет запрос) и команды таблицы
  документа (`setTableCells`, `retypeTableColumn`) вместо цикла `setNodeAttrs`.
- `format="json"`: JSON документа считается один раз за изменение и уходит и в `v-model`, и в
  событие `change`. `activeMarks` пересекает пометки без `Set` на каждый текстовый узел.
- `Mapping.map` проходит диапазоны карт одной функцией модуля, без вызова метода-замыкания каждой
  карты: 1000 карт × 10 000 позиций — 63 мс в отдельном процессе вместо 100. В общем прогоне
  `bench:editor` эта операция с 2026-10-15 (`c5d9898`, код отображения не менялся) стоила 260 мс
  вместо 36: V8 оптимизирует горячий цикл по-разному в зависимости от операций до неё; после
  правки — 214 мс при пороге 250.
- Пороги `bench:editor`: «проверить команды панели на выделении всего документа» (1,6 мс, порог 25)
  и «сделать все текстовые блоки заголовками» (36 мс, порог 250). Браузерный бенчмарк снова
  проходит целиком (`bench/results/2026-10-21-docker-chromium.json`).
- Выделить всё и переключить жирный стало быстрее, чем 2026-10-15 (313 / 351 мс), хотя на каждое
  изменение с тех пор добавились панель, node views и синхронизация `v-model`: p50 275–305 / p95
  314–329 мс в двух прогонах (до правок ниже — 373–404 / 525–605). Профиль Chromium показал две
  лишние работы:
  - `placeInChunks` считал последний блок чанка стоящим не на месте (соседа справа внутри чанка
    у него нет, следующий блок — первый в следующем чанке) и переносил его. Когда менялись все
    блоки, цепочка переносов сгоняла 10 000 блоков в последний чанк, а `tidyChunks` удалял ~312
    пустых чанков и нарезал столько же новых. Теперь блок перед первым блоком следующего чанка
    стоит на месте; пересчёт стилей и раскладка на переключении упали с 10–12 до 1–3 мс, сверка
    вида — с 247 до ~160 мс.
  - `removeMark` обходил документ отдельно для каждого вида пометки схемы и сравнивал пометки
    через `JSON.stringify`; теперь один обход, только нужные виды, сравнение `sameMarks`: снятие
    жирного со всего документа — 34 мс вместо 134.
  - Порог `bench:check` для этой операции был p95 ≤ 700 мс (с 2026-10-21 — 100 мс, раздел ниже).
    Рост числа DOM-узлов между
    переключениями — мусор: после сборки число узлов не меняется (141 885 и после 4, и после 10
    переключений).

### Бюджет задержки 100 мс (2026-10-21)

- Правило: действие пользователя на целевых данных (10 000 блоков) доходит до нарисованного
  результата за 100 мс p95. Пороги `bench:check` стерегут цель, а не текущее медленное значение;
  долгие работы режутся на куски не длиннее кадра.
- Монтирование. Статичная копия `NuiContent` рисуется только на сервере (обёртка
  `nui-editor__server` с `display: contents`), на клиенте её больше нет: минус ~670 мс. Вид
  рисует первые 128 блоков корня сразу, остальные дорисовывает в простое кусками до 8 мс
  (`requestIdleCallback` с таймаутом 100 мс); высоту недорисованного хвоста держит распорка после
  корня. Позиция за нарисованной частью (`domAtPos`, переход Ctrl+Home/End, правка там) сначала
  дорисовывает всё; правка в начале документа продолжает дорисовку, если хвост не изменился.
- Скрытые чанки. Обновление вида не трогает блоки корня в чанках вне экрана: они попадают в
  `stale` и догоняются в простое кусками или сразу, когда чанк подходит к экрану
  (`IntersectionObserver` с запасом 200 % высоты). Жирный по всему документу перерисовывает
  только видимое.
- Новые id. Источник id состояния продолжает счёт после самого большого id исходного документа
  с тем же префиксом (`idSourceAfter`, документ сканируется при первом новом id) и запоминает
  номер каждого id, который шаг транзакции внёс в документ (вставка из другого документа с
  `n`-id выше начального не приведёт к повтору). Такому источнику транзакция доверяет: новый id
  не ищется в документе, а шаг `replace` получает множество выданных и ещё не размещённых id и не
  строит для них индекс id документа (10 мс на 10 000 блоков на каждый новый документ). Id
  из переданного снаружи источника (`ids` в опциях) и все остальные вставляемые id проверяются
  поиском по id (с 2026-11-12 — через предыдущий документ, без полного индекса).
- Проверка содержимого. Замена детей проверяется по состояниям автомата старого родителя
  (`matchesSplice`, кеш состояний на неизменяемый узел): автомат проходит вставленные узлы и идёт
  дальше только до схождения с прежним прогоном. Так работают команды (`wrapTextblock`,
  `setBlockType` с одним блоком) и шаг `replace` (общие начало и конец старого и нового
  содержимого сравниваются по ссылкам). `regionOf` и `doc.slice` ищут детей двоичным поиском.
- Холостые прогоны панели и меню «Вставить» на курсоре в свежем документе: 14–30 мс → 2,5–4 мс в
  Node; в браузере ~120 мс на монтаже → ~10 мс.
- Прочее: плагин подсветки кода хранит позицию каждого блока и отображает её через шаги вместо
  индекса id нового документа на каждой транзакции и не заходит в текстовые блоки, ища изменённый
  код; вид не сравнивает декорации, если наборы не изменились; поиск последнего текстового блока
  идёт с конца; `addMark`/`removeMark` ищут границы шага одним проходом без объекта на каждый кусок
  текста; пути в `fromJSON` и `check` — ленивая цепочка, массив строится только для сообщения об
  ошибке; записи спецификаций атрибутов кешируются.

### JSON после кадра и обходы без замыканий (2026-10-22)

- `toJSON` всего документа и событие `change` шли синхронно в обработчике клавиши: на «выделить всё
  + жирный» это ~7–10 мс до кадра. Теперь JSON собирается после ближайшего кадра, правки одного
  кадра дают одно значение и одно `change`; пауза HTML-модели (300 мс) стартует сразу, как раньше.
  Уход фокуса, отправка формы, снятие компонента и новый `editor.flush()` выдают отложенное
  значение немедленно; значение, пришедшее снаружи, отменяет отложенную выдачу.
- Перепись циклов на явные условия (d5dca43) сделала обход документа (`nodesBetween`) медленнее:
  замыкание `startOf` создавалось на каждый посещённый элемент и вызывалось трижды на ребёнка —
  ~19 мс на одно нажатие жирного по 10 000 блокам. Обходы (`visitRange`, `cutContent`, поиск
  текстовых блоков) снова считают начало ребёнка один раз за шаг, без замыканий.
- «Выделить всё + жирный» (Chromium, два прогона): 86 / 96–99 → 78–80 / 89–93 мс (p50 / p95).

### Смещения детей новых узлов (2026-10-23)

- Кеш смещений детей заполнялся заново для каждого нового узла: шаг внутри блока копирует путь от
  корня, и следующий `resolve` пересчитывал смещения 10 000 детей корня — O(n) на нажатие клавиши.
- Теперь новый узел получает смещения от старого. Замена одного ребёнка (`replaceChild`) сдвигает
  хвост на разницу размеров, при нулевой разнице массив общий. `spliceContent` берёт голову из кеша
  старого узла и досчитывает только вставленных детей и хвост. Начало после последнего известного
  ребёнка — его смещение плюс его размер, а не размер узла: в `size` элемента входят токены границ.
- Свойства в `properties.node.test.ts` сверяют выведенные смещения со свежими суммами после
  случайных шагов и сплайсов в пустой и заполненный узел.
- Чередующиеся прогоны с HEAD (три круга, p50): набор 1 000 символов 100–118 → 59–64 мс, обращение и
  применение 1 000 шагов 101–104 → 49–67 мс, отображение 10 000 позиций 197–225 → 105–113 мс;
  `resolve`, разбиение и «всё в заголовок» в пределах шума.

### Холодный монтаж (2026-10-23)

- Раскладка по меткам `performance.mark` в Docker Chromium (10 000 блоков, ~125 мс до кадра):
  чтение JSON ~30 мс, холостые прогоны команд панели 11–17, отрисовка закрытых меню панели
  (вставка, тип блока, цвета) 15–20, `reset` навигации панели 5–7, `createEditorView` ~7,
  первая подсветка кода ~4 плюс таймер после кадра, остальное — кадр и скрытые оверлеи.
- `fromJSON` проверяет узлы в том же проходе, что и читает: функции `check.ts` (личность, тип,
  атрибуты, форма, текст) остаются одной реализацией правил, путь для сообщений — стек индексов
  в контексте проверки вместо объекта на каждый узел. Порядок сообщений прежний: личность до
  детей, остальные проверки узла вставляются перед сообщениями детей. 10 000 блоков в node:
  первый вызов 51–61 → 29–36 мс, повторные ~37 → ~26.
- Шаг правки больше не сканирует всех детей родителя: `fitsEdited` берёт границы из области
  сплайса, а производные смещения детей записываются сдвигом и собираются при первом
  `childOffsets` (без изменения числа детей — копия и сдвиг на месте). Холостой прогон, который
  не разрешает позиции, не платит за хвост смещений.
- Выводятся смещения только у широких узлов (от 64 детей): жирный по всему документу менял
  ~15 000 текстовых блоков, и запись сдвига на каждом блоке (WeakMap, объект, мусор) подняла его с
  ~68 до ~95 мс в node; у блока с парой текстов дешевле досчитать смещения по запросу. Бенч ядра
  держит операцию «жирный по всему документу» под порогом 100 мс.
- Обход диапазона (`nodesBetween`) больше не строит смещения детей каждого посещённого узла:
  если диапазон начинается до содержимого узла, начало ребёнка копится суммой размеров, двоичный
  поиск нужен только узлу, внутри которого диапазон начинается. Жирный по всему документу в node
  52 → 42 мс.
- Кнопки основной и всплывающей панели делят одну подсказку (`anchor` с целями
  `.nui-editor-toolbar__action`); текст берётся из реестра кнопок (provide/inject, кнопка
  регистрирует свой элемент и действие), а не из DOM. Пятнадцать подсказок с поповером,
  позиционированием и слушателями заменены одной.
- Меню панели и ручки монтируются при первом открытии (`lazy` у `NuiMenu`), доступность пунктов
  «Вставить» считается только у открытого меню, первая подсветка кода ждёт простоя страницы.
- Чередующийся A/B с HEAD на загруженном хосте (12 холодных загрузок): холодный монтаж медиана
  143 → 105 мс, тёплое перемонтирование 73 → 45. Порог 100 мс на тихом хосте — в записи
  результатов бенча.

## Alternatives Considered

- ProseMirror, Tiptap или Lexical как основа отвергнуты планом 1.0; модель написана заново.
- DOM как источник правды без модели несовместим с совместной работой, историей и SSR без DOM.
- Id у текстовых узлов мешают слиянию и разрезанию текста на каждом вводе; якоря внутри текста
  строятся от id блока и смещения.
- Позиции-пути (массивы индексов) дороже отображать через шаги и сравнивать; плоские позиции и
  их отображение — основа шагов коммита C2.
- Проверка содержимого в фабрике удваивает работу при построении больших деревьев и мешает
  пошаговой сборке; проверка вынесена в отдельный вызов.

## Consequences

Точка входа `./view` — единственная с DOM: `check-artifacts.mjs` проверяет, что `.` и
`./fixtures` не трогают `document`, `window`, `navigator`, `Node` и `ResizeObserver`. Вид
проверяется в jsdom (разметка, переиспользование DOM, позиции), геометрия и ввод — в браузерах
вместе с C6–C8.

Появляются пакет `@numior/editor-core`, зона `editor-core` в fallow (зависит только от себя),
корень тестов `packages/editor-core/test` и строка в покрытии. Документ на 10 000 блоков из
генератора (больше миллиона позиций) строится и проверяется в unit-тесте за доли секунды;
бенчмарки ядра с порогами — коммит C3. Страница модели документа в доках ждёт блока F (список в
`docs-site.adr.md`).

### Проверка обёрток без транзакции (2026-10-24)

- Холостой прогон списков, цитаты и обёртки в блок (`toggleList`, `toggleWrapper`, `turnIntoList`,
  `wrapInBlock`) больше не строит транзакцию с шагом `replaceAround`: применимость проверяют
  чистые функции по документу (`wrapFits`, `listTypesAt`), и те же функции использует настоящий
  прогон, так что правило одно. Сценарий `blocks.node.test.ts` сверяет ответ холостого и
  настоящего прогона на каждом текстовом блоке трёх сгенерированных документов.
- Холодный монтаж редактора (20 загрузок): p50 94,2 → 92,7, p90 105 → 99 мс.

### Холодный монтаж — пять загрузок (2026-10-23)

- Холодный монтаж во всех браузерных бенчах (таблица, лист, дерево, редактор) меряется пятью
  загрузками страницы: первая — страница теста, остальные — в новых контекстах браузера (свой
  HTTP-кэш и кэш кода, поэтому каждая загрузка по-настоящему холодная). Порог сравнивается с p95
  по пяти пробам, то есть с худшей: одиночная проба болталась вокруг порога то в одну, то в
  другую сторону.
- С 2026-11-05 загрузок двадцать, p95 — 19-я по рангу (вторая худшая). При пяти пробах «p95»
  был максимумом, а максимум на общем хосте определяли пауза сборки мусора или граница кадра:
  первый кадр ждёт vsync, поэтому одна и та же работа даёт то 88, то 105 мс. Порог 100 мс не
  менялся, поменялась только оценка p95 (решение пользователя, как доля пропущенных кадров у
  колеса книги).

### Холодный монтаж без вынужденных раскладок (2026-11-05)

- Профиль CPU на несжатой сборке показал три вынужденные синхронные раскладки в хуках
  монтирования: прокрутка к активному пункту навигации списков, замер разделителей колонок и
  отступ под экранную клавиатуру. Каждая заставляла браузер разложить документ на 10 000 блоков
  до кадра.
- `useListNavigation.setActive` без фокуса откладывает прокрутку к пункту до следующего кадра
  (одна отложенная прокрутка на кадр), с фокусом прокручивает сразу; `NuiCommand` больше не
  держит своего наблюдателя за активным пунктом. Кадр переиспользует одну раскладку.
- Разделители колонок меряются из `ResizeObserver` и наблюдателя узла, без `onMounted`; отступ
  под клавиатуру не читает размеры окна, пока панель на телефоне выключена.
- Холостой прогон `insertBlock` (меню «Вставить» и slash) не строит транзакцию: `insertFits`
  проверяет вставку по автомату содержимого родителя с пробным id, а `tr.newId()` (обход
  документа ради наибольшего номера) зовётся только настоящим прогоном. Функции разметки блоков
  таблицы и колонок принимают `BlockMaker` (`doc.schema` и `newId`), поэтому один и тот же
  построитель питает проверку и вставку. Сценарий `blocks.node.test.ts` сверяет ответ холостого и
  настоящего прогона и следит, что холостой не читает `state.tr`.
- Проверка личности в `fromJSON` делает один поиск в наборе id вместо двух (`size` до и после
  `add`): чтение JSON 10 000 блоков 34 → 30 мс.
- Чередующийся A/B с HEAD (три круга по пять холодных загрузок, хост под нагрузкой): среднее
  102–107 → 94–98 мс, худшая проба 115–124 → 102–105.
- Окно от готовности данных до первого кадра по меткам `performance.mark` (медиана 12 холодных
  загрузок на тихом хосте, ~87 мс): чтение JSON со схемной проверкой ~31, рендер шаблона
  редактора и панели ~14, `createEditorView` ~8, дорендер после `ready` (закрытые оверлеи) ~7,
  остальное до кадра ~5, кадр (стили ~4, раскладка ~10, отрисовка) ~16. Вынужденных раскладок в
  окне больше нет.
- Панели ссылки и медиа создают содержимое при первом открытии (`lazy` у `NuiPopover`): дорендер
  после `ready` 7,3 → 5,6 мс. Остальные оверлеи стоят по 1–2 мс каждый (меню `/` — список и
  слой, ручка — кнопка, вставка — слой меню). `fromJSON` не пересчитывает размер узла, который
  только что посчитал сам (`checkBuilt` вместо `checkOwn`), и обходит атрибуты один раз.
  Итог в пределах шума: первый кадр привязан к vsync, и экономия в пару миллисекунд видна
  только тогда, когда работа перестаёт пересекать границу кадра.
- Закрытые оверлеи (ручка блока, меню `/` и `@`, пузырёк, вставка, загрузки, панели ссылки и
  медиа) монтируются при первом фокусе, движении указателя или `dragenter` над рамкой редактора, а
  не сразу после `ready`: дорендер ~5,6 мс уходит из окна холодного монтажа. С `autofocus` фокус в
  `onMounted` будит их в том же тике. Виды узлов по-прежнему монтируются по `ready`. Сценарий
  e2e ручки в RTL проходил впустую: наведение приходилось на блок вне окна, а заранее
  смонтированная ручка считалась видимой; теперь `hoverStart` прокручивает блок в окно, а `grip()`
  ищет ручку только у показанного блока.
- Чередующийся A/B с HEAD (три круга по 20 холодных загрузок, нагрузка хоста 5–7 от соседней
  системы на той же VM): в двух кругах p50 91,5 / 111,4 → 79,5 / 80,0 мс, p95 105,7 / 293 →
  93,1 / 94,3; в третьем обе стороны шумят одинаково (p50 98,0 / 97,8, p95 112,5 / 121,8).
  Записанный прогон того же кода сразу после — p50 95,8, p95 106,0: на таком хосте соседние
  прогоны расходятся на 15 мс в медиане, и порог 100 мс по p95 пока держится не в каждом прогоне.
- Холостые прогоны подъёма и сдвига пункта (`liftListItem`, `sinkListItem`), смены вида списка
  (`toggleList` поверх другого списка) и снятия обёртки (`toggleWrapper` внутри цитаты или выноски)
  тоже больше не строят транзакцию. Раньше при каретке в пункте списка на 10 000 блоков они стоили
  ~14,5 мс на каждое состояние: шаги на промежуточных документах заново строят индекс id всего
  документа (`indexTree` через `positionOf` в `keeps` преобразования и `idsFree` шага `replace`).
  Теперь применимость проверяет автомат содержимого затронутых родителей по исходному документу
  (`liftFits`, `sinkFits`, `relistFits`): для смены вида — подъём и обёртка в новый список у того
  родителя, в котором текстовый блок окажется после подъёма. Все холостые прогоны панели на пункте
  списка вместе — ~0,05 мс. Сценарий `blocks.node.test.ts` сверяет холостой и настоящий прогон
  всех команд панели на каждом текстовом блоке и падает, если холостой прочитал `state.tr`.
- Настоящие многошаговые правки на большом документе по-прежнему перестраивают индекс id на
  каждом промежуточном шаге (Tab в пункте списка на 10 000 блоков ~7 мс). Это в пределах бюджета;
  инкрементальный индекс — отдельная работа, если правки над многими узлами упрутся в него.

(`spliceContent`), а транзакция склеивает куски без пометки через границы блоков, пока между ними
нет куска, где пометка уже есть, — обратный шаг остаётся точным. `map` больше не создаёт объект
результата на каждую карту (120 мс вместо 170 на 10 миллионах отображений).

### Браузерный бенчмарк (C8, 2026-10-15)

`tests/bench/editor.bench.spec.ts` (`pnpm bench:browser`, проект `bench-chromium`, Docker
Playwright 1.63 на том же хосте, окно 1440×900): `NuiEditor` на странице
`/bench.html?view=editor&blocks=10000&seed=1` с документом генератора на `contentSchema`.
Задержка — от `keydown` до кадра после правки. Порог `bench:check` — p95 ≤ 100 мс для набора,
Enter и отмены; остальное записывается.

| Операция | Первый прогон, p95 | После доработки, p50 / p95 |
| --- | --- | --- |
| Холодное монтирование до первого кадра | 1051 | 864 / 864 |
| Набрать символ (200 нажатий) | 33 | 17 / 17 |
| Разбить абзац Enter (50) | 118 | 17 / 18 |
| Отменить шаг (100) | 86 | 17 / 18 |
| Вставить 500 строк | 3403 | 13 / 15 |
| Выделить всё и переключить жирный | 2070 | 313 / 351 |
| Кадр при прокрутке колесом | 67 | 17 / 17 |
| Длинные задачи при прокрутке | 92 шт. по ~56 мс | нет |

Что найдено замерами и как исправлено:

- Вставка простого текста разбивала блок на каждую строку и копировала 10 000 детей корня
  каждый раз; теперь это один шаг `replace` с открытым срезом.
- Правило отступов `.nui-content > * + *` заставляло Chromium пересчитывать стили соседей при
  каждой вставке блока, а запись выделения платила за пересчёт. Отступ теперь у каждого блока, у
  первого — ноль; свой цвет `::selection` убран.
- `content-visibility: auto` на каждом блоке стоил 12–17 мс за кадр прокрутки на внутренних
  пересечениях (`computeIntersections`). Вид кладёт блоки корня в чанки по 32
  (`nui-editor__chunk`, больше 64 — делятся, пустые убираются), и `content-visibility` с оценкой
  высоты стоит на чанке: целей пересечения в 32 раза меньше, а поиск по странице, дерево
  доступности и выделение работают, потому что блоки остаются в DOM. Поблочный `ResizeObserver` и
  кеш высот не нужны: `auto` помнит размер чанка. `posAtDOM` и `domAtPos` понимают точки внутри
  чанков. Стили отступов редактора повторяют правила контента для детей чанков.
- Пометка по смешанному диапазону делала шаг на каждый кусок без пометки (9 990 шагов, 1,8 с в
  ядре). Теперь одна операция — один шаг на весь диапазон; шаги пометок несут `skip` —
  промежутки, которые не трогаются, и обратный шаг перечисляет в нём куски, где пометка уже была,
  поэтому отмена точна. `mapStep` отображает `skip`, шаги со `skip` не склеиваются.
- Выделение «всё» через DOM делало все чанки «важными» для браузера, и Ctrl+A размечал весь
  документ (`setBaseAndExtent` 1,8 с). Теперь `all` живёт в модели: DOM-каретка стоит в начале
  документа, корень получает класс `nui-editor__all` (подсветка блоков, прозрачная каретка),
  копирование и вырезание всего текста идут через свой обработчик, стрелки уводят курсор к началу
  или концу, Backspace и Delete обрабатываются на `keydown` (WebKit не присылает `beforeinput`,
  когда каретка в начале документа). Если пользователь сам выделил весь текст мышью или меню,
  его DOM-выделение не трогается.

Остаётся: холодное монтирование 10 000 блоков (~0,86 с) — чтение JSON со схемной проверкой и
отрисовка всех блоков; жирный по всему документу (~0,3 с) — перерисовка всех блоков с новыми
обёртками пометок.

Подсветка кода (C15, 2026-10-17), тот же документ с Shiki-подсветчиком песочницы против
02d4587 без подсветки, p95 в мс: набор 18,9 / 35,3, Enter 20,9 / 19,5, отмена 26,2 / 19,1,
вставка 500 строк 25,1 / 22,5, жирный по всему документу 437 / 402, тёплое перемонтирование
832 / 892, холодное 906 / 915, худший кадр прокрутки 16,8 / 16,8. Первый вариант спрашивал
подсветчик обо всех блоках кода подряд и отправлял транзакцию на каждый ответ: тёплое
перемонтирование 1295 мс и кадр прокрутки 217 мс, пока Shiki разбирал документ; куски по 8 мс
с одной транзакцией на кусок убрали оба.

## Именованные наборы значений в ядре (2026-11-04)

`@numior/editor-core` не зависит ни от одного пакета, поэтому все его наборы строк — свои константы
`as const` в `*.types.ts` каталогов: дискриминанты модели и шагов (`ContentNodeKind`, `SelectionKind`,
`StepKind`, `InputIntentKind`, `TokenKind`, `RenderChildKind`, `DescKind`), причины отказов
(`StepFailure`, `DocIssueKind`, `DocJSONIssueKind = { …, ...DocIssueKind }`), а также платформенные
значения, которые вид сравнивает сам: `Key`, `InputType`, `Direction`, `CssKeyword`, `DomName` в
`view/view.types.ts`, теги и символы разбора `HtmlTag`, `HtmlChar` в `html/html.types.ts`, имя
текстового узла и токены выражений содержимого (`NodeName`, `ContentToken`, `SlotRule = { ...NodeSlots,
None }`) в схеме. Одинаковые по значениям наборы разных слоёв (`ContentNodeKind`, `HtmlNodeKind`,
`DescKind`) остаются разными константами: это разные деревья. Публичные константы модели, шагов,
выделения и ввода экспортируются значениями из `.`; правило ESLint `NAMED_ENUMERATIONS` включено
для `packages/editor-core/src`.

Пакет `@numior/content` (2026-11-04) держит те же правила: тоны, цвета, выравнивания, переносы, типы
колонок и фильтров документа — константы `NuiContent*` в `content/content.types.ts`, списки
допустимых значений схемы выводятся из них (`Object.values`), имена узлов и пометок схемы — в
`NuiContentNodeType` и `NuiContentMarkType` (по ним сравнивают редактор и свои блоки). Значения
разбора вставки и встраиваний (`ContentTag`, `ContentAttrValue`, `YoutubeUrl`, `UrlProtocol`)
остаются внутренними. Вход `.` не тянет `@numior/table`, поэтому наборы таблицы документа не
переиспользуют `TableSortDirection` и `TableTextOp`.

`@numior/editor-vue` (2026-11-04) сравнивает узлы и пометки через `NuiContentNodeType`, выделение и
ввод через константы ядра (`SelectionKind`, `ContentNodeKind`, `NodeSlots`, `BesideSide`), клавиши,
состояния поповеров, направление, тип указателя и статусы загрузок через primitives (`Key`,
`PopoverState`, `Direction`, `PointerType`, `UploadStatus`, `UploadReason`). Подмножества наборов
не заводят своих констант: `UploadKind`, `MediaKind` и `LinkKind` — члены `NuiContentNodeType`,
`ColourMark` — члены `NuiContentMarkType`. Свои константы пакета: `NuiEditorFormat`,
`NuiEditorToolbarMode`, `NuiEditorBlockPlace`, `NuiEditorHandlePlacement` (экспортируются значениями)
и внутренние `ToolbarItemKind`, `ToolbarGroupKey`, `SlashItemKind`, `DropTargetKind`, `DropEdge`,
`UploadTargetKind`, `MediaTab`, `GripSide`, `GripEdge`, `ImageActionKey`, `KeyCode`, `DomAttr`,
`CssDisplay`. Правило ESLint `NAMED_ENUMERATIONS` включено для `packages/editor-vue/src`.

## Декорации через несколько блоков

Строчная декорация режется на куски по всем текстовым блокам диапазона (`piecesOf` в `view/decorate.ts`).
Раньше она попадала только в первый блок, поэтому выделение участника на несколько строк рисовалось на одной.

## Размещение декораций по наборам (2026-11-11)

Вид раскладывает по блокам каждый набор отдельно и помнит результат (`rangesOf`, `anchoredOf` в `view/decorate.ts`).
Декорации, привязанные к блоку, размещаются один раз на набор. Диапазоны в позициях документа размещаются заново,
когда сменился корень документа. Блок с декорациями одного набора получает тот же массив, что и в прошлый раз, и
`changedBlocks` пропускает его без сравнения.

Раньше смена любого набора пересобирала все: один комментарий заставлял на каждое нажатие заново раскладывать
всю подсветку кода (100 блоков по 300 токенов — 9,9 мс, теперь 0,06 мс).

Договор для плагинов прежний: тот же объект набора означает то же размещение. Набор с декорациями блока, который
плагин не заменил после правки этого блока, остаётся как был и режется по длине текста при отрисовке.

### Декорации блоков по блокам (2026-11-12)

Остаток прошлого раздела: набор текста в блоке кода всё равно пересобирал подсветку всех блоков кода. Плагин строил
из всех токенов новый плоский набор, вид раскладывал каждую декорацию заново и сравнивал блоки строками подписей:
300 блоков кода по 280 токенов — 50 мс на нажатие с перекраской (два набора), 100 блоков — 9 мс без перекраски.

- `DecorationSet.blocks` — карта «id блока → декорации» (`BlockDecorationGroups`). `decorationSet(…, blocks)` с
  плоским списком группирует его сам; `blockDecorationSet(groups)` берёт готовые группы и хранит их массивы как есть.
- Вид раскладывает группу один раз на пару «массив группы + узел блока» и отдаёт тот же массив, пока ни группа, ни
  узел не сменились: `changedBlocks` пропускает такие блоки без подписей.
- Плагин подсветки держит у каждого блока готовый массив декораций и при наборе меняет только массив правленого
  блока; набор собирается из массивов за число блоков, а не токенов.

Замер (Node, без DOM): нажатие с перекраской в одном из 300 блоков — 50 мс → в пределах кадра (сценарий
`code-highlight.node.test.ts`, красный на старом коде); 100 блоков без перекраски — 9,0 → 0,5 мс (p95 16 → 2,6).
Ломка API ядра: `DecorationSet.blocks` — карта вместо массива.

## Кто вправе дорисовать документ (2026-11-11)

Холодный монтаж рисует первые 128 блоков, остальное — в простое. Запрос позиции в DOM (`domAtPos`, `coordsAtPos`)
дорисовывает остаток сразу: так ведут себя каретка, выделение и навигация самого редактора.

Наблюдатели так делать не должны. Каретка участника в конце длинного документа заставляла рисовать весь документ
синхронно при первом же замере. У вида есть `drawn(pos)` — нарисован ли блок позиции — и `draw(pos)`.
`NuiEditorApi.coordsAt` отвечает `undefined` для места, которое ещё не нарисовано; слой кареток прячет такую каретку
и ставит её, когда блок появится (он перемеряет на изменения DOM редактора). `revealNode` — явный переход к блоку —
сначала дорисовывает документ; раньше показ блока из нерисованной части ничего не делал.

## Таблица документа: ячейки по ключу колонки (2026-11-11)

Аудит (P4, P6): ячейки строки стояли в порядке колонок. Правка колонки была шагом на каждую
строку — 1,5 с на 1000 строк, каждый шаг заново строил индекс id всего документа. Одновременные
правки сходились к рваной таблице: значения новой строки оказывались под чужими колонками.

- Колонка несёт `key` (непустая строка, своя в пределах таблицы), ячейка — `column` с этим ключом.
  Порядок ячеек в строке не имеет смысла; у строки может не быть ячейки колонки (значение `null`).
  Если у строки две ячейки одной колонки, действует последняя. Ячейка без колонки не показывается.
- Вставка, удаление и перестановка колонки — один шаг в `table_head`. Строки при этом не
  меняются: у новой колонки ячеек нет, ячейки удалённой остаются в строках невидимыми и
  возвращаются с отменой удаления. Первая запись в отсутствующую ячейку вставляет её в конец строки
  (вставки идут от конца документа к началу, позиции считаются один раз).
- Новая строка и разобранная из HTML таблица получают ячейки всех известных колонок: запись в них —
  шаг `attrs`, и спор двух людей за одну ячейку по-прежнему даёт «перезаписанное значение».
- `NodeSpec.renderSubtree(node)` — новое понятие ядра: узел сам отдаёт разметку всего поддерева
  для HTML и опубликованного вида (`renderTree`); `render` с дырой остаётся для вида редактора.
  Таблица рисует `<td>` в порядке колонок; текстовая версия для буфера — так же.
- Ключ новой колонки — свежий id транзакции (у участников общей правки id с разными префиксами),
  ключи разобранной таблицы — `c0`, `c1`… Схема фикстур ядра переведена на ту же модель.
  Версия `contentSchema` поднята до 5.
- Замер (1000 строк × 10 колонок): вставка колонки 1493 → 9 мс, удаление 1500 → 0,3 мс,
  перестановка 1496 → 2,3 мс, один шаг вместо тысячи; заполнение новой колонки на 1000 строк —
  27 мс (1000 вставок), на 5000 строк — 233 мс.
- Ограничения: первая запись двух людей в одну ячейку колонки, добавленной позже строки, даёт две
  ячейки — видна последняя, записи о перезаписанном значении нет. Ячейки удалённых колонок не
  вычищаются. Одновременное удаление двух последних колонок оставляет одну: второй шаг отклоняет
  схема.
- Отвергнуто: общий шаг «правка колонки» в ядре (ядро узнало бы о таблицах) и значения ячеек
  атрибутами строки (правка двух ячеек одной строки стала бы спором за один атрибут).

## Шаг move

Решение 2026-11-10 (аудит, находка E1). Перенос блока был шагом `replace` над участком между старым и новым
местом, в срезе которого лежали копии узлов на момент команды. При перебазировании над чужой правкой копии
оказывались старее документа: блок, вставленный участником между переносимыми, пропадал у всех; удалённый
блок возвращался; хвост разрезанного абзаца терялся. Эвристика `withLatestNodes` закрывала только набор текста.

- Шаг `{ kind: 'move', from, to, target }`. Диапазон `from..to` — целые соседние узлы одного родителя,
  `target` вне диапазона. Отказы: `range` (пустой диапазон, цель внутри или на краю диапазона, выход за
  документ), `depth` (края диапазона в разных родителях), `content` (родитель не может отдать или принять узлы).
- Применение (`transform/move.ts`, `applyMove`) — обмен двух соседних участков `low..mid` и `mid..high` на
  уровне токенов ближайшего общего предка. Узлы не копируются: объекты и `id` те же, меняются только предки
  на пути.
- Карта позиций — свой вид `StepMap` (`kind: 'move'`, `createMoveMap`): позиция внутри участка едет с ним,
  ничего не удаляется. На границе сторону выбирает `assoc`. Карта обратима точно.
- `Mappable.mapSpan(from, to)` отображает диапазон целиком и отвечает `undefined`, если перенос разорвал его
  (края оказались в разных участках обмена). `mapStep` такой шаг отбрасывает: удаление или пометка не должны
  задеть то, что автор не выделял. Диапазон, целиком накрывающий обмен, остаётся на месте. `mirrored` ведёт
  оба края вместе; одинокий край, который пересекает карту переноса, пока второй перепрыгнул зеркальную пару,
  тоже считается разрывом.
- `mapStep` для самого `move`: диапазон через `mapSpan`, цель с `assoc` −1 при переносе назад и +1 при
  переносе вперёд (цель держится за соседа, которого перенос не проходил). Шаг исчезает, если блок удалён,
  цель удалена или перенос стал пустым. Обратный шаг — перенос обратно, `mergeSteps` переносы не сливает.
- Команды: `moveChild` — один шаг `move`. `moveBlock` между контейнерами — шаг `move`, когда узел переезжает
  как есть: без преобразования в пункт списка, без слияния соседних списков и когда исходный родитель остаётся
  допустимым. Остальные случаи — см. «Перенос блока с преобразованием» ниже. Строки и колонки таблицы документа
  (`moveTableRow`, `orderTableColumns`) переносятся шагами `move`.
- Перенос блока с преобразованием (2026-11-12, `moveBlock`, `placeBeside`). Раньше итоговое дерево
  записывалось одним `replace` над всем участком между старым и новым местом, с копиями всех блоков на пути:
  Enter соседа в переносимом или в любом попутном блоке терял половину абзаца у всех (`withLatestNodes`
  спасал только набор текста). Команда по-прежнему сначала строит итоговое дерево (`rebuilt`), а затем ведёт к
  нему документ шагами, каждый из которых оставляет документ допустимым:
  - части, которые переезжают как есть (сам блок; дети пункта, сменившего вид списка; пункты списка, влитого в
    другой список), идут шагами `move`. Новой обёртке (пункт вокруг абзаца, список вокруг пункта) сначала
    вставляется оболочка с временной пустой строкой, блок переезжает в неё, строка удаляется. Родитель,
    который без блока недопустим, получает временную пустую строку до переноса. Заголовок становится абзацем
    шагом `markup` на месте;
  - остаток до итогового дерева снимает разбор деревьев (`commands/tree-edits.ts`): по одному шагу на каждое
    место, где дети отличаются; узел, чьи дети остаются на его месте, снимается `replaceAround` с зазором.
    Шаг, вставляющий узлы, которые удаляет другой шаг, идёт после него;
  - результат сверяется с итоговым деревом; не сошлось или шаг не прошёл — тот же разбор без переносов
    (блоки на пути уже не задеты), затем прежняя одна замена.
  Замер на 17 289 случайных переносах между контейнерами: с копиями существующих узлов осталось 4 (единственный
  абзац колонки сразу за свои колонки), было 3410.
- Следствия для итогового дерева: пункт, сменивший вид списка (маркированный ↔ задачи), получает новый `id` —
  его дети переезжают со своими `id`; при слиянии перенесённого списка со следующим за ним списком остаётся
  существующий список (раньше оставался перенесённый или новая обёртка, и следующий список терял `id`).
- Ограничение: шаги одной пачки перебазируются по одному. Если чужая правка сорвала шаг уборки, в документе
  остаётся временная пустая строка или пустая оболочка — видимый след вместо потери текста.
- Склейка строк через контейнеры (2026-11-12, `commands/join.ts`) узлы и текст не копирует. Раньше правая
  строка удалялась, а её текст вставлялся копией в конец левой: набор соседа в правой строке пропадал, набор в
  конце левой вставал после приклеенного текста. Три способа по порядку, первый применимый:
  - строка, чьё удаление ничего больше не меняет, переезжает шагом `move` сразу за левую строку и склеивается
    с ней удалением границы (`replace` двух токенов) — как соседние строки;
  - иначе содержимое правой строки переезжает шагом `move` в конец левой, затем уборка: опустевшая строка и
    контейнеры, которые без неё недопустимы, снимаются одним `replaceAround` с зазором — остатком (вложенные
    пункты, вторая колонка), либо простым удалением, когда остатка нет;
  - прежний шаг с копией остаётся для строки с узлами не-текстом, которая вливается в блок кода (перенос и
    упоминание там становятся текстом), и для остатка из нескольких несмежных кусков.
  Пометки, которых левая строка не принимает, снимаются шагами `removeMark` до переноса.
- Свой шаг после своего `move` (2026-11-12). Диапазон шага, записанного после собственного переноса в той же
  пачке (граница склейки стоит на краю перенесённой строки), обратная карта переноса разрывает, а перенос после
  чужих шагов собирает снова. `mirrored` ведёт такие края поодиночке от обратной карты переноса до её пары;
  если перенос при перебазировании пропал (пары нет), зависимый шаг отбрасывается, как раньше.
- Известные края склейки под чужим набором: текст, набранный ровно в конце правой строки, остаётся в её
  оболочке и удаляется с ней, когда строка не переезжает целиком (второй способ); набранный ровно в конце левой
  строки при втором способе встаёт после приклеенного текста. Разрез правой строки соседом (Enter) второй
  способ отменяет: перенос содержимого отбрасывается, строки остаются как есть, текст цел.
- Списки и обёртки (2026-11-11, находка P3). Команды уровня блока узлы не копируют:
  - пункт из списка наружу — один `replaceAround`: зазор — содержимое пункта, срез закрывает список перед ним и
    открывает новый после (край среза открыт, когда с этой стороны остались пункты);
  - вложенный пункт на уровень выше — `replaceAround`, который убирает следующие пункты во вложенный список
    внутри поднимаемого, затем `replaceAround`, закрывающий вложенный список и родительский пункт перед ним.
    Если за вложенным списком в родителе есть абзацы, пункт уезжает за родителя шагом `move`; единственный
    пункт вложенного списка сначала пропускает эти абзацы вперёд (`move`), потом поднимается;
  - пункт под предыдущий (Tab) — один `replaceAround`: зазор — сам пункт, срез продолжает предыдущий пункт;
  - первая строка из цитаты или выноски — `move` перед обёрткой, единственная строка — снятие обёртки;
    пустая последняя строка за обёртку — `move`.
  Раньше подъём вставлял копии и удалял оригиналы: набор соседа в пункте и в пунктах после него пропадал, а
  поднятые блоки получали новые `id` (комментарии и присутствие по `id` слетали). Вложение держалось на
  `withLatestNodes`.
- Проверки: `editor-core/test/move-step.node.test.ts`, `collaboration/test/moves.node.test.ts` (обе очерёдности
  доставки, отмена, два одновременных переноса), свойство «буквы не теряются при переносах и разрезах» в
  `collaboration/test/convergence.node.test.ts`, `editor-vue/test/table-moves.node.test.ts`,
  `collaboration/test/lists.node.test.ts` (подъём, вложение, выход из цитаты под чужим набором).

## Шапка: вставка и тип блока (2026-11-11)

Запрос пользователя: пункты меню «+» отключались без объяснения, списка блоков много, селект типа блока
в шапке лишний, заголовков три уровня вместо шести, разделители вокруг «+» мешают.

- Причина «мёртвых» пунктов: меню «+» запускало те же команды, что и меню `/`, — преобразование блока под
  кареткой. В заголовке нельзя начать список, в пункте списка — почти ничего. Теперь «+» вставляет:
  `insertBelow(command)` в ядре (`commands/below.ts`) открывает пустую строку под блоком каретки и выполняет
  команду в ней, одной транзакцией и одним шагом отмены.
  - Место строки ищется от блока каретки наружу: первая позиция, где строка допустима и команда в ней
    выполнима. Позиции внутри пункта списка пропускаются — из пункта блок встаёт под всем списком.
    Позиции, которые скрывает плагин (`conceals`, тело свёрнутого toggle), пропускаются.
  - Пустая строка под кареткой вне списка не дублируется: команда выполняется в ней, как в меню `/`.
  - Выделенный блок без текста, несколько блоков, ячейки таблицы и весь документ — строка после конца
    выделения; зазор у блока без текста — команда на месте или строка в зазоре.
  - Список сразу под списком того же вида сливается с ним (поведение `toggleList`): «+ → список» из пункта
    добавляет пункт в конец.
  Меню `/` по-прежнему преобразует строку, в которой набрано.
- Меню «+» — поповер с `NuiCommand` (поиск сверху, стрелки и Enter из поля). Совпадение — одно правило с меню
  `/` (`matchesSlash`: подпись содержит запрос или ключевое слово с него начинается). Запрос сбрасывается при
  закрытии. `NuiPopover` отдаёт `triggerElement` (как `NuiMenu`; до 2026-11-11 — `trigger`, имя совпадало с пропом `trigger` поповера, и справочник документации его не видел) — кнопка «+» остаётся пунктом панели с одной точкой
  табуляции.
- Тип блока (текст, заголовки, код) переехал в панель над выделением. В шапке меню типа остаётся, когда панели
  над выделением нет: режим `fixed`, сенсорный экран (панель у клавиатуры). Опция `blockMenu` у
  `toolbarGroups`.
- Группы шапки: документ («+», отмена, повтор), пометки, действия приложения, структура, отступы (только у
  клавиатуры). Разделителей вокруг «+» нет: он первый в группе с историей.
- Заголовков шесть уровней: `CONTENT_HEADING_LEVELS`, `NuiContentHeadingLevel` в `@numior/content`; правило
  набора `#`…`######`; кегли 4–6 — `lg`, `md`, `sm` (шестой приглушённым цветом). Версия схемы не менялась:
  прежние документы остаются допустимыми.
- Отвергнуто: подсказка «почему недоступно» у отключённого пункта (объяснять пришлось бы почти каждый пункт
  в списке и коде); скрытие недоступных пунктов (меню меняло бы состав от места каретки).
- Проверки: `editor-core/test/below.node.test.ts`, `editor-vue/test/slash.test.ts`, `overlays.test.ts`,
  `toolbar.test.ts`, `tests/e2e/editor.spec.ts`, `editor-a11y.spec.ts`.

## Слои поверх текста узнают о сдвиге вёрстки от редактора (2026-11-11)

Замечание пользователя (U7): каретка участника оставалась на 40 px правее текста, когда якорь перетаскивания
прятался и строка возвращалась на место. Тот же дефект был у рамки выделения, к которой привязаны меню над
выделением, панель ссылки и форма комментария (39 px), и у поповера ветки комментария. Все три слоя мерили
место текста по своим поводам (правка документа, присутствие, прокрутка) и не знали о сдвиге строки без
правки: якорь толкает блок сменой класса с переходом отступа.

Повод один на редактор: `useLayoutWatch(frame, content)` и метод ручки `NuiEditorApi.watchLayout(listener)`
(возвращает отписку). Слушателей зовут в кадре, когда текст мог сдвинуться:

- в тексте сменились `class`, `style`, `dir`, `hidden`, `open` или сам текст; в редакторе появился или исчез
  узел (панель инструментов над текстом);
- изменился размер области текста; загрузилась картинка или вставка (`load`); загрузились шрифты страницы;
- начался переход или анимация (`transitionrun`, `animationstart` — в том числе по наведению, без смены
  разметки). Пока в тексте идёт конечная анимация (`getAnimations({ subtree: true })`), слушателей зовут
  каждый кадр: слой стоит у текста на всём пути перехода. Бесконечные анимации цикл не держат.

Наблюдатель атрибутов смотрит только область текста: слои лежат рядом с ней и пишут свои `style`, не будя
друг друга (наблюдатель на корне редактора дал бы бесконечный обмен кадрами между слоями). Без слушателей
кадр не заказывается. Прокрутку каждый слой слушает сам, как раньше.

Подписаны: рамка выделения редактора (`use-editor-overlays.ts`), слой кареток участников и поповер
комментария (`collaboration/src/vue/use-editor-layout.ts`). Якорь перетаскивания не подписан: он сам снимает
и ставит класс сдвига при замере и будил бы себя каждый кадр; он ставится по движению указателя.

Не закрыто: мгновенный сдвиг строки чистым CSS без перехода и без смены атрибутов (например, `:hover` с
отступом без `transition`) редактор не видит до следующего повода.

Отвергнуто: каретка участника виджетом в потоке текста (мешает вводу и IME, см. ADR коллаборации);
постоянный цикл замеров на каждый кадр; свой набор наблюдателей у каждого слоя (первый вариант правки —
три копии одного механизма).


## Место внутри блока (2026-11-12)

Вопрос пользователя (U14): человек правит ячейку таблицы документа, а у соавтора его каретка стоит в
абзаце под таблицей. Присутствие редактора знало только выделение текста; ячейка таблицы — не текст
документа, щелчок по ней выделение не двигает.

- Ядро: плагин `blockSpots()` (его ставит `NuiEditor`) хранит своё место вне текста —
  `{ block, part }`, id блока и путь внутри него. Команды `setBlockSpot(spot)` и
  `leaveBlockSpot(block)` меняют его метой транзакции: документ, выделение и история не трогаются.
  `blockSpotOf(state)` читает место. Места других людей отдаёт свойство плагина `spots(state)`,
  `peerSpotsOf(state)` собирает их со всех плагинов.
- Блок: контекст `NuiEditorBlockContext` получил `setSpot(part)`, `leaveSpot()` и `peers()` (места
  участников в этом блоке). `NuiEditor` раскладывает места по блокам один раз на список
  (`spotsInBlocks`) и отдаёт блокам через хозяина `NuiEditorBlockHost { run, focus, peers }`.
- Таблица документа: активная ячейка `NuiContentTable` (событие `cell` — id строки и ключ колонки)
  становится местом `[строка, колонка]`, пока фокус внутри блока; уход фокуса из блока снимает место.
  Места участников идут в проп `peers` и рисуются рамками `NuiTablePeers` (ADR таблицы). Строка
  ищется по id, поэтому рамка остаётся на ячейке при сортировке и фильтре, а у скрытой строки
  её нет.

Отвергнуто: ставить выделение документа в текст ячейки (ячейки правит таблица, а не вид редактора;
щелчок по ячейке двигал бы чужую каретку внутрь таблицы); каретка участника над таблицей (место в
ней не видно); отдельный канал присутствия у каждого блока (второе сообщение протокола на то же
событие).

## Поиск узла по id (2026-11-12)

Найдено в аудите: `byId`/`positionOf` строили индекс id всего документа на каждой новой версии. Любой
поиск по id после шага — проверка id во вставке (`replace` с узлами), плагин, ищущий блок каретки
соавтора или якорь комментария, — стоил полного обхода: 10 000 блоков — 13–25 мс на нажатие,
транзакция из 50 шагов с поиском — 1,4 с, из 3000 — исчерпание памяти (у каждого промежуточного
документа свой индекс).

- Документ, который построил шаг (`applyStep`), помнит предыдущий документ и карту шага
  (`DocLineage`). Поиск id: позиция в предыдущем документе (тем же способом, рекурсивно) →
  карта шага с привязкой вправо → проверка, что в новом документе там узел с этим id. Не нашёлся и
  позиция удалена — узел ищется только во вставленных участках карты (новые id появляются только там).
  Ответ кешируется в документе.
- Проверка не сошлась без удаления (карта не описала судьбу узла) — полный индекс, как раньше:
  ответ всегда верный, медленный путь — страховка.
- Цепочка не длиннее 64 документов: дальше документ строит свой индекс при первом поиске и
  отпускает предков. Документ с индексом обрывает цепочку. Цена — до 64 предыдущих версий в памяти
  (их общие узлы и так живы; своё у каждой — путь от изменённого места до корня).
- Индекс строится одним проходом с бегущей позицией, без массивов смещений у каждого узла (13 мс
  вместо 23 на 10 000 блоков).
- Проверка содержимого после замены детей (`matchesSplice`) отдаёт новому узлу состояния автомата,
  собранные из прежних (копия массива вместо прохода по всем детям корня на каждом шаге).

Замер (Node, 10 000 блоков): транзакция из 50 вставок с поиском блока перед каждой — 1404 → 35–46 мс,
300 — 7,7 → 0,18–0,19 с, 3000 — 1,8 с (раньше такая транзакция в команде таблицы исчерпала кучу 4 ГБ, P4); поиск дальнего блока после каждого из 100
нажатий — 1059 мс → в бюджете 100 мс. Проверка: свойство «каждый документ транзакции находит узлы,
как свежий индекс» (вставка, удаление, перенос копией, шаг `move`, обёртка и подъём, разрез, склейка,
смена типа; обратный порядок запросов), свойство «состояния автомата нового узла равны свежему
проходу», два бюджетных сценария (красные на старом коде).

Отвергнуто: постоянный индекс со структурным разделением (свой HAMT по поддеревьям — та же цена
сборки корня); индекс, выводимый из индекса предка копированием (O(n) на шаг); цепочка без предела
(удерживала бы все версии документа).
